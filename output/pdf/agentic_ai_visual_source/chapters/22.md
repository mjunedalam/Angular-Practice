# 22. Enterprise Governance, Privacy & Compliance

ShopAssist can copy one customer's information into a model request, a run checkpoint, a trace, a memory record and an evaluation sample. Each copy may be useful, but each has a destination, purpose and lifetime. If those decisions are accidental, the organisation cannot explain who received the information, why it was retained or how to delete it. Governance makes these choices explicit before the system begins multiplying data and authority.

Governance also controls what an agent is allowed to become. Adding a mutating tool, changing a refund limit or removing an approval requirement changes operational risk even when the application code barely changes. This chapter connects data classification, privacy, provenance, retention and change review. The aim is an organisation that can answer what the agent may do, with which data, under whose authority and with what evidence of actual behaviour.

:::analogy A records office with controlled folders
A records office labels files, checks who may borrow them, records their purpose and follows a retention schedule. Sending a folder to another office needs an approved destination, but destination approval alone does not authorise every person or every use. Agent governance follows each copy through models, tools, memory and logs. Where it stops: digital copies and derived summaries can spread invisibly. Labels and written schedules help only when enforcement and lineage locate every relevant copy and exception.
:::

## Governance versus guardrails

Guardrails act within a run: an input filter, a tool authorisation check or an approval gate decides whether a particular operation may proceed. Governance sets the rules those controls enforce, names their owners and checks their effectiveness over time. It determines which data classes a service may process, how autonomy changes are reviewed and what evidence must be retained. Neither substitutes for the other. A reviewed policy without execution enforcement is a promise, while an inline filter without ownership becomes difficult to maintain.

The operating team needs a register of agents, owners, purposes, data sources, tools and autonomy levels. AegisOps may diagnose incidents automatically while requiring approval for production mutations. ShopAssist may answer policy questions and propose refunds within customer scope. These purposes constrain later reuse. A general claim that the organisation operates an AI assistant is too vague to justify training, marketing or broad operational access using data originally collected for one customer-service task.

Governance is shared work between engineering, security, privacy, risk and the relevant business owners. Engineering builds classification, enforcement and audit mechanisms. Other owners determine applicable legal obligations and business limits. Describe that division without assuming that every regulation applies identically to every agent. Jurisdiction, deployment role, sector and use case change the requirements. The technical design should provide evidence that supports the actual mapping rather than claiming a generic checklist proves compliance.

## Data classification and policy enforcement

Classification assigns a handling category to data. A simple organisation might distinguish public, internal, confidential and restricted material. Public documentation can usually enter approved broadly available workflows. Internal runbooks need organisation controls. Customer and financial records require entitlement and appropriate provider terms. Restricted credentials, health information or payment data may need stricter handling or an explicit reviewed exception. The names are illustrative; use the organisation's real classification policy.

Classify at the source when possible. A database column's meaning is more reliable than trying to recognise every sensitive value in free text after retrieval. Carry class, tenant, purpose and lineage into tool results and state. Derived content should retain appropriate classification: summarising a confidential customer record does not make it public. If a transformation changes the handling category, record the approved transformation and its limits rather than silently relabelling the result.

Enforce data flow at each boundary: context assembly, model routing, tools, memory writes, telemetry and user outputs. A destination matrix says which classes a destination can accept, but that is only one condition. The requester must also be entitled, the purpose must be allowed, any required transformation must have occurred and any exception must be current. Self-hosting can satisfy a placement constraint; it does not automatically authorise processing restricted data for an unrelated task.

The following pseudocode makes those conditions visible. It assumes source-authenticated metadata and reviewed policy records, not labels supplied by the model. `exception_for` returns a verifiable exception with scope and expiry when policy requires one. `require_transformation` checks recorded evidence that an approved transformation was applied. The example is a policy interface, not a claim that one function supplies classification discovery, legal interpretation or lineage storage.

```python
def require_data_flow(item, destination, task, policy, now):
    policy.require_entitlement(task.principal, item)
    policy.require_purpose(item, task.purpose)
    policy.require_placement(
        item.classification, destination.region,
        destination.provider_terms,
    )
    policy.require_destination_class(item, destination)
    policy.require_transformation(item, destination)
    if policy.needs_exception(item, destination, task):
        exception = policy.exception_for(item, destination, task)
        if exception is None or now >= exception.expires_at:
            raise PermissionError("reviewed exception required")
        exception.require_scope(item, destination, task)
```

## PII, PHI and confidential-data handling

Personally identifiable information, protected health information and confidential business data need handling appropriate to their context. First ask whether the task needs the value at all. A refund explanation may need the payment amount and status without needing a full card number. Minimising the data removes exposure paths rather than trying to repair every copy afterward. Structural projections and source classification often make this easier than searching an entire transcript for patterns.

Tokenisation replaces a sensitive value with a reference whose original is held in a protected vault. The model might see customer_7c rather than an email address, while an authorised sending tool resolves the reference only for the approved recipient. Use opaque tokens with adequate entropy, tenant/purpose scope and collision handling. A short truncated deterministic hash can create collisions or unwanted linkage; it should not be presented as a general production tokenisation service.

Tokenisation is not necessarily anonymisation. If a vault or other information can reconnect the token to the person, the record remains re-identifiable and needs appropriate privacy controls. Masking, such as revealing only the last few digits, also reduces detail without automatically removing identifiability. Redaction removes selected values from outputs or logs, but it can miss indirect references and earlier copies. Evaluate the transformation against the actual privacy requirement rather than treating its name as a guarantee.

Encryption complements these measures. It protects bytes at rest and in transit, but an entitled model service or application still sees decrypted data during processing. Encryption cannot make an unauthorised purpose acceptable or prevent an application from deliberately sending plaintext to a permitted connection. Prefer avoidance and scoped transformations where useful, then maintain encryption and access controls around the necessary copies. These are cooperating controls rather than a simplistic strongest-to-weakest ranking.

Pattern detectors can find common emails, card-like numbers and identifiers. Use them as a baseline together with structured source knowledge and appropriate detection services. False negatives leave sensitive data exposed; false positives can damage the task by removing relevant facts. Record transformation versions and test representative languages and formats. Secrets should remain outside model context entirely, as Chapter 20 explains, rather than relying on a regex to redact them after generation.

## Retention, deletion and purpose limitation

Every artifact needs a retention reason and schedule. Run state can support recovery and disputes; traces support debugging; memory supports an approved continuing purpose; evaluation samples support quality improvement. Their lifetimes need not be the same. Retain full sensitive content only as long as justified, while metadata may have a different schedule. Legal holds and regulated recordkeeping can affect deletion, so the organisation must define the applicable policy rather than using a universal number of days.

Purpose limitation prevents data collected for one task from silently becoming available for another. A customer-service transcript should not become a marketing-training example simply because it is technically accessible. Record approved purposes and evaluate reuse through that policy. Production evaluation data may need consent or another applicable legal basis, minimisation and review. A self-hosted model does not remove those questions; the purpose is still a separate condition from the destination.

Deletion must follow lineage. Copies can exist in state, transcripts, object storage, memory, embeddings, caches, evaluation sets and derived summaries. Backups need a documented handling policy, including how expired data is prevented from reappearing after restore. An immediate live-store delete and a delayed backup expiry are different guarantees. Tell users and reviewers the actual deletion behaviour, and retain appropriate evidence that the workflow processed the relevant copies.

Avoid contradictory storage promises. An immutable audit record should not contain unnecessarily extensive personal content if that content may later require removal. Store minimal event metadata and protected references where possible, with retention and access policy appropriate to the record. Hashes are also not always anonymous when they can be linked or guessed. Governance needs to balance reconstructability with minimisation through deliberate schema and storage design.

## Auditability and decision/action provenance

Provenance connects an action to the request, agent release, evidence, policy, approval and observed effect that produced it. For an AegisOps rollback, the record should reveal the service and version change, why it was proposed, which evidence supported the hypothesis, who approved the exact proposal and how execution was verified. A model's final explanation alone cannot establish these facts because it may omit or misdescribe intermediate events.

Use linked event records with stable identifiers. Include the run and tenant, actor and on-behalf-of principal where applicable, event type, resource, proposal digest, policy version and evidence references. Approval events record approver identities and decision time; execution events record operation identity and observed result; verification events record the success criteria and outcome. The schema must support those fields rather than showing them only in a decorative diagram.

Protect audit integrity separately from routine logs. Append-only permissions, write-once archives or signed/hash-chained events can make changes detectable under their stated threat model. A hash chain alone does not prevent a writer from rewriting the entire chain. Anchor a trusted digest outside the writer's control or use protected append-only storage and verification. Record key rotation and verification procedures so future reviewers can assess integrity rather than merely observing a hash-shaped field.

Audit access also matters. Decision records can contain personal identifiers and operational details. Restrict who can read them, audit that access where appropriate and separate them from general-purpose debugging exports. A tamper-evident record that is freely disclosed can preserve integrity while violating privacy. Governance must establish confidentiality, integrity, retention and reconstructability together rather than treating one of them as proof of the others.

## Tenant isolation, residency and provider boundaries

Tenant isolation applies to every source and copy, as Chapter 20 explains. Data residency adds a placement condition: selected data may need to be processed and stored in an approved region. Model routing must consider that requirement together with quality and availability. State, indexes, telemetry and disaster-recovery copies need the same review. Failover to an otherwise healthy region can violate the placement contract if the tenant is region-pinned.

Review provider terms for retention, training use, subprocessors, regions and available account settings. Product branding is not a substitute for the actual contract and configured endpoint. Record the provider and region used by each consequential run. Self-hosting may provide stronger operational control over placement and retention, but it transfers patching, access and lifecycle responsibilities to the organisation. It does not automatically satisfy every privacy or sector requirement.

## Policy versioning, approvals and exceptions

Prompts, tools, instruction packs, model choices, risk policies and autonomy settings all change behaviour. Version them with owners and release review. A change to a refund threshold belongs to the business-policy owner as well as engineering. A new tool that can export restricted data may require privacy and security review. Record what changed and which release bundle uses it so an incident can be connected to the actual configuration.

Exceptions should be explicit, narrow, time-boxed records. An exception identifies its owner, permitted purpose, resource/data scope, destination and expiry, with the appropriate approval. Check it during execution; a note in a wiki or a prompt saying “special customer” is not an enforceable exception. Expired exceptions should fail safely and appear in operational review. Permanent exceptional behaviour may indicate that the underlying policy needs a deliberate revision rather than repeated informal bypasses.

## Governance review before increasing autonomy

Increasing autonomy includes adding mutating tools, raising limits or removing an approval gate. Require evidence for the business need, quality by critical slice, updated threat model, tested recovery and monitoring. Approval acceptance rate alone is insufficient because reviewers may have been fatigued or correcting proposals manually. Examine actual outcomes, rejected cases and security probes. Define a bounded rollout with kill switches and a named accountable owner.

Autonomy can be reduced as well as expanded. A model update, new attack or stale knowledge base may invalidate earlier evidence. Governance should connect monitoring to operational restrictions, not merely collect reports after harm. Review dates and trigger conditions make the autonomy register actionable. A system earns wider freedom through measured performance under its current conditions, rather than inheriting permanent trust from a successful launch.

## Regulatory and standards landscape

The EU AI Act uses risk- and role-based obligations, including requirements for particular high-risk systems, transparency duties and general-purpose model providers. Applicability and phased timelines depend on the use case and role. The NIST AI Risk Management Framework is voluntary and organises work through Govern, Map, Measure and Manage, with a generative-AI companion profile. ISO/IEC 42001 specifies an AI management system; certification of that system does not prove every generated answer is correct.

Data-protection and sector laws add separate obligations concerning lawful processing, purpose, rights, transfers and incident handling. GDPR, India's Digital Personal Data Protection framework and health or financial-sector rules do not become interchangeable because an architecture diagram uses the word compliance. Work with relevant owners to map specific obligations to evidence: classification and minimisation, audit records, oversight, evaluation, monitoring and change control. Keep the mapping dated and update it when the law or deployment changes.

## Build it: a governance starter kit

Start with a data inventory and approved purpose for one ShopAssist workflow. Map each class to its model, tool, memory, telemetry and output destinations. Add trusted enforcement points, transformation records and explicit exceptions. Define a minimal linked audit schema and protected storage, then establish retention and deletion coverage. Finally record release owners and the conditions for changing autonomy. These artifacts should connect to the actual running interfaces rather than remaining a separate compliance presentation.

Test one forbidden data flow, one expired exception, one audit-tampering scenario and one deletion request across derived copies. Record what each test demonstrates and which guarantees remain outside the implementation. The design question is whether the organisation can reconstruct and control the complete path, not whether it has many policy documents. A small enforced policy with clear evidence is more useful than a broad untested promise.
