# 14. MCP - Model Context Protocol

An enterprise capability often needs to serve several AI hosts: a development assistant, an incident investigator and a customer-support runtime. Rewriting the integration for each host creates duplicated discovery, schema and transport code. The Model Context Protocol, or MCP, standardizes how an application connects to capability servers and uses their tools, resources and prompts. It makes the connection reusable while leaving business authority and safe execution in the participating applications.

This chapter follows MCP revision 2026-07-28 and the official Python SDK 2.x documentation checked for this edition. Legacy deployments use earlier handshake-based revisions, so compatibility remains an explicit engineering concern. We will separate model function calling from MCP invocation, build a deliberately local read-only server and place an async client behind a controlled execution boundary. A transport connection is never permission to perform every operation it exposes.

:::analogy Standard connectors and a company equipment register
A standard connector lets a laptop recognize different approved devices without a custom cable for each one. The company's equipment register still decides which devices may connect, what software they require and who may use them. A network printer additionally has its own access and operating rules. Where it stops: a shared connector does not make a device trustworthy or interoperable in every feature. MCP peers need compatible protocol/transport/authentication contracts, and a server's description or annotation cannot grant itself permission.
:::

## Roles: host, client, server

The host is the AI application the user interacts with, such as ShopAssist, AegisOps or an IDE assistant. It owns the model-facing capability set, connection policy, user consent and task-level controls. A client is the protocol connection within that host, usually one per server connection. The server exposes capabilities backed by files, APIs, databases or other systems. A host can use several clients without giving those servers direct control over its model or unrelated resources.

MCP messages use JSON-RPC requests, responses and notifications. The model does not normally send JSON-RPC directly to the server. Instead, the host discovers tool contracts, presents permitted ones through the model provider's function-calling mechanism and receives a proposed call. The runtime applies its own checks, then the MCP client submits an accepted invocation. The server validates its own inputs and authority and returns a result for the host to interpret as data.

## Capabilities: tools, resources and prompts

Tools expose actions through names, descriptions and input schemas. A model may select them through the host, but execution remains host/server-controlled. Resources expose readable data by URI for application-managed context use. Prompts expose reusable parameterized templates for a user or supported host interface to invoke. These primitives differ in how they are selected and consumed; treating all discovered content as trusted standing instructions discards that useful separation.

A read-only observability tool can return a measured series; a resource can expose its runbook; a prompt can prepare a diagnostic question. The host still verifies whether each is appropriate for the current user and task. Resource text and returned templates can contain third-party instructions, so their trusted status depends on reviewed source policy. A standardized URI or schema says how to exchange material, not whether its content is authoritative.

The 2026-07-28 revision supports multi round-trip input requests. Elicitation asks for needed user information through an input_required result and continuation behavior defined by the protocol. Earlier peers used server-initiated request patterns; sampling asked a host to generate model output and roots described file access boundaries. Sampling, roots and protocol-level logging are deprecated in the documented modern core, with migration guidance. Do not silently apply new semantics to an old peer that still negotiates a legacy contract.

Long-running work can use the optional tasks extension when both peers support it. Task handles, status polling and input updates suit operations that outlive one immediate response. An extension is not available just because a server speaks core MCP. Negotiate support, define fallback and preserve cancellation/recovery semantics. Likewise, tool annotations can describe read-only or destructive intent, but an untrusted server's hint is not a sufficient basis for granting authority.

## Lifecycle and discovery

Modern requests carry protocol version and client capability metadata. There is no initialize handshake for the 2026-07-28 modern contract; a client may use server/discover to learn support or handle a version rejection. Legacy revisions through 2025-11-25 use initialize/initialized behavior, and HTTP deployments may involve protocol session identifiers. The official SDK documents dual-era compatibility. Record the chosen revision so traces and support cases can be interpreted against the correct semantics.

Discovery returns tool, resource and prompt catalogs with their contracts. Treat that information as a proposal for review, not an instruction to expose everything to the model. Apply server and tool allowlists, namespace local capability names and compare pinned contract/description hashes. Schema drift includes changes to descriptions because tool poisoning can live in wording even when field types stay unchanged. A changed contract should be reviewed before the host accepts its use.

Catalog change notifications and cache hints improve operations but need compatible support and cautious caching. A running agent should not silently gain a new destructive tool because a server updated its list. Pin the reviewed capability release for the task or explicitly approve a controlled refresh. Retain the server identity, selected protocol revision and resolved schemas in provenance. Discovery helps portability only when the host knows which advertised features it actually supports.

## Transports: local and remote servers

A local stdio server runs as a subprocess selected by the host and communicates through standard input/output. It is useful for development tooling and approved local files, but its process permissions are consequential. Launching a server can execute arbitrary installed code. Review the binary/package and arguments, constrain environment and filesystem/network access where needed and keep credentials out of prompt content. Local does not mean harmless or authenticated automatically.

Remote Streamable HTTP servers are operated services with network exposure, scaling, identity and tenant obligations. The older HTTP+SSE transport is legacy/deprecated, so compatibility should be planned rather than guessed. The modern transport's exact request and subscription behavior is revision-specific. Deploy remote servers behind appropriate TLS, authentication, authorization and rate limits. A host supporting MCP in one transport/revision does not necessarily support every remote extension or credential flow.

## Build it: a read-only MCP server

The following complete server-definition file uses the documented SDK 2 MCPServer interface and synthetic data. It has no production metrics client or hidden runbook service. Both the tool and resource enforce the same service allowlist. It is intentionally a local public-data demonstration, without remote authentication or multi-tenant policy. The SDK supplies request parsing and schema derivation; business checks still belong in the handlers.

```python
from typing import Annotated
from pydantic import Field
from mcp.server import MCPServer

mcp = MCPServer("observability-demo")
SAMPLES = {"checkout-api": {"p50": 210, "p95": 1800}}

@mcp.tool()
def query_latency(
    service: str,
    window_minutes: Annotated[int, Field(ge=5, le=1440)] = 60,
) -> dict:
    """Read synthetic latency values; not live production metrics."""
    if service not in SAMPLES:
        raise ValueError("service is not allowed")
    return {"service": service, "window_minutes": window_minutes,
            "quantiles_ms": SAMPLES[service], "synthetic": True}

@mcp.resource("runbook://{service}/latency")
def latency_runbook(service: str) -> str:
    if service not in SAMPLES:
        raise ValueError("service is not allowed")
    return ("Inspect current metrics and changes "
            "before proposing action.")
```

Save it as observability_server.py in an isolated Python environment using SDK 2.x. Install the CLI extra and launch through the documented runner. Resolve an exact tested patch release into your dependency lock before sharing the example as a reproducible deployment. The range below selects the compatible major for exploration; it is not an immutable production pin. Record the resolved package version and chosen protocol revision with the client connection.

```bash
python -m pip install 'mcp[cli]>=2,<3'
mcp run observability_server.py --transport stdio
```

Connect a compatible host or inspector and verify tool discovery, valid/invalid windows and allowed/disallowed service names for both primitives. Synthetic quantiles do not change with the window; the field demonstrates schema validation rather than a real aggregation. Replace the data source only after adding the actual metrics query, principal/resource policy, freshness and error contract. Calling this definition read-only says what it does, not that every possible host can expose its data without review.

## The client side: MCP behind your tool registry

The SDK 2 Client is used inside an async context manager. list_tools returns a result with tools, whose input_schema and description can be checked. call_tool returns structured content, content blocks and an error indicator. Normalize those fields into the host's common result contract while preserving source, status and bounds. Do not stringify a coroutine or discard error status merely because the API call itself returned normally.

Keep one internal capability definition across local and MCP-backed operations: exact name/version, reviewed input contract, scope/risk policy and an awaitable executor. Namespace the host's exposed name separately from the server's raw tool name. The synchronous Chapter 11 harness cannot accept an async function as tool.fn without an explicit execution-model change. In an MCP-capable runtime, use a coherent async executor and preserve the same authorization, approval, budget and effect contracts around awaitable calls.

```python
import asyncio
from mcp import Client

async def inspect_demo(server_url):
    async with Client(server_url) as client:
        catalog = await client.list_tools()
        names = {tool.name for tool in catalog.tools}
        if "query_latency" not in names:
            raise ValueError("required demo capability is absent")
        result = await asyncio.wait_for(
            client.call_tool("query_latency", {
                "service": "checkout-api", "window_minutes": 60,
            }), timeout=5.0,
        )
        if result.is_error:
            raise RuntimeError("demo tool reported an error")
        return result.structured_content
```

This is a complete inspection function, not a production policy adapter. It calls a known public synthetic demo tool and lacks schema pinning/authentication because those belong in the reviewed client configuration and controlled executor described here. An asyncio timeout stops waiting; it does not prove a remote mutation was cancelled. For mutating MCP tools, retain accepted identity and reconcile uncertain outcomes according to the server/backend contract, just as for other network operations.

## Authentication, permissions, consent and trust

For protected remote HTTP servers, MCP defines an OAuth-based authorization framework. The authorization server issues access tokens for the resource server; clients and servers follow the applicable discovery, issuer and audience rules. Authorization support is optional in the core, so do not assume every reachable endpoint protects data. The enterprise host must reject inappropriate connections and apply the identity requirements of its intended use.

The host decides whether this user/agent may connect to a server, which capabilities may reach the model and which calls require review. A gateway can validate identity, apply routing, quotas, auditing and data-loss policy. The server checks the identity's authority over the requested resource/arguments. The backend enforces its own rules. These checks overlap usefully without becoming interchangeable: a valid access token does not decide whether the agent should perform a high-risk change now.

Use audience-bound tokens and narrow scopes. Do not pass a broad user token through to an unrelated backend; obtain appropriate downstream credentials or use an authorized token exchange. Validate the selected authorization issuer and keep credentials keyed to the right issuer/resource. The documented current revision prefers Client ID Metadata Documents and retains deprecated dynamic client registration for compatibility. Consent should explain the server connection and newly requested authority, while exact risky actions may require separate approval.

## MCP tool versus ordinary application tool

From the model's view, both can be represented as a function contract. Operationally, an in-process tool usually changes with the host's deployment, while a remote MCP server can change independently. A local call and a network call also have different latency/failure contracts. Keep the same task-level execution boundary, then add source review, schema pinning, version/transport compatibility and network recovery for remote capabilities. Portability should not erase useful operational distinctions.

## Enterprise patterns: registry, gateway, versioning and governance

An MCP registry records approved servers, owners, releases, transport/authentication requirements, data classes, risk and capability contracts. A gateway can provide a controlled route with identity and audit, but it must not become an unreviewed shortcut around server/backend policy. Separate trust domains and financial/destructive surfaces deliberately. A read-only release should not quietly gain mutations under the same approval assumptions.

Test server upgrades in a shadow or controlled staging release before exposing changed contracts broadly. Compare discoverable capabilities, descriptions, result schema and client behavior, then pin the approved assembly. Trace calls with server/tool identities, schema hashes, principal context and latency under privacy rules. Unmanaged shadow servers create unknown data paths; connection allowlists, reviewed registry entries and egress controls help make those paths visible and containable.

## Portability of skills and capabilities

A reusable skill can expose an MCP tool for its executable contract, resources for approved reference material and prompts for standard invocations. Its deterministic core, authority and tests remain in the package/service, while MCP supplies the doorway. Folder-based skill interoperability and optional protocol extensions have their own requirements. Test compatible hosts, revisions and authentication rather than claiming that every compliant client can use every extension unchanged.

## Failure modes

Auto-trusting discovered tools exposes malicious descriptions. Unpinned upgrades change behavior while a task is running. Token passthrough creates overbroad or confused authority. Unbounded outputs flood context. Async/sync mismatches return coroutine objects instead of observations. Mixed risk surfaces can hide privilege escalation. Diagnose these failures through connection provenance and the common execution boundary, keeping transport errors distinct from server tool errors and unknown external effects.

## Interview drills

Explain model function calling as generated intent and MCP as application/server capability exchange. Describe host, client and server roles using one call. State the revision before explaining negotiation and legacy behavior. For security, trace consent, audience/scopes, resource authorization and exact action review. For portability, name compatibility requirements and retained business contracts. A useful answer includes what the host refuses to expose, not only what the server advertises.

## Key takeaways

MCP reduces duplicated connection work while leaving authority explicit. Hosts choose reviewed capabilities, clients speak the compatible protocol, servers validate their resources and backends enforce invariants. Discovery is valuable but untrusted until governed; annotations and risk hints do not grant permission. Use coherent async execution for network clients, retain version/schema provenance and treat uncertain effects like any other external operation.
