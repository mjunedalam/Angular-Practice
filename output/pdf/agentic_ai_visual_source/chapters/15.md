# 15. A2A & Remote-Agent Interoperability

AegisOps can investigate application latency itself, but the database team owns the PostgreSQL diagnostic service. That team uses different models, tools and deployment rules. Giving the incident commander access to every database tool would erase an important ownership boundary. A better arrangement lets the commander request a diagnosis, track the work and inspect the result while the database team retains control of its implementation.

This chapter explains that arrangement. You will describe a remote capability, establish who may use it, submit a bounded task, handle questions and failures, and bring the result back into your own evidence ledger. The central problem is not transporting a prompt. It is maintaining a reliable relationship between two independently operated systems, neither of which should gain authority merely because the other produced convincing text.

:::analogy Commissioning an outside contractor
A project manager commissions a specialist report. The contractor advertises services, receives a written brief, asks questions, submits deliverables and may miss a deadline. The manager keeps responsibility for the overall project and checks the report before relying on it. An Agent Card resembles the contractor's profile; a remote task resembles the work order. Where it stops: a profile and signature establish claims and origin, not competence, correctness or automatic deduplication. Those require explicit contracts and checks.
:::

## Why a remote agent is more than a simple tool call

A simple tool interface describes an operation and its arguments. A remote agent can accept a goal, choose its own intermediate operations and return a deliverable after several interactions. Its caller may not know the implementation or be allowed to inspect it. That makes task identity, progress, questions, cancellation and acceptance criteria part of the contract. A function-shaped interface can still expose this behaviour, but the caller must understand what happens behind that interface.

Do not define the distinction by speed or determinism. A tool can run for hours, call a model, ask for further input or cross an organisation boundary. A remote agent can finish immediately. The useful distinction is the responsibility exposed to the caller: requesting a capability through its operation contract, or commissioning independently managed work through a collaboration contract. A2A and MCP overlap in transport patterns while addressing different integration concerns.

The open Agent2Agent protocol supplies a vocabulary for agent discovery and collaboration. In this edition, protocol examples refer to A2A 1.0; production adapters should pin the specification and SDK versions they actually support. Protocol interoperability does not make policies interchangeable. Two teams can agree on a task message format and still disagree about data access, deadlines or what constitutes a satisfactory answer. Integration tests need to cover those decisions as well as wire-format parsing.

## Identity, discovery and capability cards

Discovery answers where a suitable agent can be found. An Agent Card describes the advertised agent version, supported interfaces, skills, content modes and authentication requirements. An interface combines an endpoint with a protocol binding and protocol version. An advertised skill narrows the broad agent description into a task the caller can reasonably request. This helps the commander choose database diagnosis instead of sending an unrestricted instruction to an unknown service.

An enterprise agent registry, governed alongside the MCP registry from Chapter 14, can add information the public card does not establish: the owning team, approved environments, allowed tenants, data classifications, support contact and integration test results. Static configuration is also reasonable for a small deployment. A well-known discovery address is convenient, but discovery itself is not authorisation. The caller must verify that the endpoint belongs to the approved service and that its configuration has not drifted since the integration was reviewed.

Signed cards protect authenticity and integrity when the signature is verified against a trusted key. They do not prove that a skill works, that an endpoint is currently healthy or that its outputs are true. Signed cards were supported before version 1.0, so avoid treating their presence as a newly introduced correctness guarantee. Pin an accepted card or its relevant contract fields and decide which changes require re-review: a new endpoint, broader data modes or changed security requirements usually do.

For AegisOps, the approved registry entry might describe a database reliability agent with two skills: query-performance diagnosis and replication-health inspection. The registry permits read-only diagnosis for tenant Northwind's clusters and disallows customer record exports. The Agent Card advertises how to connect; the registry and policy engine decide whether this caller may connect for this task. Keeping those decisions separate prevents an attractive skill description from becoming an entitlement.

## Task delegation, status, messages and artifacts

A task is a stateful unit of remote work. Its identifier connects the original submission, later messages, progress updates and outputs. Messages carry interaction between caller and worker. Artifacts are deliverables, such as a diagnosis JSON file or a report. Status describes whether the work is pending, progressing, waiting for input or finished. These objects serve different purposes; a friendly progress message should not be mistaken for a validated result.

In the database example, the commander sends incident INC-77, the approved cluster identifier, a time window and references to relevant metrics. The worker may reply that the cluster identifier is ambiguous. An input-required state therefore pauses the investigation rather than proving that it failed. The commander obtains the missing identifier from trusted run state or asks an authorised human. It then continues the existing task instead of starting a second investigation with a longer prompt.

An authentication-required interruption is different. A model should not paste credentials into a conversation to satisfy it. The application must route that requirement through the approved identity flow and determine whether continued access remains within the task's authority. A rejection is also different from a technical failure: the remote agent may decline a task it does not support. Completed, failed, rejected and canceled outcomes should remain distinct in local state and user-facing explanations.

Artifacts need acceptance rules agreed before submission. A diagnosis might require the affected cluster, observation window, findings linked to evidence, uncertainty and proposed next checks. Parse its shape, verify the referenced resources belong to the expected tenant, and label its provenance. Schema validity establishes that required fields exist; it does not establish that the diagnosis is correct. The commander should compare the report with independently obtained evidence before proposing a consequential action.

## Synchronous, streaming and asynchronous interaction

Synchronous interaction holds a request open until a result arrives. It suits short work with a bounded duration and a simple caller. Streaming keeps the caller informed through progress and partial results. Asynchronous interaction returns a task handle so the caller can disconnect and retrieve progress later through polling or a callback. A system may combine these modes: stream while a user is present, then continue asynchronously if the work outlasts the interactive window.

For a long investigation, correctness should survive loss of the stream. Store the remote task identifier and a local status checkpoint before entering a durable wait. On reconnection, query the task rather than assuming the missing connection means failure. A callback is a notification to examine authoritative state, not an instruction to execute whatever its payload suggests. Authenticate its source, match it to an expected task and process duplicate notifications without repeating the local transition.

Choose polling frequency from the operational need rather than from the model's eagerness. Polling every second for a day-long task creates unnecessary traffic; polling every minute for a ten-second user interaction feels unresponsive. Enforce an individual RPC timeout, a task deadline and an overall run budget. The first bounds one network call, the second bounds the delegated job, and the third protects the caller's whole workflow. One timer cannot reliably serve all three purposes.

## Handoffs versus remote-agent calls

A handoff changes which component controls the next stage of a conversation. ShopAssist might route a billing question to a refunds specialist, which now selects the next response. Delegation keeps the caller in control: AegisOps commissions a database diagnosis, receives findings and decides what to do with them. Either pattern can cross a runtime boundary, so physical location is not the definition. Ownership of the current goal and continuation is the clearer distinction.

Write that ownership into state. During delegation, the commander owns the incident, budget and stopping decision; the remote worker owns only its bounded task. During a handoff, record the receiving owner, relevant context, pending obligations and an escape path if the recipient cannot continue. A transfer of software control does not erase organisational accountability. The human team operating the overall service remains responsible for defining the authorised behaviour and handling failures.

## Authentication, authorisation and tenant boundaries

Every call needs a verified caller identity and an explicit permission decision. A workload identity identifies the software making the request. Where the agent acts for a user, preserve that user relationship through the approved delegated-access mechanism described in Chapter 20. Request a scope for database diagnosis rather than a broad administrative token. The remote system must enforce its own resource and tenant checks; trusting a tenant field supplied by the caller is insufficient.

Send the smallest useful brief. Resource identifiers, time windows and permitted evidence references often suffice. Do not send the entire incident transcript, unrelated customer records or credentials merely because the remote context window is large. Reference-based sharing still requires authorisation: the worker must not gain access to a document simply because a URL appears in the message. Expire shared references where appropriate and record which data was released to which remote service.

On the return path, remote output is external data. A report can contain attacker-controlled log text or instructions embedded in a retrieved document. The caller must not treat such text as policy, permission or a new user request. Keep provenance and trust labels when reports pass into another agent. An instruction to restart a database in a diagnosis artifact remains a recommendation to evaluate; it is not an approved action or a reason to expand credentials.

## Timeouts, partial failure and idempotent delegation

An unanswered submission has an uncertain outcome. The remote service may have created the task even though the response never reached the caller. Repeating the request can create duplicate work unless the service has an agreed deduplication contract. A2A assigns task identifiers on the server. The caller can send a stable message identifier, but A2A 1.0 permits rather than requires idempotent Send Message behaviour. Verify support instead of assuming that identifier reuse is enough.

A robust adapter persists a logical delegation key before submission and maps it to the returned remote task identifier. The remote service or gateway must atomically recognise repeated submissions for that key within a documented retention window. If the create response is lost, the caller needs a supported lookup or reconciliation path. When no such mechanism exists, record outcome-unknown and escalate or reconcile before creating replacement work. Avoid a helper named get-or-create unless its contract actually establishes these semantics.

A timeout after task creation is easier to recover: query the saved task ID, continue waiting within the deadline or request cancellation. Cancellation is best effort for work already underway; it may not undo effects the remote service performed. A diagnostic worker should be read-only, but even reads can incur cost or reveal data. Accept partial artifacts only if they pass validation, label their limitations and make missing evidence visible in the final conclusion.

The following pseudocode assumes a durable store, a deduplicating remote adapter and bounded RPCs. Its purpose is to show ordering, not supply those services. The adapter must document key retention, task lookup and what happens when creation has an uncertain outcome. A production implementation also authenticates calls, handles version negotiation and records trace context. Keeping these interfaces explicit makes the example honest without hiding the critical idempotence requirement in an unexplained utility.

```python
async def start_delegation(store, remote, key, brief):
    op = await store.reserve_delegation(key, brief)
    if op.task_id is not None:
        return await remote.get_task(op.task_id)
    # Required adapter contract: atomic dedupe by key.
    task = await remote.submit_once(key, brief)
    await store.bind_remote_task(key, task.id)
    return task
```

```python
async def inspect_task(remote, task_id, validate):
    task = await remote.get_task(task_id)
    if task.state == "completed":
        return {"status": "received",
                "artifacts": validate(task.artifacts)}
    if task.state in {"input-required", "auth-required"}:
        return {"status": "waiting", "request": task}
    if task.state in {"failed", "rejected", "canceled"}:
        return {"status": task.state, "reason": task.reason}
    return {"status": "working", "task_id": task_id}
```

## Gateways, versions and cross-platform interoperability

A gateway can centralise authentication, token exchange, rate limits, contract validation and audit for remote calls. It can also translate transport bindings or maintain an organisation's deduplication extension. That translation is a responsibility, not magic compatibility: preserve task identity, terminal states, content modes and error meanings. If one backend cannot support a required lifecycle feature, reject the integration clearly rather than flattening a long task into a misleading immediate success.

Version the Agent Card, skill expectations and local adapter together. Run contract tests in staging for normal completion, input-required, rejection, duplicate submissions, callback duplication and lost responses. Trace a delegation as a child of the caller's run while retaining both the local operation key and remote task ID. Use a circuit breaker for persistent dependency failure and a documented fallback such as reduced local diagnosis or escalation to the database team's humans.

## MCP versus A2A, and the final design choice

MCP connects applications with exposed capabilities such as tools and resources. A2A supplies an agent-collaboration contract with discovery, messages, tasks and artifacts. A remote database agent may use MCP internally, and the commander may expose an A2A delegation through its own tool registry. MCP also has task-oriented extensions for long-running work, so “long task means A2A” is not a sufficient architecture rule. Select the contract whose ownership and lifecycle semantics match the integration.

Before integrating a remote worker, answer a design question: what does the worker own that the caller should not absorb? Then answer the recovery question: how will the caller find the same job after a lost response or restart? If either answer is vague, the attractive multi-agent diagram is premature. A small, explicit remote contract usually produces a more dependable system than sharing broad prompts, context and authority between teams.
