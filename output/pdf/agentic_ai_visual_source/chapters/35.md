# 35. Architecture Selection Patterns & Senior Design Review

Knowing many patterns creates a new problem: a system can accumulate them faster than it earns their benefits. A router adds a decision, a specialist adds coordination, a memory adds retention, and a durable workflow adds operating responsibilities. The senior task is choosing the smallest arrangement that meets the actual requirements, then showing the evidence behind each addition. Complexity is justified by a need and a measured result, not by the vocabulary used in its diagram.

This chapter turns the earlier material into a selection and review method. We will use ShopAssist's billing-dispute flow as a worked design: answer policy questions, investigate duplicate captures, propose a refund and execute only under the required authority. Some steps are fixed; others depend on evidence. The design review examines both paths and asks what fails when the model, a dependency or a human decision is wrong.

:::analogy Choosing a treatment with a careful clinician
A clinician does not prescribe every available treatment. They identify the problem, choose a treatment whose benefits fit it, consider side effects, and check whether the patient improves. Architecture selection similarly needs indications, limits and evidence. A sophisticated pattern can be the wrong prescription for a simple task. Where it stops: software design is not clinical diagnosis, and no architecture flowchart decides the answer automatically. Organizational authority, operating capacity and observed workload behavior must still be examined directly.
:::

## Pattern reference

### Control patterns

A deterministic workflow is appropriate when required steps are known. It can still include model extraction or drafting inside nodes. For a refund, order lookup, eligibility validation, approval and accounting are usually mandatory. Their sequence should not depend on the model remembering it. A workflow becomes restrictive only when it tries to predetermine genuinely exploratory investigation, such as which evidence source will clarify an ambiguous dispute.

A router chooses among finite handlers. Use it for distinct intents with clear fallback behavior, such as order status versus returns policy. Measure misrouting on overlapping requests and allow clarification. A bounded ReAct loop lets the model choose the next tool from each observation; it fits open investigation, but needs cost, time and capability limits. Plan-and-execute makes a proposed sequence inspectable, with replanning when new evidence invalidates assumptions.

Reflection or evaluator-optimizer work is useful when the critic supplies a clear rubric, external evidence or a check the original generator did not perform. Repeatedly rereading the same draft with the same knowledge may add cost without reliability. Graph orchestration makes mandatory states, parallel work and pauses explicit. Use its control where it helps, without turning a trivial extraction into a distributed graph merely because a framework provides one.

### Collaboration patterns

A supervisor coordinates scoped workers while retaining the task's goal, state and budget. This fits AegisOps when telemetry, knowledge and change investigation genuinely benefit from separate capabilities. A handoff transfers control between domains; it needs an explicit ownership transition. If accountability must remain with the original owner, expose the specialist as a bounded subtask instead. Returning findings and owning the incident are different responsibilities.

Remote agents belong at real organizational or runtime boundaries. A2A can carry tasks, status and artifacts, while the caller still constrains delegated authority. Parallel workers help independent questions meet latency targets; they hurt when quotas are tight or the tasks require each other's results. Hierarchy can reflect large ownership structures, but each level adds delay and ambiguity. Ensembles can reveal useful disagreement, provided they do not merely repeat correlated mistakes at greater expense.

### Knowledge and memory patterns

Begin with baseline retrieval for a direct question over a governed corpus. Add agentic retrieval when the task requires choosing sources, resolving subquestions or checking sufficiency. Graph retrieval helps questions whose meaning depends on relationships, provided reliable entity and edge data exist. A diagram showing a knowledge graph does not compensate for missing or inconsistent entity definitions. Evaluate retrieval separately from the final answer so failures can be diagnosed.

Governed SQL tools suit quantitative questions with agreed definitions and entitlement rules. Their output should preserve the query, units, population and time interval. Memory supports continuity and personalization when the retained information has a lawful, useful purpose and a deletion path. It should not duplicate volatile system-of-record facts as authoritative truth. ShopAssist can remember a preferred language while still refetching a payment's current refund balance before acting.

### Safety and recovery patterns

Risk-based approval applies to consequential actions under the organization's policy. A pre-approved runbook is a precise exception with bounded conditions, not a general license to skip review. A reader/actor separation reduces the combination of untrusted content and sensitive tools, while both sides still need validation and scope. Sandboxing contains generated code or UI actions; it requires an explicit filesystem, network, resource and secret policy.

Retries, replanning, compensation and escalation address different failures. A definite transient read failure may be retried. An unknown mutation outcome must be reconciled. A changed environment can require a new plan and approval. Compensation semantically reverses an applied effect when authorized and possible; it is not an automatic undo button. Evaluated model fallback or a degraded read-only mode can preserve useful service without substituting a different unapproved action.

## Decision matrix: choosing the architecture

Ask first whether the next steps are known. If they are, begin with a workflow and use models only inside the steps that benefit from them. If the path depends on observations, use a bounded agent for the exploratory part. Then ask whether one domain, capability set and permission scope can handle the task. Do not split an agent merely because its prompt contains several headings.

Distinct intents may justify a router and handlers. Independent investigations may justify parallel workers. Different permissions, ownership or model requirements may justify specialists. Long waits or mandatory state transitions may justify a durable workflow around the exploratory loop. These questions are not a mechanical scoring system. A regulated approval boundary may outweigh a small latency gain; a team unable to operate extra infrastructure may favor a supported managed path.

Overlay authority, knowledge and recovery on the chosen control. Untrusted documents plus sensitive tools require scope and injection defenses. Executable code requires isolation. Quantitative answers require definitions and database enforcement. Cross-session continuity requires owned state and governed memory. A request lasting longer than the connection requires asynchronous status and durable progress. Each overlay should address a named failure rather than serve as decorative completeness.

For ShopAssist, start with a single bounded investigator reading order, payment and policy evidence. It returns a structured eligibility proposal. A deterministic service validates accounting and approval requirements, then dispatches the effect. No second agent is needed merely to call `issue_refund`. If the organization later separates policy research from private order access, that real permission boundary may justify an additional reader. The decision changes because the boundary changed, not because multi-agent designs became fashionable.

## The architecture review

### Walk one risky request

Begin with the user and intended outcome. A customer says two captures occurred for order ORD-104233. Authentication establishes the principal, while the order service checks ownership. The investigator reads current captures and applicable policy, producing evidence IDs. The validator determines whether the extra capture is eligible and fixes payment, amount, currency and logical effect identity. Only then is an approval request meaningful.

The support lead sees the exact proposal, evidence, expected impact, expiry and recovery options. The approval service checks the lead's role and records authority bound to that proposal. The executor revalidates current refund accounting and consumes or reserves approval atomically with local intent. It sends the persisted key to the payment provider. A timeout after provider processing becomes outcome unknown; continuation reconciles before another effect. This walk exposes more architecture than a diagram listing nine generic services.

### Review through fixed lenses

The autonomy lens asks why an agent is needed and what each action class may do. The control lens asks who chooses the next step, what limits apply and what ends the run. The tool lens asks which capabilities mutate, which credential reaches them and how duplication is prevented. The state lens asks what survives a crash and how old records remain interpretable after a release. Each answer should point to evidence.

Context, knowledge and memory lenses examine what the model sees, how evidence is scoped, what is retained and what can be forgotten. Security and identity lenses examine injection, exfiltration, delegation and tenant separation. Governance examines data flows, audit and behavioral change control. Reliability asks about timeouts, dependency failures, uncertain effects, compensation and dead-letter recovery. Do not merge these into one vague “safety” checkbox; their failures require different controls.

Quality asks for labeled cases, critical slices, calibrated judges and outcome checks. Operations asks for SLOs, dashboards, ownership, runbooks and emergency controls. Cost and scale ask for admission limits, quotas, capacity and cost per successful task. Simplicity asks which component can be removed. A review should leave a small list of evidence gaps and decisions, each with an owner and due condition, rather than an unprioritized catalogue of possible improvements.

### Ask what can be removed

Try removing a reflection loop that has no measured benefit, a second agent sharing the same tools and permissions, or a memory duplicating current application records. Replace a known-intent model router with rules where the data supports that choice. A smaller design is not automatically better: removing durable approval storage to simplify the diagram would violate the lifecycle requirement. Simplification preserves the necessary contract while reducing unnecessary machinery.

Use controlled comparisons to test disputed complexity. Hold model version, tasks, prompts, grading and environment constant while changing the mechanism. Use slice analysis to report success, safe escalation, false completion, cost, latency and operational burden by case type. The clinician analogy helps here: keep the needed treatment, remove the ineffective addition, and measure the outcome. Architectural taste alone is insufficient when the decision affects users and operators.

## Production-readiness gates and launch checklist

Launch gates require an owner, pass condition and inspectable evidence. The design gate confirms requirements and autonomy boundaries. The security gate verifies scoped authority and adversarial behavior. The quality gate evaluates critical slices and uncertainty. The reliability gate demonstrates crash continuation, dependency failure and effect reconciliation. The operations gate verifies alerting, on-call access and recovery. Governance confirms data and change-control obligations. The rollout gate controls exposure and rollback through a canary release.

Zero successful forbidden actions is a required test result, not proof that no attack can ever succeed. State the corpus, threat assumptions and residual risks. Confidence intervals should use independent cases as their observational unit; repeated runs measure variability but do not turn one case into many independent tasks. A small suite can block known regressions while still requiring shadow observation and careful rollout. Avoid dressing finite evidence as universal safety certification.

For the ShopAssist launch, preserve read-only answers if refund execution is disabled. Test the kill switch at the executor, not only in the prompt. Rehearse provider failure, an approval that expires, a late response and a run that exhausts its budget. Operators must be able to locate the customer's status and hand off without inventing an outcome. A useful degraded mode tells the customer what is known and who owns the remaining work.

Increasing autonomy is another release decision. A high approval rate alone is not enough: reviewers may be rubber-stamping poor proposals. Examine error and reversal rates, acceptance accuracy, critical scenario coverage, blast radius and recoverability. Define the exact action segment eligible for changed policy, then stage the change with monitoring and a return to the prior mode. The model's confidence is evidence to analyze, not authority to remove the approval gate.

## Senior system-design interview drills

A clear design answer follows the request through its boundaries. First clarify the users, goal, scale, latency, data and risky actions. State which parts are fixed and where adaptive choice helps. Draw the smallest coherent control plane. Walk one read path and one effect path, including approval and a crash. Then discuss evaluation, operations, cost and the simplifications considered. This order connects requirements to implementation instead of producing a diagram before understanding the problem.

For a telecom billing-dispute agent, begin with bill ownership and the allowed adjustments. Separate explanation from account mutation. Retrieve the governing tariff version and current account facts, then show how a disputed charge becomes a bound proposal. Describe what happens when evidence conflicts, when the billing service processes an adjustment but its response is lost, and when no eligible remedy exists. An explicit refusal or safe handoff is a valid outcome when the system cannot establish authority.

When asked to design an enterprise platform, state which shared services earn centralization: an LLM gateway for model accounting, policy, tool identity, approvals, run ownership and observability. Distinguish services that must be separate from modules that can share a process. Explain tenancy and fair admission under a workload spike. Choose one durable execution strategy and define its business-effect contract. A platform should support different agents without making every agent pay for the largest deployment architecture.

When asked what you would cut for an MVP, name a component and the contract preserved by the cut. Merge investigators with identical scopes, defer optional remote agents, or start with one evidence corpus. Keep eligibility, approval binding, effect reconciliation and basic operating controls. The question tests judgment: removing necessary safeguards is not simplicity, and adding every possible specialization is not future-proofing.

## Key takeaways

Choose control for the work, then add knowledge, collaboration and recovery where explicit requirements need them. Review designs by walking real requests and demanding evidence for each promise. Treat launch and autonomy expansion as owned decisions with finite test evidence, operational rehearsal and staged exposure. Ask what can be removed without breaking the contract. The strongest design is the one whose complexity can be explained through the outcomes it actually improves.
