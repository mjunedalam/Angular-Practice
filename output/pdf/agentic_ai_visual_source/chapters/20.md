# 20. Identity, Authorization & Delegated Access

A support employee asks ShopAssist to refund an order. The employee has permission to handle that customer's account, but the agent runs as a service that also serves thousands of other accounts. If the service uses one broad payments credential for every request, the downstream API sees the service's power rather than the employee's entitlement. A user who can persuade the agent may gain capabilities they never possessed directly.

This is a confused deputy problem: a privileged service uses its own authority on behalf of a requester who lacks the relevant permission. The correction is to separate who asked, which software is acting and what credential reaches the target system. Authentication establishes those identities; authorisation determines whether this action is allowed on this resource with these arguments. The same design also needs a defined mode for background jobs with no user present.

:::analogy A courier collecting one document
An account holder asks a licensed courier to collect a document from a bank. The bank checks the account holder's permission and the courier's identity, then issues a pass for that collection rather than a master key. The requested service, requester and limited credential are distinct. Where it stops: a digital bearer token can be reused during its lifetime unless additional controls prevent that. A pass also needs validation at the destination; merely printing restrictions on it does not enforce them.
:::

## Three identities in an agent action

The user principal identifies the person or organisation whose request is being fulfilled. Its roles, tenant, relationships and attributes constrain what may be done. The agent or workload principal identifies the deployed software: its service identity, environment and approved capability ceiling. The tool credential is what the downstream API validates, with an audience, scope and lifetime. Collapsing these into one service-account name hides both responsibility and the basis for permission.

For a user-directed operation, effective authority should be constrained by the user's entitlement, the agent's ceiling and the task's scope, with downstream enforcement as an additional boundary. This is an intersection, not a union. The employee's right to inspect an order does not automatically give ShopAssist permission to move money. Conversely, an agent approved to create refunds cannot create one for a user who lacks access to that order. Policy must consider the specific operation and resource.

Background work needs a different explicit principal model. An overnight reconciliation job may act as an approved workload without an end user. Do not invent a user identity to make an intersection diagram appear universal. Define the job's purpose, resource scope and accountable owner, then authorise its workload accordingly. Its audit should say that it acted as itself under a reviewed service policy rather than misleadingly suggesting a human requested every operation.

## OAuth, OIDC and workload identity

OpenID Connect builds authentication information on top of OAuth and lets an application obtain verified identity claims through an approved login flow. OAuth access tokens let resource servers enforce access granted by an authorisation server. These roles are related but not identical: proving that a user logged in does not establish that they may refund a particular payment. Application and downstream policy must still check that resource-level decision.

A service can authenticate through a client-credentials flow, but long-lived client secrets create storage and rotation responsibilities. Workload identity instead ties an identity to a running component through the platform's supported trust mechanism. Examples include cloud-managed identities, federated Kubernetes service accounts and SPIFFE identities. The exact exchange and audience rules differ by platform. The useful aim is to avoid embedding a reusable administrative secret in agent code or model context.

Validate claims at the boundary that consumes them. Verify the issuer, signature or introspection result, expected audience and lifetime using the appropriate token profile. Do not trust a decoded token merely because its fields look plausible. An ID token intended for an application login is not automatically an access token for a payments API. Keep authentication middleware and policy inputs tied to the selected identity provider's documented contracts rather than accepting arbitrary claims from a prompt.

## Delegated authorisation and scoped tokens

When ShopAssist acts for a user, the payments system should receive enough identity information to understand both the subject and the actor. OAuth 2.0 Token Exchange, RFC 8693, provides a protocol for requesting a token based on existing tokens and identity context. It supports impersonation and delegation patterns. It does not automatically guarantee a dual-identity token, narrower scopes or a five-minute lifetime. Configure and test the authorisation-server policy that provides those properties.

In a delegation profile using JWTs, the subject identifies the user and the `act` claim identifies the current actor through an object. The audience selects the target resource server, while scope and expiry constrain accepted use when the server validates them. The signature authenticates the claims; it does not independently establish the business policy for an order. The resource server still checks whether the requested action is allowed in the current resource state.

This example is a decoded claim fragment, not a token that can be sent to an API. `exp` is an absolute NumericDate; the issue time and expiry here describe a five-minute lifetime. The actor is an object rather than a bare string. A complete implementation must use its identity provider's supported token profile and validation library, and determine whether resource-bound scopes or equivalent authorisation constraints are available.

```json
{
  "iss": "https://identity.example",
  "sub": "user:priya",
  "act": {"sub": "agent:refunds"},
  "aud": "payments-api",
  "scope": "refunds:create",
  "iat": 1791540000,
  "exp": 1791540300
}
```

Prefer an audience-restricted token with minimal scope and a short lifetime suited to the operation. If resource binding is supported, constrain it to the approved payment or equivalent resource. Keep the token in the executor; the model receives the tool result, not the credential. A five-minute token is not necessarily one-use. It reduces a leak's usable time window but may still be replayed until expiry unless binding, revocation or operation-level controls prevent misuse.

## RBAC, ABAC and relationship-based policy

Role-based access control asks whether a principal belongs to a role that may perform an action. It is useful for broad permissions such as support staff being allowed to use a customer-service tool. Agent operations often require more detail: amount, environment, time, resource tenant, current status and recorded approval. Attribute-based access control evaluates those properties. Relationship-based checks can express ownership, such as whether an employee's team manages a service or a customer owns an order.

These mechanisms can work together. A support role can provide an outer permission, an ownership relationship can select accessible orders, and attributes can limit the refund amount and environment. Policy-as-code expresses the decision in versioned, tested code or a policy engine such as Cedar or OPA rather than relying on a prompt to remember all conditions. Version the policy and include its decision reason in audit. Deterministic enforcement is easier to test, but still depends on correct and trustworthy attribute data.

Do not let the model supply the facts that grant itself permission. It may suggest an amount or extract an order identifier, but the executor obtains ownership, captured total, refunded total and approval status from trusted systems. A user-written note saying “manager approved” is not an approval record. Policy errors can also arise from stale trusted data, so consequential updates need current downstream constraints rather than a decision cached indefinitely from an earlier read.

For ShopAssist, a refund rule could require an entitled support principal, matching tenant, an approved agent environment, an amount within the relevant limit and a valid independent approval when the action class requires one. It must also constrain aggregate refunds to the captured amount. Checking only the single proposed amount misses concurrent refunds or previous partial refunds. The payments system should enforce its financial constraints atomically even when the agent platform made an earlier policy decision.

## Per-tool, resource and argument permissions

Tool-level permission decides whether this principal and agent may use the operation at all. Resource-level permission decides whether it may act on this order, payment or service. Argument-level permission constrains amount, recipient, deployment version, region or other parameters. A schema-valid tool call can fail any of these levels. Hiding a tool from the model's list is useful, but the executor must still reject an unadvertised or manually named call at execution time.

Authorisation occurs again at the downstream boundary. The agent platform checks the task and approval context; the payments API validates the credential and applies its own financial and resource policy. This separation limits the impact of a bug in one layer. It also makes failures understandable: an upstream allow followed by downstream denial should be recorded, not retried with a broader token to get the operation through.

The pseudocode below shows the order of these responsibilities. `policy.require_allowed` must use trusted resource and approval state, not values asserted by the model. `broker.exchange` has a configured delegation profile. `execute_conditionally` requires downstream resource-version and operation-identity support. The interfaces are explicit so a reader can see which properties must be implemented before claiming that this flow safely executes a refund.

```python
def execute_delegated(call, context, services):
    tool = services.registry.require(call.tool_name)
    args = tool.validate_args(call.args)
    resource = services.resources.read_for(tool, args)
    approval = services.approvals.load_for(call.proposal_id)
    services.policy.require_allowed(
        user=context.user,
        workload=context.workload,
        task=context.task,
        tool=tool,
        args=args,
        resource=resource,
        approval=approval,
    )
    token = services.broker.exchange(
        context, tool.audience, tool.required_scopes,
        resource.id,
    )
    return tool.execute_conditionally(
        args, token=token,
        resource_version=resource.version,
        operation_id=call.operation_id,
    )
```

## Multi-tenant isolation

Tenant isolation must hold wherever data is copied or authority is used. Identity tokens and trusted session context establish the tenant; tools enforce resource membership; retrieval queries apply tenant and entitlement filters inside the search operation. Filtering results only after retrieval is too late if another tenant's content entered the model context or logs. Memory and state need tenant-aware keys and access checks, not merely a tenant field that an unrestricted caller can choose.

Caches are a common hidden boundary. A tool result should be keyed by tenant, relevant principal scope, arguments and resource/version context, with a freshness rule. A shared semantic answer cache can return another tenant's personalised answer even if the question looks similar. Prefix caches also need an appropriate trust-group isolation policy. Do not assume the absence of a database write means a cache is outside the security review.

Telemetry and evaluation datasets need the same attention. Traces may contain identifiers, prompts or private tool results; restrict access and prefer metadata where possible. A production sample used for evaluation should retain purpose and privacy controls instead of being exported as an unrestricted debugging fixture. Encryption can protect stored bytes, but it does not correct an application that authorises one tenant to read another tenant's decrypted record.

Test isolation adversarially. Use another tenant's order ID, change a requested tenant field, construct a retrieval query that closely matches private documents and repeat a cached request under a different principal. Assert on content delivered to the model and external recipient, not just the final answer. A model that refuses after seeing unauthorised data has not preserved isolation; the breach already occurred at context assembly.

## Credential lifetimes, rotation and audit

Short-lived credentials limit the exposure window after a leak, but they must last long enough for the allowed operation or support a controlled renewal. Do not put refresh tokens into agent memory merely to make retries convenient. Prefer workload federation and a protected broker. Where static secrets are unavoidable, store them in a secrets manager, inject them into the executor and rotate through the documented provider process. Scan logs and results for accidental exposure.

Cancellation should revoke or stop credential use where supported, but not every token is instantly revocable. Check the selected profile's behaviour instead of promising that run cancellation invalidates every issued token. Enforce local denial after cancellation and bound the downstream token lifetime. Emergency break-glass credentials need separate approval, scope, monitoring and expiry; they should not be an automatic fallback whenever a normal operation is denied.

Audit allowed and denied decisions with principal, workload, task, action, resource, policy version and reason. Record which credential profile and audience were used without recording the secret token. This lets reviewers distinguish an unauthorised request from an authorised operation that failed downstream. It also exposes permission drift after a policy or agent release. The identity record is part of evidence for an action, not sensitive text to paste into every model message.

## Build it: review the complete delegated path

For the duplicate-charge example, begin with a verified support user and the deployed refunds workload. Load the order and payment under the user's tenant, then obtain a proposal and any required approval record. Evaluate tool, resource and argument policy using current trusted facts. Only after that decision does the broker request a constrained payments token. The payments API applies its own token validation and aggregate refund constraint while deduplicating the logical operation.

If the broker cannot produce the required profile, the task does not gain a broader service credential. If the payments API denies the call, investigate the identity, policy or resource mismatch. If a response is lost, recover using the same operation ID and the downstream status contract. If no user is present, use the separately reviewed background-job policy. These explicit choices make “whose permissions?” answerable at each step rather than relying on the service's deployment identity as a blanket explanation.
