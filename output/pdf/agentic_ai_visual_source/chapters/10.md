# 10. Skills & Reusable Capability Architecture

ShopAssist handles many refund requests, but it should not rediscover the procedure from scratch each time. The work includes identifying the order, checking payments and policy, calculating eligibility, proposing review, confirming execution and explaining the result. Some parts benefit from interpretation; others must follow fixed rules. A skill packages that reusable know-how and its supporting resources so the same procedure can be tested and improved in one place.

This chapter defines skills as capability packages within the book's architecture. We will separate them from atomic tools, workflows and whole agents, then design their contracts, loading and release process. A package can be loaded as instructions or exposed as a controlled operation; those forms have different execution implications. Reuse is valuable only when the package's authority, dependencies and acceptance evidence remain explicit.

:::analogy A restaurant's recipe kit
A restaurant keeps a recipe kit containing the procedure, measured ingredients, preparation scripts, plating templates and quality checks. The menu describes each dish briefly. Once chosen, the cook opens the recipe and only the resources the step needs. Several cooks can use the same approved edition without rewriting it. Where it stops: a software skill can include probabilistic interpretation and live service calls, so one released package does not guarantee identical outcomes. Recipe reuse also does not grant permission to spend money or run arbitrary scripts.
:::

## Tool, skill, workflow, agent

A tool exposes one controlled operation, such as listing captured payments. A workflow defines a fixed sequence and its known branches. A skill packages reusable expertise, potentially including instructions, deterministic workflow code, resources and tests. An agent chooses among available capabilities to pursue a goal within its controlled loop. These are useful architectural roles rather than disjoint product categories: a skill may contain a workflow and may be exposed through a tool contract.

The distinction matters at the boundary. Loading a refund instruction package tells the agent how to use existing capabilities; it does not execute a refund automatically. Calling an executable refund skill starts a controlled subworkflow whose own authority, waiting and recovery contract must be defined. A remote agent performing a larger goal is a delegation relationship rather than just an instruction file. Chapter 15 develops that case, while Chapter 14 covers shared capability transport.

Granularity should follow one meaningful responsibility. A god skill that investigates incidents, edits code, handles invoices and writes customer messages is difficult to review and reuse. A package so small that it merely repeats one tool's name may add no value. ShopAssist's handle_refund_request is a useful middle ground because its stable procedure connects several atomic operations and gives them a tested business purpose.

## Anatomy of a skill

A package needs an identifier, exact release, owner, summary, applicability, inputs, outputs, dependencies, permissions and risk. Its instructions explain the procedure; deterministic code supplies fixed calculations or sequencing; resources provide reference material and templates; tests establish expected behavior. The summary and when-not-to-use description help selection. The full procedure should not be stuffed into the catalog entry merely because discovery is convenient.

The book's teaching package can use a manifest such as skill.json, an INSTRUCTIONS.md file, workflow code, templates, reference data and tests. That is a local convention, not a claim that every skill runtime recognizes it. Standardized folder formats, including SKILL.md conventions supported by specific ecosystems, have their own required metadata and loading rules. Map the internal contract to the actual runtime rather than assuming that renaming a file establishes interoperability.

```json
{
  "id": "commerce.handle_refund_request",
  "version": "2.3.0",
  "owner": "payments-team",
  "summary": "Assess and propose an eligible captured-payment refund",
  "when_not": ["chargeback", "account security change"],
  "inputs": ["order_id", "customer_message"],
  "outputs": ["status", "proposal_id", "refund_id", "evidence_ids"],
  "dependencies": ["get_order@2.1.0", "list_payments@4.0.2"],
  "permissions": ["orders:read", "payments:read"],
  "risk": "financial execution requires bound approval"
}
```

The example manifest is complete as data but is not a JSON Schema or a runnable loader. Its fields declare the internal package contract for discussion. A production implementation must validate input/output schemas, resolve dependencies and distinguish read permission from later financial execution permission. Keep risk and approval metadata in the host's reviewed policy; a third-party skill cannot grant itself authority by declaring that its operations are harmless.

## Composite skills and deterministic sub-workflows

Place business rules where they can be tested independently of generation. ShopAssist can use a model to interpret a customer's explanation and produce a candidate reason. The service then confirms the relevant facts, determines eligibility and calculates remaining refundable amount. The classifier's result must not bypass factual preconditions. If it labels a pending authorization a duplicate capture, payment records should still prevent an invalid financial proposal.

A complete skill separates stages: validate the task, retrieve owned records, interpret relevant language, apply deterministic rules, create a bound proposal, wait for review, execute through the controlled tool and verify the outcome. The explanatory text can be generated from the retained result. If the task stops while waiting or its outcome becomes unknown, the skill returns that status rather than a misleading successful output with a missing refund_id.

Avoid repeating approvals inside both an outer agent and an inner workflow without a clear owner. The outer runtime may display a proposal while the executable skill retains its exact identity and waits; or the host may own the approval contract and pass an authenticated bound decision. Whichever design is chosen, approval must reach the actual effect boundary. A skill that says requires_review but calls the payment function directly is only documenting a wish.

AegisOps skills follow the same structure. diagnose_http_latency can combine metrics, deployment history and runbook evidence, while propose_rollback can compute a reviewed change proposal and wait. Reusable skills make procedures consistent, but a release does not make every model classification or live observation identical. Evaluate the variable parts separately and preserve deterministic invariant checks around them.

## Progressive disclosure

A catalog should let the agent choose without reading every procedure in full. Expose short relevant summaries first. After selection, load the reviewed instructions and contract for that skill. Open a template or reference file only when its step needs it. This is progressive disclosure: reducing unnecessary context while preserving access to detail. The catalog itself should be filtered by principal, tenant features and task domain before the model sees it.

Loading needs an execution boundary too. A load_skill operation verifies the approved source, exact version, permissions and resource index. A request for an unoffered or unauthorized skill is denied, even if the model names it. Resource paths must remain inside the approved package or permitted storage roots. Do not let instructions redirect the loader to arbitrary code or a remote file merely because the text resembles a dependency declaration.

Dynamic loading has tradeoffs. It adds a selection/loading turn, and a poor summary can hide the correct package. For a small fixed domain, preselecting one known skill may be simpler than model-driven search. For a large catalog, retrieval or a bounded router can find relevant candidates. Compare token savings, selection accuracy and latency on representative tasks, including ambiguous requests. More layers are useful when they reduce actual confusion rather than merely creating a sophisticated menu.

## Skill packages with resources, scripts and templates

Templates make recurring outputs consistent, but dynamic values still need validation and appropriate data placement. Reference resources such as reason codes or escalation matrices need versions and authority. Examples demonstrate intended behavior and must stay aligned with tools and policies. Scripts perform deterministic work under a capability contract; they can have side effects even when their text is never loaded into the model's context.

Do not claim scripts cost exactly zero tokens. A script's full contents may not be read by the model, yet its description, path, invocation and output can consume context. Likewise tests may run outside inference without becoming a prompt section. Distinguish execution cost from information cost. A schematic package drawing should show these responsibilities without pretending that a 60-token metadata plate is larger than a 1400-token instruction plate in a proportional chart.

Self-contained packaging helps reproducibility but does not eliminate external dependencies. A skill that uses a payment API or current policy register still needs live authoritative data. Freeze templates and helper code with the release, declare the external contracts and retain resolved dependency versions. A package with cached stale policy text cannot honestly claim that every invocation follows the current business rules simply because the folder version stayed unchanged.

## Discovery, versioning, trust and access control

Run the catalog as a product with search, owners, reviewed sources, release history and retirement plans. Dependency ranges can express compatibility during build or deployment resolution, but each released agent/skill manifest should record exact versions and content hashes. A mutable range such as ^2 does not by itself explain which implementation a past run used. Keep the resolved assembly available for audit and supported continuation.

Trust includes more than signatures. A signature can establish who supplied a package, not whether its instructions or scripts are appropriate. Review third-party procedures like other third-party code, including resource access, network destinations and declared risk. Filter discovery by allowed scope and enforce that scope again during loading and execution. A package owner should have a support path and a clear responsibility for failures discovered after release.

The permission model should prevent privilege amplification. A skill requiring orders:read cannot acquire refunds:execute simply because it contains a script with that name. The host supplies authenticated capabilities under policy. If an executable composite needs stronger authority, its call contract and review state must say so explicitly. Narrow capability exposure improves selection, while the executor/service boundary remains the enforceable gate.

## Testing, lifecycle and deprecation

Use contract tests for schemas, dependency resolution and declared permissions. Use unit tests for deterministic calculations, reference lookup and template rendering. Use behavioral evaluations for interpretation, tool selection and explanation against representative cases. Keep the scoring tied to accepted outcomes and trajectories: an agent that writes an attractive reply after an unverified refund is not a successful refund skill. Failed/ambiguous cases are particularly valuable release tests.

A useful lifecycle is draft, opt-in beta, stable, deprecated and removed. A new release passes the relevant checks and records changes in behavior. Deprecation announces the replacement and allows a defined migration window for pinned agents and pending tasks. Monitor residual calls before removal. A running approved proposal should not silently bind to a new major implementation whose effect differs from the one reviewed.

Allow agents to propose improvements with evidence, not silently rewrite their own live procedures. A proposed shorter search step may save calls; a removed ownership check may weaken protection. Both deserve review appropriate to their consequence. Use evaluated runs to explain the improvement and the regression risks, then release an immutable approved version. This preserves learning while keeping authority over procedure changes accountable.

## Exposing skills through standard capability layers

A skill can be published as an MCP tool when other hosts need its callable contract. Resources can expose approved runbooks and templates. The host still controls which capabilities reach the model and the server still checks resource authority. MCP provides connection and discovery semantics; it does not automatically supply the skill's business rules, safe retries or approval. Chapter 14 shows how to place that transport behind the same tool registry.

If another team owns a goal-directed remote agent rather than a procedure, use a delegation contract that covers task identity, progress, artifacts, cancellation and uncertainty. That is the concern of Chapter 15's A2A discussion. Some runtimes can load standardized skill folders directly; verify the supported metadata and dependency rules for that runtime. Portability means a tested mapping across compatible contracts, not that one folder layout runs unchanged in every platform.

## Failure modes

Repeated improvised procedures create inconsistent behavior and duplicated maintenance. Monolithic skills obscure ownership. Unfiltered loading creates token bloat or privilege confusion. Unpinned releases change behavior without a trace. Unreviewed scripts introduce side effects beyond the skill's declared purpose. Self-modification weakens controls when hostile context influences a procedure update. Address these problems through package boundaries, explicit contracts, evaluated releases and execution policy rather than merely adding a richer manifest.

## Interview drills

Explain a tool as one operation and a skill as reusable expertise that may compose operations. Show where deterministic eligibility lives and how uncertain interpretation is contained. Describe progressive disclosure through discovery, instruction loading and resource access, naming the policy gate at each step. Explain exact resolved versions and retirement of a pinned skill. A good answer can trace one invocation and one failed dependency without relying on platform vocabulary.

## Key takeaways

Skills let expertise accumulate in reviewed packages rather than scattered prompts. They combine a useful contract, procedure, resources and tests, with deterministic rules where precision matters. Load only relevant information and execute helpers under explicit authority. Keep the approved assembly traceable and the variable outcomes honestly evaluated. The recipe kit is valuable because its procedure is reusable, not because its existence guarantees every meal tastes identical.
