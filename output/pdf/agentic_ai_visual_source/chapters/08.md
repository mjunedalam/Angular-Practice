# 8. Context Engineering

ShopAssist can have the right model and still reach a poor decision because the request contains yesterday's order status, an irrelevant policy or too much repetitive history. The model operates on the view it receives for this call. Context engineering builds that view deliberately: selecting permitted records, arranging them usefully, fitting them to a budget and retaining their provenance. It is information preparation with a clear consumer, not a synonym for making a prompt longer.

The difficult tradeoff is completeness versus attention, cost and privacy. Sending everything is often impossible and may be harmful. Sending too little invites unsupported inference. We will follow the information needed for a refund proposal, decide what stays exact, what can be summarized and what must be refreshed. The controller's state remains authoritative while each model request becomes a bounded, inspectable view of it.

:::analogy Packing a suitcase for a specific trip
A traveler with a weight limit packs essential documents and medicine first, then clothing suited to the destination, then optional items if there is room. A packing list records what went in; prohibited items never enter the bag. Repacking from a pile of old souvenirs without checking the trip would produce a heavy, unhelpful suitcase. Where it stops: token limits are not a simple weight limit. Message overhead, output and reasoning allowances vary by provider, and a passage's usefulness depends on meaning, not only its size. The packing list also cannot prove that the traveler interprets an item correctly.
:::

## Context assembly and source prioritisation

List the sources before deciding their budgets. A model request may include reviewed instructions, output contract, allowed tool schemas, current task, state snapshot, recent conversation, tool observations, retrieved evidence and relevant memory. Each has a distinct owner and trust classification. The current user question is not an optional historical message; a financial precondition is not merely one relevant passage among many. Prioritization should reflect the decision's required information.

Start with non-negotiable instructions and capability/output contracts, then the goal and exact state needed for the next action. Include the current request and recent accepted observations, followed by relevant retrieved evidence and memory. Older conversation can often become a summary or retrievable references. This is a useful default, not an immutable universal ordering. A long-document question may need different presentation while still retaining required policy and tool-result structure.

For ShopAssist, the state snapshot should explicitly name the order, the two capture identifiers, observed amounts, source times, plan position and pending review. That saves the model from reconstructing transaction facts from a dozen conversational turns. It must also distinguish a proposed refund from a completed one. State fields supplied by validated runtime logic are more reliable for execution than a generated recap saying "refund handled," which can hide whether any money moved.

## Token budgeting

Budget the complete serialized request and reserve the capacity needed for generated output and provider-specific reasoning requirements. A visible text count misses message envelopes, tool definitions, structured-output schemas and sometimes other content types. Use the appropriate tokenizer or a validated counting approximation with conservative margin. If required instructions and current facts cannot fit, fail explicitly or choose a supported different configuration rather than silently cutting the end of the request.

Allocate flexible sections so overflow has a defined response. Older history can shrink to a source-backed summary; evidence can drop lower-ranked passages; a large tool result can project required fields or return pagination. Required exact facts should not be compressed until their meaning changes. Validate the shrink operation's result and the final provider serialization. A function named keep_top is a strategy, not proof that the returned content fits its allowance.

It is an illustration of an allocation, not a recommendation for every model. A real application should measure fixed instruction/tool overhead and tune evidence/history allowances against accepted task outcomes. Small segment labels belong in the keyed legend, not crowded inside the bar.

## Pruning, summarisation and compression

Pruning removes material no longer needed for the decision. A sliding window retains recent turns, while older detail remains retrievable from the record. Before dropping history, extract commitments and critical facts into structured state. A customer constraint, an accepted action and an unresolved payment outcome must not vanish because they fell outside the last six messages. Define what is pinned according to task semantics, not only what the summarizing model marked interesting.

Summaries reduce narrative while losing exact wording and sometimes distinctions. A repeated summary of a summary can turn "refund proposed" into "refund issued." Regenerate from original records when fidelity matters, and retain source identifiers for statements the next step may act on. Treat summaries as views with their own creation/version metadata. They are useful for navigation and explanation; they are not a substitute for the authoritative effect ledger.

Observation compaction projects old tool results into small records: status, relevant values, source time and a pointer to the full retained result. Retrieval over history can recover older discussion when a new question needs it. These mechanisms can work together, but provider conversation constraints must remain valid. Keep assistant tool-call messages paired with corresponding tool results or use a supported transformed context format. Dropping one side of a required protocol pair can make the next request invalid.

A refund run illustrates the choice. Keep payment identifiers and exact remaining balance in state; retain the newest status response; replace an old ten-page policy result with the relevant current passage and its version locator; summarize earlier small talk. The resulting context is shorter because irrelevant narrative leaves, not because meaningful transaction fields are guessed. Compare accepted outcomes before and after compaction, including cases where an early customer constraint changes eligibility.

## Context caching and reusable prefixes

Provider caching can reuse stable request prefixes and reduce repeated processing cost or latency under the provider's contract. Reviewed instruction packs, stable tool ordering and long-lived examples are good candidates. Timestamps and random request identifiers near the beginning can defeat prefix reuse. Put volatile state and the latest request later where the message contract and attention needs allow. Measure cache behavior instead of assuming every stable byte produces a hit.

Caching semantics vary across providers and model generations. Retention, routing, minimum cacheable lengths and supported controls may differ. A cached prefix still contributes information to the call and may have different billing rules; it is not free infinite context. Changes to instructions or offered tools can legitimately invalidate reuse. Preserve immutable versions and ordered schemas, then use observed cache-hit and task-success metrics to judge whether the composition serves both economics and quality.

Application caches need their own freshness rules. A repeated order lookup can be reused within a run when the fact's validity allows it. Before a refund, a volatile balance may need another authoritative read. Retrieval results must remain entitled and version-aware; a cached hit from an earlier user or tenant cannot bypass policy. Embeddings of unchanged documents are another useful cache, but deletion and access revocation still need propagation through derived copies.

## Stale, contradictory and poisoned context

Stale information was true at one time but is no longer adequate for the decision. Retain observed_at and an appropriate maximum age, then refresh consequential facts when required. Fresh retrieval time alone is not proof that the underlying document is current: a server can return a freshly fetched superseded policy. Distinguish source effective date, record version and observation time. ShopAssist's payment state and returns policy have different freshness needs.

Contradictory information requires source precedence and an explicit conflict record. A customer email may describe two charges while the current payment service shows one capture and one pending authorization. Explain the distinction and inspect the relevant evidence rather than letting the model silently select whichever supports a refund. A curated policy register can outrank a stale FAQ, but authority depends on the source's actual governance. A label saying trusted is not a reason by itself.

Poisoned context contains planted instructions or misleading facts. Provenance and delimiter structure help interpretation, but the action boundary protects consequences. Filter unauthorized data, keep external content separate from reviewed instructions and gate memory writes. A forged policy passage should not grant permission even when retrieved from an internal index. Its presence may require corpus cleanup or investigation in addition to denying the proposed operation.

## Provenance and explainability

Give every selected item an identifier and a source locator. A context manifest records which items, versions, token contributions and trust labels were included in a particular model call. It should describe actual selected content, not every candidate considered. If ranking changes the order and budgeting keeps only E2, the manifest must name E2. Pair item metadata with its rendered representation through selection so those two views cannot drift.

Provenance supports citations, debugging and deletion. An investigator can see which policy version informed an invalid proposal. A citation can resolve to a retained section rather than a mutable homepage. A lineage record can identify derived summaries or caches after a deletion request. This makes the manifest a useful privacy-conscious alternative to unrestricted raw-prompt logging, although locators and identifiers themselves can be sensitive and need appropriate access controls.

## Context policies for multi-tenant and sensitive data

Apply tenant and entitlement checks before content enters the view, even when the agent's service account can read more. Define which data classes may reach which provider and region. Minimize fields to the purpose: a payment summary may need status and last-four display data, not full card details. Secrets and credentials belong in execution infrastructure rather than prompts or memory. Classification should follow the application's actual policy, not an invented universal rule that all sensitive data has the same treatment.

Central filtering must cover every source. Evidence and memory are obvious candidates, but state summaries, recent messages, cached tool outputs and rendered templates can also contain private data. Either validate them centrally or record a clear upstream validation contract that the builder enforces. A pipeline that filters only retrieved documents can still leak a foreign order through an earlier observation. Repeat critical resource checks at action time because a permitted view is not authorization for every possible operation.

## Build it: a token-budgeted, attributed context builder

The following complete function illustrates paired selection for already policy-approved, rendered items. Each item supplies an exact identifier, text and source. Required instructions and message-envelope overhead are supplied separately by the caller, which must include them in fixed_tokens. The function does not claim to perform tenant or privacy checks; its input contract states that those occurred. The final provider request still needs a serialization-aware size check.

```python
def select_context(items, count, window, output, fixed_tokens):
    remaining = window - output - fixed_tokens
    if remaining < 0:
        raise ValueError("required context exceeds capacity")
    selected = []
    for item in sorted(items, key=lambda x: x["priority"]):
        size = count(item["text"])
        if size > remaining:
            if item.get("required"):
                raise ValueError("required item does not fit")
            continue
        selected.append((item, size))
        remaining -= size
    text = [item["text"] for item, _ in selected]
    manifest = [
        {"id": item["id"], "source": item["source"],
         "tokens": size}
        for item, size in selected
    ]
    return text, manifest
```

For a larger builder, make sections explicit and attach their own shrink policies. Preserve identity when projecting or expanding evidence, and record whether a selected representation is a full source, a bounded excerpt or a generated summary. Escape identifiers and source attributes if constructing delimiter tags, not only passage text. Test a reordered candidate list with only one item fitting; that catches the subtle provenance bug where rendered passages are paired with their pre-ranking metadata.

## Failure modes

Context stuffing produces expensive, distracting requests. Unbounded history hides current facts under repeated turns. Silent truncation removes required data without an explicit failure. Volatile prefixes lose cache benefit. Stale facts drive invalid actions. Missing provenance makes the cause difficult to reconstruct. Incomplete policy coverage leaks through the unfiltered source. These are builder failures with distinct repairs, not proof that a bigger context window will solve every problem.

## Interview drills

Explain context as a bounded per-call view and identify its authoritative source records. Describe budgeting in terms of serialized input, output and supported reasoning capacity. For long runs, distinguish structured exact facts, source-backed summaries and retrieval over retained history. For a stale refund status, describe the freshness contract and action-time refresh. For privacy, enumerate every context source and the central or verified-upstream gate covering it.

## Key takeaways

A useful context contains the right permitted information for the current decision, not the largest available archive. Budget deliberately, preserve exact operational facts and make compression accountable to source records. Stable prefixes can improve economics while freshness and authority determine whether facts may be used. Pair selected text with its provenance throughout the builder, and keep the final view distinct from execution state.
