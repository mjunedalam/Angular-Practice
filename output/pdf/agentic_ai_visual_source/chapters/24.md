# 24. Agent Testing Strategy

A rejected approval should produce zero refunds. That rule does not become probabilistic because a language model selected the refund tool. The proposal may vary, but the executor's decision check, resource constraint and effect ledger are ordinary software. Testing becomes clearer when the model's changing behaviour is isolated from the deterministic machinery around it. A team can then prove important runtime properties with fakes while evaluating live-model quality separately.

This chapter builds that testing structure. You will test validators and policies, verify tool/provider contracts, drive every control-flow branch, replay recorded trajectories and inject faults. Security assertions inspect actual data and effects rather than relying on reassuring final text. Chapter 25 then adds statistical evaluation of live-model behaviour. The two disciplines cooperate: a correct harness can host a poor model policy, and a promising model cannot repair a broken approval check.

:::analogy A flight simulator and its checklist
A simulator lets a crew practise a known engine failure, delayed clearance or unexpected instrument reading repeatedly. Engineers can inspect whether the required procedures were followed without waiting for the failure on a real flight. Fake models and services give agent tests that control. Where it stops: a simulator demonstrates behaviour under its modelled conditions, not every real-world situation. Recorded responses test the harness; live-model decisions and production environments still need evaluation and monitoring.
:::

## The agent test pyramid

Use many fast checks for local deterministic logic and fewer broader checks for integrated behaviour. Unit tests verify one rule or transformation. Contract tests verify that interfaces agree. Path tests drive a state machine with scripted decisions. Golden/replay tests check reviewed trajectories. Fault and adversarial suites test recovery and protected boundaries. Live-model evaluations measure behavioural quality with repeated trials and uncertainty. The pyramid describes emphasis and cost, not a rule that security always belongs near the top.

Separate what the test controls from what it observes. A scripted model makes a chosen tool call; the real policy and fake payment service decide whether an effect occurs. A test that mocks out the policy and then asserts that policy was called proves little about permission correctness. Keep the important rule real while replacing the expensive or dangerous dependency. An end-to-end fake environment should expose a ledger so the test can inspect actual effects.

Not every test is fully deterministic merely because it avoids a real model. Clock reads, random fault injection, concurrent completion order and mutable fixtures can vary. Inject time and random sources or record their decisions when they affect control flow. Use fixed seeds for reproducible CI probes, then broader varied staging runs to search for cases the fixed probes miss. Reproducibility and coverage are related goals, not substitutes for each other.

## Unit tests for pure logic and validators

Start with rules whose expected result can be stated precisely. Validate argument ranges and identifiers, compute canonical operation keys, check risk requirements, merge evidence, account for budgets and redact known sensitive fields. Include boundary cases and invalid inputs. A refund amount of zero, a different tenant ID or changed recipient should have an explicit expected outcome rather than depending on how persuasively the model explains it.

Test the permission rule with trusted input fixtures, not only through a model conversation. An approved action needs the right outcome, proposal/run binding, entitled distinct approvers and fresh conditions. Vary one condition at a time and inspect the effect counter. Also test combinations that can expose gaps, such as matching stored digests with changed actual arguments. Chapter 18's helper should be exercised through the same canonicalisation and decision policy used by execution.

Reducers deserve conflict tests as well as happy-path deduplication. Two identical evidence IDs with identical content can merge; the same ID with different content should follow the declared conflict rule. Budget tests should include concurrent reservations and the allowance reserved for safe exit. A test that repeats the implementation expression is weaker than one that checks the externally meaningful invariant, such as “spent plus reserved cannot exceed the hard allowance.”

## Tool contract and provider adapter tests

The tool's model-facing schema and runtime argument model must agree. Verify required fields, descriptions, side-effect class, content limits and error results. Check that invalid arguments never reach the downstream executor. A mutating tool needs its approval and operation identity contract, while a read tool still needs tenant, data and rate-limit policy. Contract tests should reject stale or changed tool descriptions when the integration requires a pinned contract.

Provider adapters translate vendor-specific messages, tool calls, usage and stop reasons into internal types. Recorded response fixtures can test normal completion, multiple calls, truncation, refusal and error classification without paying for a live request. A malformed or truncated structured output must not become a partial mutation request. Version fixtures with the provider contract and test new SDK/API versions before switching production traffic. Compatibility at the HTTP path does not guarantee identical feature semantics.

For MCP and A2A integrations, run staging contract tests against the pinned server configuration. Test discovered tools, content modes and expected lifecycle states, including questions and cancellation. A2A duplicate-submission safety needs a specific remote deduplication contract; a stable message ID alone is not the test's proof. Check what happens when an acknowledged remote task becomes temporarily unreachable and whether resumption finds the same task rather than silently creating another.

## State-machine and graph path tests

A scripted fake model returns an ordered sequence of decisions. That lets a test enter the exact branch under review without hoping a live model chooses it. Enumerate every conditional route, each loop at its limit and every interrupt outcome. For an approval wait, cover approval, rejection, expiry, modification, stale resource state and crash/resume. Both evaluator and verification retries must consume the appropriate guard, as Chapter 16 explains.

The test should observe the real invariant at the protected boundary. After rejection, the payment effect count stays zero even if the scripted model insists on refunding. After a valid approved operation and lost response, recovery should reconcile the same logical operation under the fake downstream contract. Changing the proposal cannot reuse an old approval. These tests expose execution defects without needing the model to behave maliciously by chance.

```python
class ScriptedModel:
    def __init__(self, decisions):
        self._decisions = iter(decisions)

    def decide(self, context, tools):
        decision = next(self._decisions)
        if callable(decision):
            return decision(context, tools)
        return decision

def assert_rejection_has_no_effect(harness, payments):
    waiting = harness.start("duplicate charge")
    assert waiting.status == "waiting"
    finished = harness.resume(
        waiting.run_id, decision_outcome="rejected")
    assert payments.effects == []
    assert finished.status in {"completed", "escalated"}
```

This is a test sketch with injected harness and payment fixtures. The fixtures must use the real decision validator and a fake effect store, and the scripted decisions must attempt the protected operation. A test that never reaches the action path cannot prove rejection enforcement. Keep the reason recorded in audit as well as the effect count, because a safe stop should also be explainable to the user and operator.

## Simulation and property-based fake-model tests

A simulated environment combines fake orders, payments, knowledge sources and users with configurable outcomes. It can model a timeout before an effect, a timeout after commit, a changing order version or a unavailable approval service. Make its assumptions explicit. A fake payment API that deduplicates every request can demonstrate the harness's use of a key, but it cannot prove that an unrelated real API supports the same contract.

Property-based testing generates many input combinations or trajectories and checks invariants. Hypothesis can produce sequences of proposed tool calls, amounts and failure positions that the test author did not enumerate. Construct mutable fake systems inside each generated example or use a documented reset mechanism. A function-scoped test fixture is not necessarily reset for every Hypothesis example, so shared effect state can create false failures or conceal missing initialisation.

Useful invariants include no unauthorised effects, bounded calls and preserved operation identity across recovery. “At most one refund” needs the right scope: a run may legitimately refund several distinct payments, while the same logical approved refund must not occur twice. State the business-operation identity in the assertion rather than banning every second refund globally. The generator should include duplicate triggers, changed arguments and restarts to exercise the distinctions.

## Golden trajectory tests

A golden trajectory is a reviewed reference for a representative task. It can specify required reads before a proposal, critical argument constraints, forbidden effects, valid approval before execution and a step budget. Do not require identical wording or one exact tool sequence when several legitimate routes exist. Partial-order constraints and outcome invariants preserve flexibility while catching a premature mutation or missing evidence check.

Keep proposed calls and executed effects distinct in the event schema. A test for refund-proposed should not require that a financial effect already occurred. An approval-requested event does not establish an approved decision. For every executed protected action, verify the authenticated decision outcome, proposal digest and timing rather than merely finding any approval request earlier in the run. Also enforce the budget included in the golden specification; an unused max_steps field gives false confidence.

```python
def check_protected_effects(events, decisions):
    problems = []
    for event in events:
        if event.kind != "effect_executed":
            continue
        if not event.approval_required:
            continue
        decision = decisions.get(event.proposal_id)
        if decision is None or decision.outcome != "approved":
            problems.append("missing approved decision")
            continue
        if decision.digest != event.proposal_digest:
            problems.append("approval binding mismatch")
        if event.executed_at >= decision.expires_at:
            problems.append("expired approval used")
    return problems
```

This checker assumes decisions were already authenticated and entitlement-validated by the fixture's real approval service. Tests should cover that validator separately and together with execution. Add required read ordering, argument and budget checks for the chosen task; no single generic function captures every business rule. With recorded model decisions the suite is deterministic. With a live model, the same structural checks become behavioural evaluation measures rather than a guarantee of repeated identical trajectories.

## Fault injection and chaos-style tests

Inject faults where the recovery contract is vulnerable, not only at the beginning of a call. A timeout after payment commit tests whether the same operation is recovered. A worker crash between effect and checkpoint tests uncertain-result handling. A lost lease followed by a stalled worker resuming tests fencing. An approval service outage tests whether the run waits or exits without bypassing its gate. A vector-index failure tests the honesty of the degraded answer.

Use fixed fault schedules or seeds in CI so a failure can be reproduced. Periodic larger staging tests can vary schedules and concurrency to find interactions not covered by the fixed suite. Chaos-style testing should have bounded blast radius and clear stop conditions; it is not permission to disrupt production indiscriminately. Record which invariant failed and the relevant configuration so the fault becomes a regression case rather than a one-time surprise.

## Adversarial security and prompt-injection suites

Translate the threat model from Chapter 19 into executable cases. Prompt injection attempts should be tested through both controlled model requests and realistically poisoned content. Put direct and indirect injections in messages, documents, logs, tool descriptions and memory records. Probe exfiltration through external sends, image URLs and search arguments. Try another tenant's IDs, path escapes, redirects and expensive trajectories. Keep the attack input and expected control together so a failed case points to an actual boundary rather than merely labelling the model unsafe.

Measure model attempts and successful effects separately. The model can attempt a forbidden action while the executor correctly rejects it. Track that vulnerability and improve it, but the hard system assertion concerns whether the effect happened or unauthorised data crossed the boundary. Fake models can deterministically test the enforcement layer; live adversarial evaluations measure how often realistic content elicits an unsafe proposal. Both are necessary, and neither alone covers the complete system.

## Deterministic replay and regression baselines

Replay uses recorded inputs and responses to reproduce a run's controlled decisions. Record the configuration release, context manifest, model responses, tool outcomes, approvals and control-relevant time/randomness within the permitted retention policy. Protect sensitive full context and retain versioned source references where possible. A manifest without accessible source versions may explain what was included but cannot fully reconstruct the original content.

Replay should stub external effects rather than issue a real refund or deployment again. Compare request hashes and fail clearly if context diverges from the recording. That divergence can be a useful regression signal after a context-builder change. Replaying with a new prompt or model creates new decisions and therefore becomes a counterfactual evaluation, not deterministic replay. Preserve this distinction so a test does not claim exact reproduction while silently invoking live services.

Every production defect should become a targeted regression case when privacy and retention permit. A small recorded path can protect the specific failure; representative evaluation cases then check whether the fix improves behaviour more broadly. Do not preserve an entire uncontrolled production transcript merely because it might someday be useful. Extract the necessary conditions and outcome contract, document what the reduced fixture retains and keep access restricted.

## Wiring the layers into CI

Run fast unit, contract and controlled-path suites on each change. Add replay, fault and adversarial checks appropriate to the changed boundary. Live-model evaluations gate behavioural changes using the dataset and statistical policy described in Chapter 25. Prompts, tools, model routes and risk policies can change behaviour without ordinary source-code changes, so they belong in the release pipeline too. A green deterministic suite proves only the assertions it ran, not that every live answer will be good.
