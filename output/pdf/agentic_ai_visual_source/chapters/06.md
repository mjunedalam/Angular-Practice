# 6. Tool Calling & Action Architecture

A model's helpful explanation becomes consequential when it reaches a capability that reads a private order, sends a message or moves money. The tool boundary is where the application decides what work is legitimate. Good names and schemas make the model easier to guide, while execution controls make the application easier to trust. Both faces matter. A clear description without authorization is unsafe; a secure operation with an ambiguous contract is difficult to use correctly.

We will design ShopAssist's payment and refund capabilities from the model-facing request through validation, approval, execution and recovery. The same structure applies to AegisOps operations such as reading metrics or proposing a rollback. The main question is not whether the model knows the right operation, but whether the runtime can identify its exact intended effect and enforce its contract before that effect occurs.

:::analogy The service counter and the back office
At a government service office, a sign tells applicants which counter handles renewals and a form specifies the required fields. Behind the counter, staff check identity, eligibility and records before issuing a document. An application receipt identifies the work so a caller can ask about its status without submitting a second application. Where it stops: a receipt alone cannot force another office to avoid duplicate work. Software retries and uncertain external effects need atomic records or an explicit downstream idempotency/reconciliation contract.
:::

## Anatomy of a tool

The model-facing contract contains a distinct name, a useful description and an argument schema. It explains what the operation does, when it is applicable, what it returns and what prerequisites matter. The runtime-facing implementation supplies validation, authenticated identity, resource authorization, risk handling, deadlines, effect identity and audit. Keep these two faces connected through a versioned tool definition, but do not expose credentials or execution authority as fields the model can choose.

For issue_refund, the request identifies the order and captured payment, the currency, an exact amount and an allowed reason. The wrapper fetches current payment state, checks ownership and remaining refundable balance, obtains any required approval and records the intended effect. The payment service performs the transaction under its own invariant checks. The returned refund identifier and status become evidence. The model can explain that evidence; it cannot manufacture it by returning a success string.

## Writing contracts models use correctly

Use names that distinguish purpose, such as get_order, list_payments and issue_refund. Two names for almost the same lookup create unnecessary classification ambiguity. Descriptions should state when to use the operation and when another capability is appropriate. Include meaningful prerequisites, but enforce them independently. "Use after confirming captured payment ownership" guides selection; the service must still check ownership if the model skips that step.

Schemas should make ordinary mistakes difficult. Use enums for closed reasons, patterns for identifiers, positive numeric bounds and bounded lists/text. Give amounts explicit units and currency. Integer minor units work well when the currency's exponent is defined by the application; Decimal with deliberate quantization is another valid contract. Binary floating-point is a poor default for exact financial invariants. A maximum schema amount is not the same as the customer's current refundable balance, which requires a domain check.

```python
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field

class RefundArgs(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)
    order_id: str = Field(pattern=r"^ORD-\d{6}$")
    payment_id: str = Field(pattern=r"^PAY-[A-Z0-9]{10}$")
    currency: Literal["INR"]
    amount_minor: int = Field(gt=0, le=5_000_000)
    reason: Literal["duplicate_charge", "damaged"]
    evidence_ids: list[str] = Field(min_length=1, max_length=8)
```

The strict schema above prevents unwanted extra fields and coercion in this local validator. It deliberately supports one currency for the teaching example. A production service should define supported currencies and their units explicitly rather than treating every currency as having two decimals. Validate evidence identifiers against the run's retained sources; a correctly shaped string is not proof that a policy passage or payment exists.

A contract also specifies outputs, errors, side effects and limits. Return identifiers and facts the next step needs, not an unbounded backend response. Errors should distinguish missing resource, forbidden resource, already-completed effect, invalid precondition, dependency failure and unknown outcome. A generic failed message forces the model to guess whether another call is useful. A precise result helps it recover without weakening the executor's policy.

## Tool choice: automatic, constrained, required and policy-filtered

Providers may let a request choose automatically, require some tool, force one named tool or prohibit tools for a final drafting phase. These settings guide generation and differ by provider. They do not authorize execution. A forced call can still have invalid arguments, and an automatically chosen operation can still be forbidden. The executor should validate every request using the same boundary regardless of how the model was instructed to produce it.

Filter the offered capability list for the task, principal and tenant configuration. ShopAssist answering product questions does not need refund execution. Reducing the list lowers ambiguity and context cost. However, a model can still name an unoffered capability, and a caller can submit a request outside the model. The registry/executor must reject unknown or unauthorized names. Capability omission is a useful least-privilege presentation choice; execution checks provide the enforceable protection.

## Serial and parallel calls

Several independent read operations can run concurrently, such as looking up an owned order and searching an authorized policy corpus. Bound concurrency and give each call a deadline. Independence must be established, not inferred solely from read classification. A read can depend on an earlier write, and two reads can compete for a shared quota or reveal sensitive data. Preserve the relationship between each request identifier and its success or error result.

Writes need ordering based on effect dependencies and conflict scope. This book's small harness serializes mutations deliberately. A production application may allow proven-independent writes under appropriate locking and service contracts, but parallel execution should not be automatic merely because the model returned a batch. Do not reorder every read before every write: that can turn "update then inspect" into a stale observation. Plan the batch from explicit dependencies and policy.

Partial failure is part of the batch result. A failed lookup should not erase another successful observation or crash the run without recording either. Use typed envelopes for every call, and document whether later dependent operations are skipped. Catch expected dependency errors at the invocation boundary. Avoid hiding programming defects inside a success-looking data field. The model needs a truthful view of what actually happened and which operations were never attempted.

## Read-only versus mutating tools

Classify consequences more precisely than read/write alone. Reads require resource entitlement and egress controls. Internal writes may be reversible but still affect records other people rely on. External messages disclose information and may make business promises. Financial or destructive operations change money, availability or recoverability. This classification informs default risk routing, credentials, approval and recovery, while the exact resource and arguments determine the final decision.

A read-only tool is not universally harmless to repeat. It can incur charges, exhaust rate limits, access secrets or transmit query data to a remote service. Similarly, a reversible write can still be harmful before reversal. Define the operation's actual effect contract, including observability and who can perform compensation. The classification is a starting policy input, not a complete security proof.

## Idempotency, retries and compensation

An operation is idempotent when repeated application has the intended single effective result under its defined semantics. A downstream API may implement this using a retained idempotency key. If a refund succeeds but its response is lost, retrying the same accepted intent with the same key can retrieve the original outcome. The runtime must understand key retention, parameter matching and conflict behavior. An arbitrary local hash has no protective effect unless the execution path uses it consistently.

Derive the key from stable business effect identity. Payment, currency, amount and tenant/resource scope belong in that identity; the model's reason wording and narrative evidence do not. Persist the accepted intent and key before execution and reuse them on resume. A key scoped only to one run step may prevent transport duplicates while allowing a later step to propose the same business refund. The domain service still needs a rule against over-refunding or duplicate business effects across runs.

```python
import hashlib
import json

def refund_effect_key(tenant, payment, currency, amount_minor):
    identity = {
        "tenant": tenant, "payment": payment,
        "currency": currency, "amount_minor": amount_minor,
    }
    encoded = json.dumps(
        identity, sort_keys=True, separators=(",", ":")
    ).encode()
    return hashlib.sha256(encoded).hexdigest()
```

This function illustrates canonical effect identity, not a complete payment API's key policy. Some domains permit distinct legitimate transactions with the same amount and resource; they need an authenticated business-operation identifier as well. Decide whether a key identifies one accepted proposal or a domain-unique effect and document that choice. The invariant cannot be inferred from hash length or from naming the function idempotency_key.

When a service lacks idempotency support, checking whether an effect exists is useful reconciliation but may not be enough. Two workers can both read absence, and a previous timed-out write may not yet be visible. Use atomic uniqueness/transaction guarantees or an enforced lock/fencing mechanism where appropriate. If the previous outcome cannot be established, record outcome_unknown and escalate or reconcile. Do not automatically submit a second non-idempotent write to resolve uncertainty.

Compensation is a new operation that mitigates an earlier completed effect. Restoring a configuration value may reverse a change; correcting an email cannot unsend it; recovering a refund may require a reviewed re-charge rather than an automatic opposite transaction. Define compensation alongside the original capability with its own authority and evidence requirements. A saga coordinates such recovery across steps, but its final state may still be partially resolved. Chapter 23 treats that operational reality in detail.

## Tool authentication, scoped credentials and least privilege

Obtain credentials at execution time through the runtime's identity boundary. The model should never choose a token or receive a secret merely to describe an operation. Use short-lived, audience-bound credentials and the narrow scopes needed for the accepted action. Where delegated identity is supported, downstream systems can enforce the user's own entitlement rather than trusting a powerful shared service account to remember every restriction.

Validate destinations as well as values. A tool accepting URLs, paths, SQL or hostnames can become an egress or execution capability unless its allowed scope is narrow and checked. Bound redirects and resolution where relevant, and use sandbox/network policy appropriate to the operation. Apply per-principal and per-tool quotas to protect shared dependencies. Least privilege should remain visible in the service contract, even when an SDK hides credential retrieval.

## Tool-output injection, poisoning and trust boundaries

A tool written by your team can return content written by someone else. A support email, product review or web page may contain instructions intended to influence later model decisions. Retain provenance, label external text, minimize fields and keep untrusted material separate from standing instructions. Model guidance helps, but it does not replace capability restrictions, egress policy and external approval/authorization checks.

Tool poisoning attacks the contract itself. A discovered description could instruct the model to send the conversation to an unrelated server before performing a lookup. Review discovered tools, pin schema and description hashes and alert on changes. Runtime capabilities should not gain privilege simply because a remote description changed. Chapter 14 applies these controls to MCP discovery; the same principle matters for any dynamically loaded capability source.

## Registry lifecycle, versioning and deprecation

Give every capability an owner, released version, reviewed schema, risk metadata and support path. Breaking changes require a migration plan; compatible releases still need tests. Record exact resolved versions and schema hashes in runs and audits. Deprecation removes a tool from new definitions first, retains it for supported pinned work where necessary and monitors remaining usage before retirement. Avoid making a pending approved operation resolve silently to a different implementation.

## Build it: a mutating tool with approval and idempotency

The complete executor in Chapter 11 demonstrates these boundaries using a small SQLite-backed fake payment service. Its accepted intent is persisted before the effect; downstream deduplication is atomic in the fake service. Authorization is rechecked on resume, rejection never executes and the verifier reads the actual payment record before completion. The code is a local teaching contract, not a substitute for a payment provider's transaction, credential and retention semantics.

For a production wrapper, validate arguments, authenticate the principal, check resource ownership, calculate current eligibility, bind approval to the accepted effect and enforce remaining limits. Then persist intent, submit under the service's idempotency/deadline contract, record outcome and return a bounded envelope. Apply redaction before serialization and keep truncation explicit. Arbitrarily slicing serialized JSON can produce invalid results and lose precisely the fields needed for recovery.

## Failure modes

Ambiguous descriptions cause selection errors; loose schemas admit malformed values; unstable keys create repeated effects; expired credentials or mismatched audiences break delegated authority; huge outputs overflow context; poisoned results influence later decisions. Each has a distinct prevention and diagnostic record. Contract tests should exercise invalid arguments, forbidden resources, denied approval, duplicate intent wording and failure after external success. A happy-path refund count alone does not test the uncertain crash window.

## Interview drills

Explain function calling as proposed intent, then walk through the accepted operation's envelope. For duplicate-side-effect prevention, distinguish transport deduplication, local intent recording and the domain's business uniqueness rule. For authorization, name principal, resource and arguments rather than only a scope string. For an uncertain timeout, describe reconciliation instead of reflexive retry. These answers make the safety argument inspectable without tying it to one tool framework.

## Key takeaways

Good tools are both understandable and controlled. Their contract helps a model choose and express work; their wrapper and domain service determine whether it can occur. Exact units, effect identity, authorization, approval and recoverable outcomes matter more than a long description promising care. A retry is justified by the effect contract, and a success message is justified by the authoritative result.
