# 33. Cloud & Enterprise Integration Tracks

An agent platform becomes useful when it fits the systems the organization already operates. ShopAssist needs an identity provider, order and payment services, durable storage and an approval channel. AegisOps needs alert streams, telemetry, change systems and incident records. A cloud offers components for these jobs, but choosing components is not the same as designing their contracts. Begin with the responsibilities, then map them to the services available in your account.

Cloud product names and availability in this chapter are orientation for the October 2026 edition. Check the provider's current documentation, supported regions and account quotas before committing to a design. A managed agent service can shorten deployment work without meeting every approval, retention or isolation requirement automatically. We will build one reference deployment deeply, then document how the important contracts would survive a move.

:::analogy Connecting a new building to a city
A new clinic needs rooms, water, electricity, roads and emergency access. The architect defines what each connection must supply; local utilities determine how it is installed. Moving the same clinic design to another city changes suppliers, permits and maintenance arrangements. An agent platform similarly joins an existing cloud and enterprise fabric. Where it stops: cloud services with similar purposes can have different delivery, identity and recovery semantics. A matching label in a catalogue does not make them interchangeable.
:::

## Building blocks across clouds

Separate the public entry point from background execution. The entry point authenticates the caller, validates a request, assigns an owned run identity and returns progress or an asynchronous receipt. Workers perform bounded model and tool work. A durable workflow coordinates waits, retries and completion. An LLM gateway, the owned model-access service, applies provider routing and accounting. These roles stay useful across vendors because they describe behavior rather than a specific deployment product.

The data layer holds different kinds of records. Run state and event history describe execution; an approval service records authority; an effect ledger supports dispatch and reconciliation; search indexes retrieve evidence; object storage holds large raw payloads. A cache can accelerate access but should not become the only copy of a pending approval. Identity, secrets and telemetry surround the whole system. Assign an owner and failure behavior to each building block before naming its provider service.

All three clouds offer container execution, serverless computation, queues, relational databases, object storage and observability. They also offer model access and increasingly managed agent capabilities. That breadth makes many architectures possible, but it does not remove trade-offs. For a long approval wait, inspect timeout and continuation behavior. For messages, inspect delivery and ordering. For state, inspect transaction and restore guarantees. These are the equivalents of checking water pressure rather than merely finding a water supplier.

## Track 1 - AWS

One self-managed AWS arrangement uses API Gateway for entry, EKS or ECS for services and workers, SQS or managed Kafka for buffered work, and Aurora or RDS PostgreSQL for durable application records. S3 holds raw evidence; ElastiCache supports coordination or caches. OpenSearch or PostgreSQL with pgvector provides search, depending on workload. Bedrock access sits behind the application's model gateway so quotas, cost and provider behavior remain centralized.

Step Functions can coordinate AWS-native workflows; Temporal can provide code-driven durable workflow semantics when that is the chosen application contract. Do not choose from their diagrams alone. Run a pending approval through a worker restart, timeout, late decision and downstream unknown outcome. Confirm where retry behavior is configured and which identifier reaches the effect service. An event's redelivery must recover or find existing work rather than create another refund.

Amazon Bedrock AgentCore offers managed runtime and surrounding capabilities, including gateways and policy integration. A gateway can turn supported APIs into tools; Cedar policy evaluates permission outside model reasoning. The [official policy concepts](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-core-concepts.html) describe the relevant boundary. Business eligibility and exact approval binding still belong to your application. A tool permitted by a gateway may still be invalid for the particular payment or live revision.

Use workload identity for pods or tasks rather than distributing static keys. Give the observation worker read access to its service's telemetry and the remediation executor narrowly scoped change authority. Route telemetry to CloudWatch or your chosen enterprise system, with redaction before export. Test that disabling the mutation path leaves alert ingestion and read-only investigation functioning. The deployment should keep helping responders even when authority to change production is withdrawn.

## Track 2 - Microsoft Azure

An Azure reference can use API Management at the edge, AKS or Container Apps for execution, Service Bus or Event Hubs for work and events, and Azure Database for PostgreSQL for durable state. Blob Storage holds large payloads; managed Redis provides caches. Azure AI Search can combine keyword, vector and ranking capabilities for governed retrieval. Microsoft Foundry model access passes through the owned model gateway, preserving consistent application accounting.

Entra ID often supplies the enterprise user's identity already. Managed identities supply workload authentication, but they do not mean that every operation should use the workload's broad rights. A refund or rollback should preserve the user or approved system principal, the agent actor and the targeted resource. Confirm how delegated credentials reach downstream services, how audience checks are performed and how the audit records both identities.

Durable Functions can express durable orchestration in an Azure-native serverless model. Temporal is another option when the application has chosen its workflow semantics. Foundry Agent Service supplies managed agent execution capabilities. Evaluate the exact workload model, not a generic assertion that managed services cannot support approvals. Some managed paths fit the requirement well; others need an external approval coordinator or an application-owned run store.

For knowledge retrieval, apply tenant and entitlement filters inside the retrieval request, not after the model sees the results. Use Key Vault or the organization's secret platform for credentials. Export operational evidence through Azure Monitor, Application Insights or enterprise collectors. Simulate a secret-access failure and a model quota failure: each should produce a bounded degraded response, not a silent fallthrough to an ungoverned public endpoint.

## Track 3 - Google Cloud

A Google Cloud reference can use Apigee or API Gateway for entry, Cloud Run for stateless services, GKE where scheduling and infrastructure control are required, Pub/Sub for buffered events, and Cloud SQL or AlloyDB for relational records. Cloud Storage holds raw evidence and Memorystore supports caches. Vector Search or PostgreSQL-compatible vector capabilities can serve retrieval. Choose the smallest arrangement that satisfies your evidence and operating requirements.

Google's Agent Development Kit supplies agent and workflow abstractions. Gemini Enterprise Agent Platform includes managed runtime, session, memory and related services; names evolved from earlier Vertex AI offerings. The [official platform update](https://cloud.google.com/blog/products/ai-machine-learning/whats-new-in-gemini-enterprise-agent-platform/) gives current orientation. Session and memory APIs still need application rules for subject scope, provenance and deletion. A managed store cannot decide which incident conclusion should become reusable knowledge.

Use workload identity rather than service-account keys in prompts or containers. Configure model access with regional availability and data policy in mind. Workflows or a chosen durable engine coordinates long-running lifecycle operations. For a Cloud Run worker, assume the instance can disappear; persist the work before acknowledging ownership and reconcile uncertain effects after continuation. A stateless service can run a stateful task only because its state is owned elsewhere.

Search and relational storage need not share a product. Keeping vectors beside application records may simplify operations, while a dedicated search service may better fit ranking and throughput. Measure with the organization's actual document types, filters and query mix. Run restore and index-rebuild drills separately. A recoverable database does not prove the searchable evidence is fresh, and a rebuilt index does not prove its entitlement metadata is correct.

## Track 4 - enterprise integration fabric

The enterprise fabric is the set of shared systems that connect applications: event streams, gateways, identity, secrets, observability and service management. An agent should join those systems through owned interfaces. Kafka alerts can start AegisOps; the API gateway authenticates operators; service identity protects tool requests; an ITSM system carries approved change records. Replacing all of that with a new agent-specific stack creates more boundaries to operate and audit.

Message consumption has two distinct deduplication jobs. A transport event ID stops the same delivery from creating duplicate work. Incident correlation groups different alerts describing the same service and symptom. Keep the first key stable across redelivery, even when a correlation time window changes. Otherwise yesterday's delayed message can be treated as a new incident simply because today's window differs. Record the original event and the correlation decision for later investigation.

A practical consumer needs a recoverable bridge between the database insert and workflow start. Store a dispatch intent or use the engine's idempotent start contract, then retry missing starts safely. Acknowledge the message only after its ownership is durably recorded. Define a dead-letter path for malformed or unauthorized events, and preserve enough redacted detail to repair them. Do not ask a model to infer whether the message bus delivered the same event twice.

Gateways and service meshes can provide authentication, transport protection, timeouts and egress restrictions. Inspect automatic retries: replaying a non-idempotent tool through a mesh can duplicate its effect before the harness notices. Secrets management should issue credentials to the executor under its workload identity, not pasted into context. OpenTelemetry correlation should continue across the queue, workflow, model gateway, MCP and downstream service so the operator can reconstruct one complete run.

## Managed agent runtime versus self-managed

A managed runtime supplies some operating responsibilities, such as scaling, session execution and service integration. The exact bundle differs by provider. A self-managed runtime gives the team control over deployment, state and extension points, with corresponding maintenance. Neither is inherently the more responsible choice. Select the arrangement whose supported lifecycle and boundaries fit the task and the team's ability to operate it.

:::diagram

:::

Ask whether long waits, external signals, cancellation, retries and versioned continuation fit the runtime's model. Check isolation, regions, private connectivity, telemetry export, encryption and retention. Try the difficult workflow before the happy-path demo. A managed session that works well for chat may require additional services for a payment approval spanning a deployment. Conversely, operating a large workflow platform for a short read-only task may add little value.

Hybrid deployment can make sense when one common policy and identity system governs both paths. For example, core refund execution can remain in an owned domain service while an approved managed runtime handles answer generation. Document where state crosses the boundary and what happens if either side is unavailable. Without this ownership description, hybrid often means duplicate histories, inconsistent approvals and two teams assuming the other recorded the effect.

## What is portable, and what is cloud-specific

Agent definitions, tools, prompt packs, evidence schemas, business policies and evaluation cases are good portable assets when their interfaces avoid vendor types. Containers and OpenTelemetry instrumentation can move too, although deployment and collector settings change. Portable does not mean no work: the model behavior, network latency and entitlement implementation may differ. Run the same contract and evaluation cases after a move, and record the differences rather than assuming parity.

Cloud-specific assets include identity bindings, managed-runtime APIs, queue delivery semantics, workflow definitions, secret access and private endpoint configuration. Put these behind adapters with behavioral tests. A queue adapter should specify acknowledgement, redelivery and cancellation, not merely `send` and `receive`. A model adapter should normalize stop reasons, usage and errors. That detail lets the new supplier meet the clinic's requirements instead of only matching its connector shape.

Maintain a migration inventory with asset owner, export format, retention constraint and test. Move read-only work first, compare evidence and outcomes, then migrate approved effects with a reconciliation plan. Keep historical approval and audit records available under their original identities. A database export is not a complete migration if paused threads cannot interpret their old tool versions or locate the evidence that justified a pending action.

## Identity and networking differences to plan for

Workload identity mechanisms differ across EKS, AKS, GKE and serverless services. Their shared purpose is authenticated workload access without static secrets. Verify which principal is presented at every boundary, and apply resource scope downstream. A network connection from an approved pod does not prove that the current user owns the order it requests. Transport identity, user delegation and record authorization are separate checks.

Private connectivity can reduce exposure and meet data-routing requirements, but its availability and cost vary. Test model endpoints, tool services, secret issuance, flags and telemetry collectors against the real egress policy. A mutation kill switch hosted outside the namespace needs an authorized access path too. If the flag service fails, the mutation policy should fail closed while diagnosis continues. Document sidecar and control-plane accesses instead of leaving them outside the diagram.

Quotas are capacity constraints, often specific to account, region and model. Allocate them across tenants and task classes before load arrives. Track admission queues, provider throttling and cost reservations. A sudden incident storm should not let low-priority postmortem drafts consume the quota needed for urgent triage. Residency-driven designs must also confirm that the selected model and its fallback are available within the allowed region.

## Build it: one reference deployment

Choose the primary cloud that fits your team's existing operating environment. Write infrastructure as code for networking, workloads, durable storage, event ingestion, secrets and observability. Deploy the agent API, workers and chosen workflow service independently. Keep effect execution in a narrow service with its own permissions and ledger. A single local container can teach the flow, but the reference deployment must show what survives process and node loss.

Use GitOps or the organization's deployment process to pin code, models, tools, policies and prompts as one release record. A rollout keeps each active run on a compatible behavior version. Prove that an approval created before deployment can be resumed after it without changing the approved arguments. If migration is necessary, make it an explicit tested operation. Do not let a new image reinterpret an old approval under new policy silently.

Finish with a mapping document for a second cloud. Name the adapters to replace, records to export, identity changes and expected operational gaps. The deliverable should let another engineer estimate the work honestly. Keep a small migration experiment using the same read-only evaluation cases. This creates evidence that the portable core is real while avoiding the cost of maintaining three complete platforms solely to prove a diagram.

## Interview drills

For a managed-versus-self-managed question, begin with the task's lifecycle and the team's operating capacity. Describe one pause, one crash and one authority boundary. Explain what the provider operates and what the application owns. For portability, name a queue or identity semantic that needs retesting. An answer that says “same architecture, different names” is a useful beginning, but the behavioral differences are where integration work becomes real.

For an event-driven design, trace an alert through durable ownership, workflow dispatch and acknowledgement. Explain how duplicate delivery finds existing work, how a lost start is repaired and where an unauthorized event goes. Then show how correlation groups related alerts without changing transport identity. This end-to-end account connects cloud services to failure handling and demonstrates why a unique database key is necessary but not sufficient.

## Key takeaways

Map the platform's required contracts to cloud services, verify their semantics, and build one deployment your team can operate. Managed execution changes who maintains infrastructure; business authority, effect safety and evidence still need owners. Treat identity, regional capacity, egress and recovery as design inputs. Like a clinic joining a city, the platform succeeds when every connection supplies what the work requires and its failures have a known response.
