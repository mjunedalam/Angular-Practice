# 37. Building AegisOps Phase by Phase

The blueprint is intentionally broad. Building it all at once would leave too many uncertain boundaries: model behavior, tools, persistence, identity and effects could fail together. Instead, each phase adds one capability and proves the contracts on which the next phase depends. The early milestones investigate with evidence. Real mutation arrives only after durable execution, scope and approval are established. Chapter 38 adds sustained verification, operating evidence and rehearsal.

Treat the phase order as dependency order, not a guaranteed calendar. A simulated portfolio with fake services is much smaller than enterprise integration with reviewed credentials and production change processes. Record the team, scope and assumptions behind an estimate. An experienced engineer can make steady progress by keeping the first scenario narrow: a bad order-api release followed by latency and 5xx errors. Each phase must leave that scenario runnable and testable.

:::analogy Building a workshop before handing over its keys
A workshop first needs an agreed purpose, sound structure, visible instruments, tested procedures and controlled access. Only after those are checked should a powerful machine be enabled. AegisOps is built in the same order: define the task, establish observation, prove reasoning, then grant narrow authority. Where it stops: read tools are not risk-free windows. They can expose sensitive data and carry hostile text, so confidentiality and input boundaries begin before any production mutation.
:::

## The build at a glance

Milestone M1 covers phases 0 through 4: a read-only investigator that diagnoses a synthetic incident with cited evidence. M2 covers phases 5 through 7: competing hypotheses, scoped coordination, reusable skills and MCP. M3 covers phases 8 through 10: a durable, authenticated, approved simulated change with current preconditions. M4 covers Chapter 38's phases 11 through 15: verification, evaluation, deployment and hostile game days. A stopped project should still have a coherent completed milestone.

Write each phase's exit test before building it. Tag milestone releases and capture a short demonstration showing evidence, not only the final answer. Keep a change log of contracts and limitations. When a later integration fails, the known-good milestone distinguishes a new adapter defect from a broken core invariant. This also produces a better portfolio story than a large repository whose history never reveals when any capability became reliable.

The test environment should include fake cluster state, changes, metrics, logs, runbooks, approvals and effect records. Their behavior must be explicit: a fake mutation can apply and then lose its response; fake observations can remain unhealthy; fake credentials can expire. Fakes let you prove deterministic control without buying a model call for every test. Live integrations and live-model evaluation come later, because they test different uncertainties.

## Phase 0 - Define the contract before writing agent code

Write a one-page problem statement with environments, users, supported outcomes and non-goals. For the first scenario, order-api's new revision correlates with elevated latency and errors. Success means evidence gathering, tested alternatives, a bound rollback proposal, the required approval, controlled execution and observed recovery. Escalation is also success when authority, evidence or recovery cannot be established. Do not define completion as the model announcing that it fixed the incident.

Create the initial autonomy register and prohibited-action list. State the risk 3 runbook exception, risk 4 two-person rule and risk 5 block. Write one decision record explaining why adaptive investigation helps and another establishing the framework-neutral application boundary. Define a versioned incident schema with tenant, service, environment, evidence and proposal identities. Reviewers should be able to describe who owns the run and what it may never do without reading a prompt.

The phase exits when the contract is testable and the synthetic incident has reference evidence. No production credentials are needed. The repository has architecture notes, decisions and a reproducible fake-run entry point. Name the person who can accept changes to the autonomy boundary. An evolving capstone can change its scope, but the change must be deliberate rather than introduced as an undocumented new tool permission.

## Phase 1 - Build the agent harness skeleton

The harness needs an owned RunContext, typed input/output, model interface, tool registry, state transition rules and budgets. The context includes the incident identity and actual permitted service/environment, not just a tenant label. It carries verified principal and workload identity, remaining allowances, deadline and trace context. Derived authority is not a model argument. A specialist receives only the subset of this context needed for its task.

```python
from dataclasses import dataclass
from datetime import datetime

@dataclass(frozen=True)
class RunContext:
    incident_id: str
    tenant_id: str
    service_id: str
    environment: str
    principal_id: str
    agent_id: str
    allowed_operations: frozenset[str]
    remaining_steps: int
    deadline: datetime
    behavior_version: str
    trace_id: str
```

This is a compact context definition, not a complete credential structure. The authentication layer constructs it from trusted identity and policy, and the execution layer refreshes short-lived credentials separately. Add model operations for ordinary and structured generation behind a provider adapter. Normalize errors and token usage. Keep budgeting around the calls so no model or tool step begins after its deadline or permitted allowance is exhausted.

Use a fake model that repeatedly requests another investigation to test termination. The run ends with a documented failed-safe or escalation reason, and any uncertain effect remains available for reconciliation. Instrument model calls, tools and transitions under one correlation ID. The phase exits when a toy investigator terminates predictably, supports typed failure and produces a trace sufficient to explain its sequence without relying on the model's self-report.

## Phase 2 - Build typed read-only tools first

Build metrics, logs, traces, workload state, recent changes and service ownership as independently tested adapters. Inputs use validated identifiers, allowed metric templates, bounded time ranges and result limits. Tenant and environment scope come from RunContext. Verify service membership too; a regex proving that a service name looks valid does not prove the caller may read it. Apply these checks before fetching observations.

```python
from datetime import timedelta

def validate_metrics_request(request, ctx):
    if request.service_id != ctx.service_id:
        raise PermissionError("service outside incident scope")
    if request.environment != ctx.environment:
        raise PermissionError("environment outside scope")
    if request.metric not in {
        "latency_p95", "error_rate", "rps", "saturation"
    }:
        raise ValueError("unknown metric template")
    duration = request.end - request.start
    if not timedelta(0) < duration <= timedelta(hours=6):
        raise ValueError("window outside permitted range")
    return request
```

The query builder uses server-owned templates and safely encoded scope values; it does not interpolate arbitrary model-supplied PromQL. Normalize results into evidence with units, observation time and source/query references. Store large raw data separately rather than returning unbounded series into context. Source authentication, factual extraction and instruction authority are distinct: text returned by a real telemetry service still cannot tell the agent to ignore policy.

Test timeout, throttling, malformed response, partial results and permission denial. A trace-search cap should hold even when the backend returns far more data. The phase exits when a model-free tool call can explain what changed, what failed, where and when, and when failures remain typed observations. Add secrets and data-exposure checks now; read-only integration is not a reason to postpone privacy.

## Phase 3 - Add enterprise RAG and evidence discipline

Ingest the approved runbooks, architecture notes, service catalogue and previous incident records. Preserve owner, version, update time, classification and entitlement metadata. Chunk by useful document structure, use hybrid retrieval and reranking where measured, and return source locators with every passage. Query-time filters ensure the investigator cannot read another tenant's restricted knowledge. A retrieved passage is evidence, not a new instruction pack.

Build an evidence ledger before teaching the model to narrate a diagnosis. Require a stable evidence ID for each extracted fact and explicit references in hypotheses and proposals. Verify that the cited passage supports the claim and applies to the service/version. Allow a hypothesis with uncertainty, but reject an action proposal whose required supporting facts are missing. This prevents confident wording from replacing the evidence the approval card needs.

Create labeled retrieval cases containing relevant runbooks, near matches, obsolete versions and an unanswerable question. Track retrieval separately from end-to-end resolution so a poor chunker is not blamed on planning. The phase exits when answers have inspectable citations, stale evidence is marked and insufficiency becomes a clear partial answer or escalation. Changing the index or reranker should rerun the same cases with its configuration version recorded.

## Phase 4 - Implement triage and observability agents

Triage parses the alert, identifies the service and environment within scope, proposes severity and a short investigation plan. Validate the output with an explicit schema and maximum plan length. Observability executes bounded read requests and returns facts and anomalies with evidence IDs. The workflow applies accepted updates; a specialist does not directly rewrite global lifecycle state. This establishes a usable investigator before collaboration complexity arrives.

Test alerts with misleading descriptions and injected text. The agent might still propose an inappropriate action, so assert on denied capability access and recorded behavior, not only a polite final response. Seed an invented metric in the model output and ensure it cannot become evidence. A field's valid JSON shape is not proof it came from the telemetry adapter. Acceptance requires source linkage and semantic checks as well as parsing.

The phase exits when the reference incident produces the affected service, degradation onset and cited observations, and when unsupported output cannot cross into the proposal path. Measure how often triage needs clarification or escalation. Keep those outcomes visible rather than forcing every input into a confident severity. An incident commander benefits from knowing which facts are uncertain before it decides how much investigation to spend.

## Phase 5 - Add change intelligence and hypothesis falsification

Retrieve recent deployment, flag and infrastructure history using bounded windows. Compare symptom onset with concrete revisions and affected populations. A correlated release is a candidate explanation, not a verdict. When evidence is ambiguous, maintain at least two plausible hypotheses with supporting and contradicting IDs. Generate a cheap test that could weaken each hypothesis. The aim is to avoid treating the first plausible story as a proven cause.

For the bad-release case, check whether errors are concentrated on new pods, whether older pods remain healthy and whether dependency latency changed. Normal aggregate database p95 weakens one explanation but does not rule out every database fault. Record the scope of each test. A dependency-outage scenario should contain unhealthy dependency evidence across old and new versions, contradicting rollback as the correct first action. Do not silently replace that scenario with unrelated database slowness.

The phase exits when the reference release is identified, one alternative is tested with explicit evidence and the final cause statement retains uncertainty where needed. An evaluator can identify missing support or unsafe leaps, but should not create new facts. Its output is a critique for the commander to validate. Keep the test cases deterministic before measuring whether stronger models improve the hypothesis quality enough to justify their cost.

## Phase 6 - Introduce the supervisor and multi-agent handoffs

The supervisor pattern gives the commander ownership of the incident plan and global budgets. A specialist registry states each role's capabilities, scope, expected evidence, cost tier and deadline. The commander chooses specialists from current needs instead of broadcasting every alert. Shared state remains in the owned workflow/store; workers receive limited context. Their outputs merge under evidence semantics, and conflicting reports remain inspectable until the commander applies a stated resolution rule.

Handoff envelopes include the task, relevant evidence, allowed operations, deadline and output schema. Distinguish delegated subwork from transferring incident ownership. An optional remote A2A boundary can demonstrate another team's capability, but the local policy still limits what its result permits. Test a specialist returning malformed output, unsupported instructions or no response. The system should continue with documented partial evidence or escalate, never invent the missing report.

The phase exits when traces show commander-to-specialist-to-commander work, specialists cannot broaden scopes, and the scenario still handles an optional role's failure safely. Compare a single investigator with the new collaboration on the same cases. Keep the additional agents only if the isolation or quality/latency benefits justify coordination. The teaching milestone demonstrates explicit handoffs; it does not require needless agent count in a real deployment.

## Phase 7 - Add composite skills and MCP

Package the latency diagnosis, deployment assessment and recovery verification interfaces as reusable skills. Each declares inputs, tools, side effects, output, limits and tests. Make a read skill usable from two investigator roles without copying its orchestration. Keep procedural changes under versioned review. A skill file can describe adaptive work, but computations and invariant checks should stay in deterministic code where they can be tested directly.

Start MCP integration with observation and knowledge servers. Put the MCP adapter behind the owned tool registry, pin server identity and schema, and expose only an exact approved capability list. Changed descriptions and new tools are reviewed before use. Test a server introducing a mutating tool with a familiar namespace. The discovery result should be rejected or quarantined, and a direct execution attempt should fail the same policy boundary.

The phase exits when one skill serves more than one role, schema drift produces an explicit audit event and newly discovered capabilities never become authority automatically. Record MCP protocol and adapter versions with the run. Transport convenience should not erase the existing tool contracts. A reviewer must still be able to locate the downstream authorization and effect-safety rules without learning the MCP client's implementation details.

## Phase 8 - Make the incident durable with Temporal

Move the lifecycle into a durable workflow with activities for external observations, model calls and effects. Deterministic replay reconstructs recorded workflow progress. Workflow code decides deterministic sequencing, while activity results record nondeterministic work. Signals carry notifications such as an approval becoming available; durable timers impose deadlines. A workflow can wait without tying up a worker. The critical contract is that continuation uses the same owned proposal and effect identity after process loss.

In the Python SDK, `workflow.wait_condition(..., timeout=...)` completes when the condition holds and raises `asyncio.TimeoutError` when its deadline expires. It is not a Boolean test for approval. Catch the timeout and execute the stated escalation path. After a signal, load or validate the authoritative approval record; the signal's arrival does not prove its contents are authorized. See the [Temporal Python message-passing guide](https://docs.temporal.io/develop/python/message-passing).

Kill the worker during investigation, while waiting and after an external effect but before its completion reaches the engine. Completed recorded activities are not re-executed merely by workflow replay; an activity whose completion was not recorded may retry. The downstream service must honor the persisted effect identity, or the adapter must reconcile safely. The phase exits when the run survives each crash and the provider-side effect ledger shows no duplicate logical change.

## Phase 9 - Add identity, authorisation and security guardrails

Separate the requesting operator or system principal, the agent workload and the downstream service identity. Use authenticated context and short-lived audience-bound tokens. Policy checks tenant, environment, operation, resource and blast radius before data access or effect dispatch. An agent token should not contain broad standing production authority merely because the agent could eventually need a rollback. Grant the exact operation only after its requirements hold.

Threat-model injected log lines, poisoned tools, compromised remote artifacts, confused deputy behavior, secret leakage and sandbox escapes. The model can read malicious content as evidence without that content becoming an instruction. Avoid broad outbound channels in the same context as private data. If code, shell or browser capability is unnecessary, leave it unavailable. If required, isolate it under the explicit filesystem, network and secret policy from Chapter 21.

The phase exits when cross-tenant requests fail deterministically, injected authority cannot execute a forbidden tool, and denials appear in audit with useful reasons. Tests should also permit legitimate scoped work so a policy that denies everything is not mistaken for success. Record residual risks, including bad proposals within allowed investigation. Evidence, approval quality and post-action verification remain necessary even when the action's credentials are narrow.

## Phase 10 - Implement human approval and safe mutations

Create an immutable ActionProposal containing operation, target, canonical arguments, evidence, impact, risk, current preconditions, recovery plan, verification and logical effect identity. The approval card presents that proposal before any effect. Risk 4 requires two distinct authorized privileged approvers; risk 5 is blocked. Editing the target, amount or revision creates a new proposal and decision requirement. Successful validation preserves human provenance rather than marking it automatic.

The approval service validates tenant, action ID, hash, roles, distinct identities, expiry and unused or recoverably reserved status. Precondition re-validation happens at the effect boundary. The executor persists effect intent before dispatch, consumes or reserves approval according to its transaction contract, and obtains the narrowly scoped token. It passes expected resource revision to the change service, which checks and mutates atomically or returns a conflict. An ordinary read followed by rollback leaves a race and is insufficient.

Begin with fake or staging change adapters. Test approve, reject, expiry, stale live revision, missing second approver, immediate replay and timeout after processing. Outcome unknown does not advance directly to verification or a second action. Record it and reconcile. After a confirmed applied result, enter VERIFYING even when the tool returns success; Chapter 38 completes the observation mechanism. M3 is finished when the authority and dispatch contract survive failure, not when production access first works.

## Interview drills

Property-based testing can supplement each phase by generating event redelivery, approval timing and dependency-failure combinations. Inspect owned records and the fake downstream ledger, not the agent's summary. Save any failing combination in the regression set. Generated sequences do not establish every possible live failure, but they can expose races that isolated happy-path examples miss.


Explain why read tools precede reasoning: evidence quality can be tested without model variability. Explain what durable workflows add beyond snapshots: recorded activities, signals, timers and replay, with external idempotency still required. Show the difference between a demonstrated run and a phase exit: the latter is a reproducible contract test with inspectable evidence. Discuss the stale-revision race at the downstream boundary rather than claiming a preceding lookup solves it.

If M3 passes, test a worker loss during approval, an immediate decision replay and a rollback whose response is lost. Then test a confirmed rollback whose service remains unhealthy. These cases join authority, recovery and verification without broadening the scenario unnecessarily. A strong explanation identifies the exact record and invariant at each failure point, making the system's safety understandable even to a reviewer unfamiliar with the chosen framework.

## Key takeaways

Build AegisOps in dependency order: contract, controlled runtime, scoped evidence, tested reasoning, reusable coordination, durability, identity and approved effects. Save a complete smaller milestone before extending it. Every stage needs deterministic acceptance evidence and explicit limitations. The workshop's keys arrive after its controls, and those keys open only the permitted machine: a bound action under current conditions, with a recoverable effect identity and a verification path.
