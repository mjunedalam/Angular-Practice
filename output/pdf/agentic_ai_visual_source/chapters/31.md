# 31. Framework Mapping: LangGraph, OpenAI Agents SDK, Spring AI & Others

ShopAssist has a small job with serious consequences: explain an order, decide whether a refund is eligible, and move money only after the required checks. The earlier chapters separated those responsibilities. We can now ask a more useful framework question than which library has the most features: which responsibilities will this library implement, and which responsibilities must our application still enforce?

This chapter maps the same refund flow onto several ecosystems. The examples are implementation sketches with explicitly described domain services. They are not complete payment applications. Framework statements are checked for the October 2026 edition; pin exact package versions, preserve your lockfile, and rerun the approval and restart tests whenever you upgrade. An unchanged method name does not prove unchanged behavior.

:::analogy Buying vehicles for a delivery business
A delivery business already knows its routes, parcel limits and driver rules before choosing vans. A manufacturer supplies an engine, transmission and dashboard. The business still decides who can drive, which parcels a driver may carry, and how a delivery is confirmed. Agent frameworks supply different engines and controls for a job whose rules should already be understood. Where it stops: software frameworks can change persistence and execution semantics between releases; knowing the controls is not enough to establish safety or portability.
:::

## The concept map

An agent definition describes instructions, a model and available capabilities. A controller repeatedly asks for a decision, checks it, and runs permitted tools. State records progress; a checkpoint supports continuation; an approval records authority for one proposed action. A framework might provide these as objects, graph nodes, decorators or services. Start with those meanings, then map them to names in the chosen SDK.

In LangGraph, the principal execution object is a compiled graph, with subgraph composition available for reusable capabilities. In the OpenAI Agents SDK, it is an agent run managed by a Runner. In Spring AI, a ChatClient call passes through advisors, including the tool-calling loop. These are different programming surfaces. None of them defines your organization's refund limit, proves that the customer owns the payment, or makes an arbitrary payments API idempotent.

Keep a framework-neutral tool contract with a typed request, bounded response, error classes, authorization rule and side-effect class. Keep an application run record containing the tenant, principal, remaining budgets, proposal and effect identifiers. Framework messages can be adapted at the edge. This takes some effort initially, but it keeps the rules reviewable and prevents a library upgrade from silently becoming a business-policy change.

The same distinction applies to memory and observability. Conversation history is not necessarily a complete interrupted execution. An OpenTelemetry trace is not necessarily a durable audit record. A namespaced store is not automatically tenant-isolated. Write down what each feature actually guarantees. In our delivery analogy, a dashboard recording speed does not replace the delivery ledger, and a glove compartment does not become secure parcel storage merely because it has a label.

## LangGraph: state graphs, checkpoints, interrupts, durable orchestration

LangGraph represents work as nodes that read state and return updates. Edges schedule the next work. Reducers specify how updates combine, while checkpointers persist graph progress. This fits ShopAssist when the application must visibly pass through gather, assess, approve, execute and finish. Chapter 32 develops the details; here the key choice is whether an explicit graph helps reviewers see the mandatory boundaries.

Place the approval in a node that constructs a proposal card and calls `interrupt()`. Resume that thread using `Command(resume=...)`. The interrupted node restarts from its beginning, so anything before the interrupt must tolerate repetition. Put the financial effect in a separate node, with its stable effect identifier and downstream idempotency contract. Separating nodes avoids approval-related repetition; it does not close the crash window around an external payment.

The approval service must check the proposed action ID, argument hash, authorized approvers, expiry and consumption status. The payments service must check current captured and refunded amounts atomically. The graph should call these services rather than reproduce their rules inside prompts. A rejected approval terminates or escalates; an expired approval requests a new decision; an unknown payment outcome enters reconciliation. These outcomes deserve distinct recorded reasons.

For production, choose durable checkpoint storage and define who may read or resume each thread. An in-memory saver is useful in tests but disappears with its process. A thread ID identifies stored execution; it is not authentication. If a user can name another tenant's thread and your API resumes it without an ownership check, the persistence feature has become an access-control defect.

## OpenAI Agents SDK: agents, tools, handoffs, sessions, guardrails, tracing

The OpenAI Agents SDK organizes a run around agents with instructions and tools. A Runner manages model calls and tool execution. A handoff transfers conversational control to another agent; an agent exposed as a tool can return work without transferring ownership. ShopAssist can use triage to hand a refund request to a specialized refund agent, while keeping a single application record for the conversation and its budgets.

Sessions preserve conversation history. They are useful for follow-up questions, but do not substitute for the application's approval record or financial ledger. Input and output guardrails validate at defined points in a run. Tracing records execution detail. The application must still decide which checks need to run before every effect, how sensitive fields are redacted, and which events must survive trace sampling or retention.

There are two legitimate approval designs. A `propose_refund` tool can create a durable approval request while an external workflow handles execution. Alternatively, a function tool marked `needs_approval=True` can pause the SDK run. Choose one explicit design for the refund path; do not allow both to create independent authorities for the same effect. The SDK's pause records pending calls, while your service decides who may approve them.

Store serialized RunState on the server under the run's tenant and owner. Do not accept a client-edited snapshot as authority. An approval request may identify the run and pending call, but the server loads the trusted snapshot and applies the verified decision. After resume, the model can request another tool, including another approval. Therefore the response handler must check for interruptions after every run, not only the first invocation.

The following sketch deliberately omits SDK setup and payment integration. Its service contracts are the important part: storage loads an owned snapshot; approvals returns only individually authorized call decisions; the runner can pause again. `effect_id` belongs to the persisted business proposal, not to a newly generated retry timestamp. Currency is represented separately from an integer amount in minor units, so retries cannot depend on floating-point rounding.

```python
async def continue_refund(run_id, principal, runtime, store):
    saved = store.load_owned(run_id, principal.tenant_id)
    state = await runtime.restore(saved.snapshot)
    for pending in state.pending_calls():
        decision = store.validated_decision(
            run_id, pending.call_id, principal
        )
        if decision is None:
            continue
        state.apply_decision(pending.call_id, decision)
    result = await runtime.run(state, saved.budgets)
    store.save_owned(run_id, result.snapshot, principal)
    return {
        "status": result.status,
        "pending": result.pending_calls,
        "answer": result.final_output,
    }
```

This is pseudocode for an adapter interface, not an SDK API listing. A complete adapter also persists remaining cost and time budgets across continuation. Resetting a Runner's invocation limit does not reset the organization's financial allowance. The [official human-in-the-loop documentation](https://openai.github.io/openai-agents-python/human_in_the_loop/) and [RunState reference](https://openai.github.io/openai-agents-python/ref/run_state/) describe the supported serialization and approval surfaces.

## Spring AI: the Java enterprise path

Spring AI fits model calls and tools into Spring applications. A ChatClient is configured with instructions, tools and advisors. Annotated `@Tool` methods expose application capabilities; advisors supply concerns such as conversation memory and retrieval. VectorStore and ingestion components support knowledge access. Micrometer observations connect the interaction to established telemetry. This is especially useful when order ownership, payment accounting and transaction boundaries already live in Java services.

In Spring AI 2.0, the tool-calling loop is an auto-registered ToolCallingAdvisor in the ChatClient chain. That allows application-controlled interception around tool calling, rather than relying on a private loop inside each model integration. Structured-output validation can retry formatting failures, but it does not establish eligibility. MCP client/server support and annotated capabilities provide interoperability. Consult the [Spring AI 2.0 release explanation](https://spring.io/blog/2026/06/12/spring-ai-2-0-0-GA-available-now/) when migrating older configurations.

A refund tool should call an authenticated domain service, not a repository directly with whatever order ID the model supplied. Use BigDecimal or integer minor units with explicit currency rules. A proposal method can return an approval ticket containing evidence and binding fields. A separate executor consumes that ticket and invokes the payments service. A database transaction protects local accounting, while downstream idempotency protects the remote operation; neither substitutes for the other.

## Claude Agent SDK: a production agent loop with built-in tools

The Claude Agent SDK includes an agent loop with built-in file, shell, search and other capabilities. It supports sessions, subagents, hooks and permission controls. That broad tool surface can reduce implementation work for coding or research systems. It also makes capability restriction an early design task. A customer-facing refund agent does not need the same workshop as an agent repairing a repository.

Permission rules and tool visibility are related but different. `allowed_tools` supplies preapproval. It should not be read as proof that every other capability is inaccessible. Hooks can inspect calls; a permission callback handles calls that reach it. Use exact approved names, deny unknown capabilities, constrain the available toolset, and check the discovered MCP schema against its pinned definition. Namespacing alone does not classify risk.

```python
APPROVED_SHOP_TOOLS = frozenset({
    "mcp__shop__get_order",
    "mcp__shop__propose_refund",
})

def shop_permission(tool_name, pinned_schema_matches):
    if tool_name not in APPROVED_SHOP_TOOLS:
        return {"allow": False, "reason": "unknown_tool"}
    if not pinned_schema_matches:
        return {"allow": False, "reason": "schema_drift"}
    return {"allow": True, "reason": "approved_contract"}
```

This is the pure policy core, not the callback's SDK return type. The adapter converts the result to the SDK's allow/deny object. Even an allowed `get_order` requires record authorization in the order service. Audit hooks redact sensitive arguments before recording them. For shell or browser work, use an isolated environment without production credentials. Working-directory selection alone does not establish filesystem confinement. The [official permission guide](https://code.claude.com/docs/en/agent-sdk/permissions) explains rule evaluation.

## The Microsoft, Google and AWS agent stacks

Microsoft Agent Framework combines ideas from Semantic Kernel and AutoGen with agent abstractions and explicit workflows, including MCP and A2A interoperability. Microsoft Foundry supplies managed services, while Entra ID and Azure data services provide the surrounding enterprise identity and knowledge components. The [April 2026 version 1.0 announcement](https://devblogs.microsoft.com/agent-framework/microsoft-agent-framework-version-1-0/) establishes the edition's terminology. Treat framework support and managed-service availability as separate facts when planning a deployment.

Google's Agent Development Kit supplies agent and workflow building blocks. Gemini Enterprise Agent Platform provides managed runtime, session, memory and related platform capabilities. The names describe a development-to-deployment path, not a guarantee that every component meets your retention or approval policy. AWS offers Strands Agents and Amazon Bedrock paths, with Amazon Bedrock AgentCore supplying runtime and gateway services. Its policy integration can enforce Cedar rules outside the model at tool access.

For all three, inspect the same contract: inbound identity, outgoing delegation, state ownership, regional availability, exportable telemetry, data retention and supported resume behavior. A managed gateway may remove credential plumbing while leaving business eligibility entirely yours. A managed memory service may store records while your application still owns write consent and deletion. Chapter 33 turns these questions into deployment tracks; do not choose a cloud by counting differently named boxes.

## LlamaIndex and LangChain components

LlamaIndex is useful for connecting, parsing, indexing and querying knowledge. LangChain supplies model, tool, retrieval and document-processing integrations commonly used beneath LangGraph. Use these components behind a retrieval interface that accepts a scoped question and returns evidence with source locators. The interface should preserve document version, entitlement filters and freshness. Returning a fluent answer without those fields discards the properties the application needs to verify it.

These libraries can reduce mechanical work, but the organization still owns relevance evaluation, document updates, sensitive-data boundaries and citation checks. Run a fixed retrieval test set when changing a splitter or reranker. The delivery business may buy a better navigation system, but it still needs the correct destination and parcel permissions. An answer generated from the wrong policy version remains wrong even if every individual integration call succeeds.

## CrewAI and AutoGen as multi-agent pattern exposure

CrewAI exposes role-based agents, tasks and processes, with flows for explicit orchestration. AutoGen helped popularize conversational collaboration between agents; Microsoft Agent Framework is the successor path described above. These systems are useful places to observe delegation patterns quickly. Their convenience should not decide the number of agents in your production design. Add a specialist for measurable isolation, expertise, context or parallelism benefits, then measure the coordination overhead.

Keep one owner for the task, an explicit handoff envelope, scoped capabilities and shared limits. Test what happens when a specialist returns an unsupported claim or cannot finish. A missing result should become partial evidence or escalation, not an invented success. A supervisor's decision must pass the same effect checks as a single agent's decision. Multi-agent conversation does not multiply the authority granted to the underlying user.

## Selection criteria

Compare control flow, persistence, human approval, tracing, policy hooks, interoperability, operations, language fit and licensing. For each criterion, write a question whose answer can be demonstrated. “Supports persistence” is too vague; “resume a pending approval in a new process using durable storage without repeating a payment” is testable. “Supports tracing” should include export and redaction, not merely a vendor dashboard screenshot.

The operational burden belongs in the comparison. Count databases, queues, migration procedures and services your team must maintain. Ask how paused runs survive code changes and how a compromised worker is contained. Check whether framework state can be inspected without vendor-specific tooling. An attractive prototype may still be a poor fit for a team that cannot support its runtime during an incident.

## Build it: the same agent in two frameworks, and an ADR

Implement ShopAssist in two chosen runtimes with shared policy, tool and evaluation packages. Use the same model configuration and the same scripted fake outcomes first. Cover approval, rejection, expiry, malformed output, a provider timeout after processing and a process restart. Then run live-model evaluations on the same labeled conversations. Repeated trials reveal variability; deterministic failures should be fixed before attributing differences to model behavior.

Record success by case, forbidden actions, cost per successful conversation, latency and operational effort. Specify the confidence interval and which cases must pass regardless of the aggregate score. An architecture decision record states the problem, options, evidence, decision, consequences and revisit condition. Do not invent attractive percentages to make the record look complete. A small honest comparison is more useful than a polished but unsupported result.

For example, choose LangGraph if explicit routing and long pauses are decisive in the measured refund cases. Choose a Spring service boundary for Java domain logic already owned by that team. Keep framework message types inside adapters and document how stored runs would migrate. The exit strategy should name real work: state conversion, checkpoint handling, trace parity and approval continuity. Replaceability is a maintained property, not a promise made once.

## Interview drills

When asked how to avoid lock-in, name the application contracts and the alternative-runtime test that keeps them honest. When asked what the framework handles, trace one request through model output, policy, approval, effect dispatch and reconciliation. Explain who owns each record. This makes the answer concrete and prevents a feature list from concealing the hardest boundary: authority over a real external effect.

When asked which framework is best, state the workload first. A coding agent needing controlled filesystem tools differs from a narrow refund service waiting hours for approval. Explain one decisive test and one operational cost. Mention the conditions under which you would revisit the decision. The goal is a defendable choice with observable consequences, not a claim that one engine wins every route.

## Key takeaways

A framework earns its place by implementing understood responsibilities. Its convenience is real, but application eligibility, authorization, approval binding, external-effect safety and evaluation remain explicit contracts. Compare runtimes under the same tasks, preserve remaining budgets across pauses, and deny unfamiliar capabilities. The delivery business can change its vehicles while keeping its delivery rules; software achieves that freedom through adapters, owned records and repeated tests.
