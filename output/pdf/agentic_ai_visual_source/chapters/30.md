# 30. LLM Gateway, Provider Abstraction & Self-Hosted Inference

Several teams use models for routing, extraction, tool decisions and evaluation. If each team independently manages keys, quotas, fallbacks and data policy, the organisation has no consistent view of model traffic. A request can change provider during an outage without preserving the tenant's region rule, or several agents can exhaust one shared quota. An LLM gateway creates a common boundary for model access while leaving the agent's task logic outside it.

The gateway can connect managed APIs and models served by the organisation itself. Self-hosting changes the operating responsibility, not only the endpoint URL. The team now owns capacity, model loading, serving software, licensing and lifecycle. This chapter explains those trade-offs and the mechanisms behind efficient inference, so a platform decision follows workload evidence rather than the assumption that open weights are always cheaper or that compatible APIs make providers interchangeable.

:::analogy A restaurant booking desk and its kitchen
One booking desk applies reservation rules, allocates capacity and directs requests to the suitable kitchen. A purchased catering service is simpler to operate; an owned kitchen gives more control but requires equipment, staffing and maintenance. During service, staff reuse preparation where appropriate and keep many tables progressing. Where it stops: models differ in competence and protocol features, and a kitchen's menu does not prove quality. Placement, privacy and measured task performance still constrain every route.
:::

## Why an LLM gateway

A gateway centralises caller authentication, task-aware routing, quota allocation, approved fallback, usage accounting and data-placement checks. Agents call a stable internal interface using verified workload identity rather than carrying provider keys. The gateway can enforce which providers and regions a tenant may use, record actual model identity and apply shared observability. This reduces repeated cross-cutting implementations, but it also creates an important service whose availability and fail-closed policies need design.

Keep its responsibility narrow. It mediates model requests; it does not replace the business executor's approval or resource policy. A gateway that filters generated text cannot guarantee that a later tool call is authorised. The agent harness still validates decisions and the protected tool gateway still enforces effects. Likewise the gateway should derive trusted tenant/agent context from authentication rather than granting privileges because a request body says risk=low or tenant=Northwind.

Define a request contract with task type, required capabilities, output constraints, bounded generation settings and trusted data classification. Responses normalise content, tool intents, stop reasons, usage and errors. Record routing reason and release/model identity so evaluation can compare the actual configurations used. The gateway should not silently substitute an unsupported output feature or reduce a high-risk quality floor to make a request succeed.

## Provider adapters and compatible interfaces

Many serving systems expose an interface compatible with familiar chat-completion APIs. That can simplify transport, but features differ: tool-call representations, structured output, streaming, token usage, context limits, caching and reasoning controls may not match. An adapter should translate into the application's own types and state what it supports. Compatibility at an endpoint path is not proof that a task's output contract or quality remains equivalent.

Test the adapter with recorded success, truncation, refusal, tool-call and error fixtures. Reject unsupported required capabilities before spending quota. Normalise billing categories without guessing that every provider's input count includes cached tokens or that every failed response consumed nothing. Preserve the actual resolved model version and relevant server settings. A provider migration is an evaluated configuration change, not only replacing an API base URL in a file.

Own the state and tool schemas the agent depends on. Translate schema details at the adapter boundary rather than letting vendor objects spread through the whole harness. Some useful provider features remain specialised; hide them behind an explicit supported capability instead of pretending they are universally portable. Soft dependence can be worthwhile when measured benefits justify it, but document the fallback limitation and the cost of migration.

## Routing, quotas, fallback, caching and policy

Routing first filters by tenant/data placement, task quality and required features, then considers health, capacity, cost and latency. Quotas can include concurrency permits, requests, tokens and tenant spend. These are different resources with different accounting rules. Reserve estimated usage atomically and release concurrency when the attempt ends. Settle financial/token allowance against observed usage or a defined uncertain-use record rather than applying one refund rule to every exception.

If a provider explicitly rejects a request before processing under its documented contract, the gateway can release the unconsumed local reservation. A timeout or broken stream does not prove that processing never occurred. It may have produced tokens or incurred cost without a complete returned result. Record the uncertain usage and reconcile where possible. Provider rate limits are also not identical to the platform's financial budget; refunding local capacity does not reset the provider's own rolling limit.

The following pseudocode demonstrates that distinction for one attempt. `confirmed_unprocessed` must come from a verified adapter error classification, not a model assertion. Reservation and ledger services are durable/concurrency-safe application interfaces. The finally block releases only the concurrency permit. The caller chooses a qualified fallback within a total deadline; unrelated unexpected errors should not be hidden as routine provider failover.

```python
def gateway_attempt(request, target, adapter, quota, ledger):
    reservation = quota.reserve(request, target)
    if reservation is None:
        return {"status": "no_capacity"}
    try:
        response = adapter.call(target, request)
    except Exception as error:
        if adapter.confirmed_unprocessed(error):
            quota.release_unconsumed(reservation)
            ledger.record_rejected_attempt(request, target)
            return {"status": "rejected"}
        ledger.record_unknown_usage(request, target, reservation)
        if adapter.is_transient(error):
            return {"status": "uncertain_provider_failure"}
        raise
    else:
        ledger.settle_usage(request, target, response.usage)
        quota.settle_actual(reservation, response.usage)
        return {"status": "completed", "response": response}
    finally:
        quota.release_concurrency(reservation)
```

Cache policy also belongs at this boundary where model identity and data placement are known. Prefix-friendly request shaping can reuse approved processing. Exact/semantic response caches need the entitlement, correctness and freshness safeguards from Chapter 28. A gateway that serves a cached answer must still validate current scope. Redaction should occur before content reaches provider and telemetry destinations, with trusted classification and purpose checks rather than a generic regex claimed to remove all sensitive data.

## Managed APIs versus self-hosted serving

A managed API transfers much of serving operation to the provider. The organisation still owns identity integration, data contracts, quota planning, task evaluation and fallback policy. It gains access to the provider's supported models and operations without running those GPUs itself. Latency includes network, provider queueing and generation. Pricing and retention follow the actual contract, so do not infer data handling from an API-compatible interface or a general marketing label.

Self-hosting gives control over the environment, model artifact, serving configuration and data placement. It also requires GPUs or other supported accelerators, drivers, runtime security, scaling, model loading and on-call. Capacity costs continue while idle, and utilisation matters to economic comparison. Include staff, reliability headroom, energy/hosting and lifecycle costs where relevant rather than comparing only one GPU's raw hourly rate with a provider's output price.

Quality depends on the chosen model and task. Managed services can expose both proprietary and open-weight models; self-hosted models can be strong at specialised tasks and differ on complex reasoning. Do not present model size or ownership as a universal quality ordering. Evaluate routing, extraction, tool selection and high-risk slices separately. A common design uses qualified self-hosted models for narrow high-volume work while retaining other approved routes for tasks those models do not meet.

## How high-throughput serving works

Autoregressive generation commonly has a prefill phase and a decode phase. Prefill processes the prompt and prepares reusable intermediate state. Decode produces tokens incrementally using that state. Long prompts can make first-token latency large, while long outputs consume many decode steps. A single tokens-per-second number cannot describe both user experiences. Measure time to first token, inter-token latency and queueing under the prompt/output distributions the service actually expects.

The key/value cache, or KV cache, stores attention key/value tensors for tokens so each new token does not recompute all earlier work. For a simple dense cache, a rough storage estimate is two times layers times KV heads times head dimension times bytes per value times stored tokens, before other overhead and parallelism details. Model architecture and serving choices change the estimate. Weights, temporary buffers and other allocations also consume memory, so KV storage is not the only capacity constraint.

For a constructed model with 16 layers, 8 KV heads, head dimension 64 and two bytes per value, the estimate is 32 KiB per stored token. At 4,096 tokens that is 128 MiB of key/value storage for one request, excluding other allocations. This arithmetic illustrates why long contexts and many concurrent requests affect capacity; it is not a benchmark or specification of a named model. Use the actual architecture and engine measurements for planning.

PagedAttention, associated with vLLM, organises KV storage in fixed-size blocks and maps logical tokens to blocks instead of requiring one large contiguous allocation per request. This can reduce fragmentation and support useful sharing. Page/block metadata and eviction policy still matter. Prefix caching reuses eligible KV state for shared prefixes under the engine's supported hashing and isolation rules. SGLang is another serving system with prefix-reuse mechanisms; implementation details need version-specific review.

Continuous batching admits new requests and removes completed requests as generation progresses instead of holding a fixed batch until its longest member finishes. It improves utilisation for mixed lengths when capacity and scheduling allow. The scheduler must balance prefill, decode and fairness; a large arriving prompt can compete with interactive generation. Throughput improvement is workload-dependent, and keeping every seat occupied is not the same as meeting each user's latency objective.

Quantisation reduces the precision used for weights or caches, often reducing memory requirements. Throughput can improve, worsen or remain similar depending on kernels, hardware, batch sizes and other bottlenecks. Evaluate quality and latency on the target workload; lower-bit storage does not itself prove a faster service. Speculative decoding uses a draft process whose proposed tokens a target model verifies under a supported algorithm. Its benefit depends on acceptance and implementation overhead, so benchmark rather than assuming universal speedup.

Tensor parallelism divides model computations across devices, while pipeline parallelism divides stages. These techniques can fit larger models and change throughput, memory and communication cost. More devices introduce coordination and network constraints; they are not free capacity. Serving engines and platforms expose different supported combinations, so pin their configuration and test the actual deployment. A compatibility table or a model-fit calculation is the beginning of planning, not a substitute for load measurement.

## Scalable serving on Kubernetes

Serving platforms such as KServe and Ray Serve can coordinate deployment, routing and autoscaling around engines such as vLLM. Their supported versions and integration details evolve, so consult the pinned platform documentation. GPU requests, node pools, model storage and network paths need explicit configuration. Distinguish scaling the HTTP frontend from scaling loaded model replicas; the frontend may become ready quickly while the weights are still unavailable.

Autoscaling should consider queue/concurrency and the task's latency/capacity measurements. Loading weights can create a long cold start, so scale-to-zero is suitable only where that delay is acceptable. Warm capacity costs money but may protect interactive objectives. Reserve different priorities or pools for bulk evaluations and interactive generation if they compete. A queue of large batch jobs should not silently consume all decode capacity intended for incident response.

Load-test realistic distributions, not only identical short prompts. Vary prompt lengths, output bounds, arrival bursts and model routes, and record queue time, first-token latency, generation pace and failures. Locate the operating region that meets objectives with headroom. A rising latency curve may reflect memory pressure, compute saturation or queueing; label a hypothetical chart's assumptions rather than attributing every knee solely to KV exhaustion.

## Observability, cost and model lifecycle

Track model/server release, quantisation, request routing, time to first token, inter-token latency, tokens per second, queueing, batch size, cache use and device memory. Record autoscaler events and loading delay so latency incidents can be separated from generation bottlenecks. Cost comparisons should use utilisation-adjusted compute and total workload outcomes, including idle reliability headroom and unsuccessful work. An impressive peak throughput number says little about the cost of a sporadic interactive service.

Register model artifacts with source, licence, version, allowed use, integrity information and evaluation results. Open weights do not automatically mean unrestricted commercial terms or no attribution duty. Review fine-tuned and quantised derivatives under the relevant licence and governance process. Deploy model changes through canary/rollback, monitor them and retire obsolete artifacts. Security patching of serving software and dependencies remains an operating obligation even when model weights themselves do not change.

Shared prefix caching needs a privacy boundary. vLLM documents cache salting to isolate reuse across trust groups and reduce timing-based inference of cached content. Choose a scope appropriate to the tenant and data policy, and review other selected engines' mechanisms. A cached prefix can improve performance while exposing information about prior requests if sharing is uncontrolled. Restrict telemetry and provider access too; self-hosting alone does not solve every shared-service side channel.

## When to fine-tune or distil small models

Fine-tuning can improve a narrow, stable task such as classification, extraction format or a fixed tool-call contract when the team has enough reviewed training data and a strong evaluation set. It is rarely the first correction for missing tools, stale knowledge or broken approval logic. Requirements that change weekly may be easier to handle through instructions and retrieval. A specialised model can retain other abilities, so do not claim it becomes useless outside one form; measure any loss or transfer explicitly.

Distillation trains a smaller model using a larger model's outputs or other supervised signals under a defined task/data process. It can reduce serving cost or latency if quality remains adequate. The teacher's output is not automatically true, so review labels and keep held-out evaluation independent of training. Production data needs its purpose and privacy governance, and model/provider terms may constrain the use. Compare with prompt improvements, routing and retrieval before taking on training and retraining operations.

The workflow includes dataset versioning, training configuration, artifact registration, task-slice evaluation, deployment and monitoring. Retrain when the task or tool contract changes, and keep an approved previous artifact for rollback if compatible. A stable high-volume classifier can justify that investment; an open-ended research workflow with changing evidence may not. The economic decision includes the training/data pipeline and operations, not only the new model's per-token runtime cost.

## Avoiding provider lock-in

Own the internal model interface, tool schemas, state, memory and evaluation data. Keep vendor SDKs and response translation inside adapters. Test important prompts and contracts across qualified alternatives rather than waiting for an outage to discover incompatibility. Preserve supported snapshots and feature flags in the release manifest. A unique provider feature can be worthwhile, but record the soft dependency and what degraded behaviour is possible if the feature disappears.

Portability is a measured option, not a promise that every provider produces the same answer. Migrating changes quality, latency, usage and sometimes data placement. Run the evaluation and rollout process before switching, and preserve the ability to explain which service processed each run. The gateway makes that change more controllable; it does not remove the need for evidence or let a compatibility layer override a tenant's contract.
