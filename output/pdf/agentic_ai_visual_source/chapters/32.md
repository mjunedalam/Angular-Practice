# 32. LangGraph in Depth: Building Durable Agent Graphs

ShopAssist needs a refund path that a reviewer can follow without guessing what the model might do next. Gather the payment facts, assess eligibility, ask for approval when policy requires it, execute with an effect identifier, and verify the result. LangGraph makes that path explicit while still allowing model-directed investigation inside selected nodes. The important question is how the graph executes and resumes, not how attractive its drawing looks.

This chapter uses the LangGraph 1.2 release family as checked for the October 2026 edition. Exact patches and supporting packages must be pinned in your project. Code listings are compact teaching units, with domain-service contracts stated beside them. They do not constitute a complete payments or incident-response application. The [Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api) and [persistence documentation](https://docs.langchain.com/oss/python/langgraph/persistence) are the primary references for upgrades.

:::analogy The railway dispatch office
A dispatch office schedules stations to report, combines their reports under agreed rules, records the journey and authorizes the next movement. Some reports arrive together; a train can wait for clearance without occupying the office staff. A graph has the same separation between scheduled work, merged state, recorded progress and the next decision. Where it stops: software nodes are not literal trains, and restoring an old journey record cannot undo a payment, rollback or message already sent outside the graph.
:::

## How LangGraph thinks: nodes, channels and super-steps

A StateGraph builder describes nodes and edges over a state schema. A node reads state and returns the fields it changes rather than rewriting the entire record. Each field behaves like a channel carrying a value through execution. An edge schedules work after the current node completes. Compile the builder to obtain the executable graph; compilation is where persistence and other runtime dependencies are attached.

Execution advances in super-steps. Nodes scheduled together can run in parallel. Their updates merge according to the state fields' rules, then the graph schedules the next work. Sequential nodes occupy different super-steps. This is a synchronization model, not a wall-clock timetable: one node may take seconds, another may stream tokens, and neither must finish on a literal clock tick. Checkpoint persistence depends on the configured saver and durability mode.

## State and reducers

The state schema gives names and types to the record moving through the graph. A field without a reducer normally receives the new value in a sequential update. If parallel nodes write the same such field in one step, the graph cannot resolve that conflict automatically and raises an update error. Do not confuse sequential replacement with parallel last-writer-wins behavior. Evidence disappearing after an update and a concurrency error have different causes.

A reducer is a function that combines the current value with an update. List addition appends, but it also preserves duplicate entries. For evidence, use a reducer keyed by stable evidence IDs and decide what conflicting versions mean. For severity, define an explicit ordering rather than lexicographic string comparison. Pure reducers are easy to test: feed the same current state and update, then verify the same merged result without invoking a model.

```python
def merge_evidence(current, update):
    by_id = {item["id"]: item for item in current}
    for item in update:
        previous = by_id.get(item["id"])
        if previous is not None and previous != item:
            raise ValueError("conflicting evidence identity")
        by_id[item["id"]] = item
    return [by_id[key] for key in sorted(by_id)]
```

This reducer treats one evidence identity as immutable and gives deterministic ordering. A system allowing corrections should create a new version with a supersession link instead of silently changing the old entry. For chat histories, `add_messages` supports appending messages and updating matching message IDs. That is different from blindly concatenating a list. Choose the merge behavior because of the information's meaning, not because a convenient annotation appears in an example.

## Nodes, edges and routing

Use a static edge when the next step is fixed. Use a conditional edge when a separate function chooses the destination. Use a Command when a node both updates state and chooses where to go. ShopAssist's assessment can set the eligible amount and select approval or finish. Keep money in integer minor units with explicit currency; a graph field should not introduce ambiguous floating-point accounting.

Type annotations such as `Command[Literal[...]]` help static tooling and graph rendering. They do not implement a business authorization rule. Validate model-generated routes against a finite destination set before constructing a Command. Also avoid mixing a static outgoing edge with Command routing from the same node: both routes can run. An approval drawing is only meaningful when actual scheduling cannot activate an execution path around the policy check.

```python
def checked_route(proposed, allowed):
    if proposed not in allowed:
        raise ValueError("route outside declared choices")
    return proposed

def route_after_approval(state):
    decision = state["approval"]["decision"]
    if decision == "approve":
        return "execute"
    return "escalate"
```

The routing helper is a pure teaching example. The approval record it reads must have been produced by a service that validates authority and binding, not copied from an arbitrary model response. Test each destination, an unknown destination, rejection and expiry. In the dispatch office, a station's suggested next platform is information; clearance to move still belongs to the office's rules.

## Checkpointers, threads and state history

A checkpointer saves graph state under a thread ID, allowing a later invocation to continue that thread. InMemorySaver is useful for deterministic tests. SQLite can support local persistent demonstrations; a shared durable implementation such as PostgresSaver is more appropriate for independently restarting workers. Operate the database, schema setup, encryption and retention as part of the application. A saver object does not maintain those operational properties for you.

Inspect the current state to find its pending nodes and values. State history supports debugging from an earlier checkpoint, often called time travel. Replaying a checkpoint branches graph execution; it does not restore the external world to its old state. A replayed investigation may call changed data sources, and a replayed mutation must still use an authorized effect contract. Audit state edits because they change the evidence on which subsequent decisions rely.

Store immutable version information with the run: graph behavior version, tool contract versions, prompt packs and model configuration. When deploying a changed graph, decide whether paused threads continue with the old behavior or migrate under a tested procedure. Renaming a pending node can strand a run. A compatibility test should include a checkpoint produced by the prior release, not only a new invocation created after the upgrade.

## Human-in-the-loop with interrupt

`interrupt(payload)` pauses inside a node and exposes the payload to the caller. Resume using `Command(resume=value)` on the same authorized thread. The interrupted node begins again from its first line; at the relevant interrupt, the supplied value becomes the return value. It may restart more than twice when there are additional pauses or retries. Write repeatable code before the interrupt rather than relying on an exact counter of two executions.

The payload should identify the proposal, action, canonical argument hash, evidence, impact, rollback plan and expiry. An approval API checks the human's identity, role, tenant and decision. The resume value carries a reference to the resulting approval record. The node loads and validates that server-owned record. A button click or a matching hash alone cannot establish that the approver was entitled to authorize the action.

Keep ticket creation, email and payment effects out of the interrupted node unless they are explicitly idempotent. Even a separate execution node can be retried after an external effect completed but before its completion was recorded. Persist an intent and stable idempotency key first; use the downstream deduplication contract or reconcile an unknown outcome. Approval expiry needs an external timer or workflow service because a paused graph does not wake itself after thirty minutes.

## Fan-out and fan-in with Send

Send creates runtime-dependent work, such as one investigation per selected source. Each worker receives a bounded input: service, tenant scope, source and deadline. Their outputs combine through reducers. A planner can select metrics, logs and recent changes without always invoking every possible specialist. Cap the number of tasks before scheduling them, and enforce concurrency limits appropriate to the deployment and downstream quotas.

A joined result must describe failed or missing branches as well as successes. If logs time out while metrics return, the hypothesis node needs to know that it is reasoning from partial evidence. Do not turn three responses into an arbitrary completion-order list and then infer priority from that order. Record source IDs and sort for presentation separately. The analogy's railway carriages reconnect, but their arrival order does not determine which report is most trustworthy.

## Subgraphs: composing graphs

A compiled subgraph can become a parent node. Shared state fields pass information across the boundary; an adapter function can translate incompatible parent and child schemas. This gives investigations or verification procedures their own tests and versioned interface. The interface should state which evidence enters, what additions return, and how an interrupted child participates in the parent's checkpoint ownership.

Be careful with append reducers on both sides. A child may return its received list plus additions; the parent can append the received items again. Return a delta or use a reducer whose semantics safely deduplicate stable IDs. Test a nonempty input, not just the convenient empty list. A modular graph is useful when it reduces reasoning about a capability; it is not useful if its hidden state causes facts to duplicate or disappear.

## Tools and the ReAct loop

A basic tool loop has a model node and a tool node. The model returns a request; the tool node returns observations; routing either continues the loop or finishes. ToolNode provides dispatch plumbing for supported tool contracts. It does not decide business authorization, risk, approval, idempotency or audit retention. Those checks belong in the tool executor or in an explicit path before a mutating tool becomes callable.

Offer only capabilities permitted for the principal, and enforce permissions again at execution. Filtering reduces model mistakes but does not secure an alternate invocation path. Bound results before storing them in messages, preserve tool-call IDs, and return a result for every requested call. Use typed error outcomes that distinguish invalid arguments, denial, dependency failure and outcome unknown. The model can reconsider a plan without being allowed to reinterpret a denial as permission.

## Multi-agent graphs: supervisors and handoffs

The supervisor pattern uses a node that selects scoped specialists and receives their results. A handoff transfers control; returning a subtask result preserves the original owner. In a subgraph, Command can target the parent graph when that interface is deliberately supported. These choices affect accountability. Do not use a handoff merely because an agent object is available: first decide who owns the remaining budget and completion decision.

Record handoff counts, deadlines, evidence references and expected output schemas. A specialist cannot change the global incident plan simply by returning authoritative prose. The supervisor validates the structured result and applies it through the state rules. Add a repeated-handoff detector and a global step cap. If two specialists keep sending the same unresolved task back, escalate with the known evidence instead of financing an endless conversation.

## Long-term memory with stores

Checkpoints concern a thread's execution; a store holds application data across threads. User preferences, reviewed incident summaries and approved procedural knowledge can live in namespaced store records. Namespaces should include tenant and subject scope, with access checked independently of model-supplied identifiers. A key-value path is useful organization, but it is not a substitute for authorization.

The memory write gate validates source, purpose, sensitivity, retention and supersession rules. A record that looks like a preference but instructs the agent to skip approvals is rejected. Deletion must cover served records and derived indexes, with backup expiry and restore suppression handled under the documented retention policy. Memory can improve investigation, but current system-of-record facts and policy still govern an action. The permanent railway archive advises dispatch; it does not issue clearance.

## Reliability: retries, recursion limits and durability

A node retry policy handles selected failures with bounded attempts and backoff. Use it only when repetition is safe. For a mutation, the same logical effect key must reach the service on every attempt; a new key creates a new operation. Classify outcome unknown separately from a definite refusal. Never compensate an effect merely because its response was lost; first establish whether it occurred.

The recursion limit caps graph super-steps in an invocation. It is a coarse brake, not a cost or wall-clock budget, and it can restart across repeated invocations. Maintain cumulative application budgets in persisted state, and evaluate model routing by task rather than treating step counts as money limits. When a limit is reached, record a terminal or waiting reason and preserve any uncertain effect for reconciliation. A failed-safe run must not lose information needed by the human who takes over.

Durability modes include synchronous, asynchronous and exit persistence. Synchronous recording reduces the window before the next step but adds latency; exit-only persistence offers less protection during execution. Choose deliberately around effects and measure the overhead. Durable timers, reminders and escalation are a separate concern; combine the graph with an approval service or workflow engine when waits need scheduled actions. See the [durability reference](https://reference.langchain.com/python/langgraph/types/Durability).

## Streaming

Streaming can expose full values, partial node updates, model messages or custom progress events. Use updates for statements such as “metrics collected,” and model message chunks for user-facing text. Do not expose raw state merely because it is easy to stream. Private application fields, tool observations and intermediate approval metadata can contain information the user is not entitled to see.

The persisted run and application event log remain the source of truth. A disconnected client should reconnect by run identity and obtain current status rather than infer completion from its last token. Progress messages should distinguish proposing, waiting, executing and verifying. “Rollback requested” is not “rollback applied,” and neither is “service recovered.” Those labels help operators make decisions while the underlying graph continues asynchronously.

## Testing LangGraph graphs

Test reducers and routers as plain functions. Then use a scripted model to exercise tool requests and final answers through the compiled graph. GenericFakeChatModel supplies scripted messages; an adapter or small subclass is needed when the loop expects tool binding. Keep fake model behavior explicit so a test failure identifies application logic rather than a changing hosted model response.

A persistence test should launch a start process and a resume process with shared definitions and durable instrumentation. In-memory counters reset on restart, so they cannot prove combined execution counts. Use a fresh database and thread ID per test. Kill after intent persistence, while waiting, after downstream effect success and before local completion. Assert the provider's effect ledger, approval consumption and final state, not only the graph's final sentence.

## Observability and deployment

Instrument node scheduling, model calls, tools, policy decisions, interrupts and state updates with one correlation identity. LangSmith can provide graph-native inspection; OpenTelemetry can connect to the enterprise tracing system. Record versions and evidence locators, redact before export, and retain an independent audit log for approvals and effects. Sampled traces cannot be the only proof that a payment was authorized.

Deploy compiled graphs inside your services or evaluate managed/self-hosted platform offerings. In either case, define queue ownership, worker concurrency, restart behavior, checkpoint access and migration. Operators need to locate a waiting run, inspect a denial, reconcile an unknown effect and disable mutations without stopping investigation. A production deployment is the graph plus these operating contracts, not merely a web endpoint calling `invoke()`.

## Build it: the AegisOps commander as a LangGraph graph

AegisOps triages an incident, selects an investigation subgraph, develops and tests hypotheses, proposes a remediation, passes deterministic policy, executes and verifies. Use evidence-ID reducers for findings and a separate attempt counter for bounded replanning. The proposal remains immutable after approval. A new plan receives a new identity and approval requirement; a failed verification is evidence, not permission to replay a broad action without review.

```python
def decide_execution(proposal, approval_record, policy):
    risk = policy.risk(proposal)
    if risk >= 5:
        return "escalate", {"reason": "blocked_action"}
    if risk <= 2:
        return "execute", {"decision": "policy_allowed"}
    if risk == 3 and policy.runbook_allows(proposal):
        return "execute", {"decision": "runbook_allowed"}
    validated = policy.validate_approval(
        proposal, approval_record,
        required_approvers=2 if risk == 4 else 1,
    )
    if not validated.ok:
        return "escalate", {"reason": validated.reason}
    return "execute", validated.approval_record
```

This policy sketch exposes the intended branches rather than hiding them in the model. `validate_approval` must check action identity, canonical hash, tenant, roles, distinct approvers, expiry and consumption. Successful human approval preserves the validated record; it is never overwritten with “auto.” The execution adapter then atomically checks live preconditions at the downstream mutation boundary, uses the persisted effect key, and records applied, rejected or unknown outcome.

## Failure modes

Duplicate effects usually point to a repeatable-execution problem, not an unusually creative model. Lost waiting runs point to persistence or thread ownership. Duplicate evidence points to parent/child merge semantics. Expensive runs within a recursion limit point to missing cumulative budgets. Unapproved actions point to routing and authorization boundaries. Investigate the violated contract before adding another prompt warning; a warning cannot repair an incorrectly scheduled node.

Keep these diagnoses visible in tests. Unknown route, new tool, stale approval, missing telemetry and changed graph version should each produce a specific outcome. The operator can then distinguish a legitimate escalation from a framework exception. Clear terminal reasons also improve evaluation: a safely escalated dependency outage is not the same failure as a run that claims completion without verifying the service.

## Interview drills

Explain one super-step using a state field and its reducer, then explain why parallel writes need a merge rule. For interruption, say that the node restarts and describe the effect-safe placement. For persistence, distinguish checkpoint, governed store and application audit. For deployment, describe how a paused run survives both a process restart and a code upgrade. These concrete transitions demonstrate understanding better than memorizing API names.

## Key takeaways

LangGraph supplies explicit scheduling, state merging and persistence interfaces. The application supplies valid routes, governed memory, authorization, effect identity and outcome verification. Checkpoints preserve a record; they do not rewind the world. An approval pause is useful only when the human decision is bound and validated. Design the graph as the railway office's schedule, then prove that real-world movement still obeys the clearance rules.
