# 7. Agent State & Checkpointing

A run is easy to continue while everything lives in one process. The difficult moment arrives when a worker disappears, approval comes tomorrow or another worker picks up the same task. The replacement needs to know what was accepted, what occurred and what remains uncertain. Conversation text alone rarely answers those questions precisely. State gives the run an explicit operating record, and checkpointing makes that record available beyond one process lifetime.

ShopAssist's critical example is a refund submitted just before a crash. If the runtime remembers only "the model wanted a refund," it may repeat the write. If it records the exact accepted intent and stable effect identity before submission, a new worker can reconcile that operation. We will build the records and transition rules that make this continuation understandable, then examine concurrency and schema changes that complicate it.

:::analogy A change of shift in a hospital
When a nurse's shift ends, the incoming nurse needs the current chart: medication already given, tests pending, observations, limits and the next action. A brief consultation note is useful but is not the whole chart, and the patient's long-term history serves another purpose. The new nurse reads the handover and checks current instruments before continuing. Where it stops: a written chart cannot by itself prevent two nurses acting simultaneously. Software needs ownership, transactional updates and external effect contracts as well as a good handover record.
:::

## State, context and memory

State records the current execution: goal, progress, accepted observations, pending work, usage and outcomes. Context is the selected view sent to a model for one decision. Memory is governed information retained across runs, such as a customer's preferred language or a previous incident. These records differ in lifetime and ownership. A model may see only a summary, while the authoritative run record retains the exact approved payment and amount needed for execution.

Context should be rebuildable from retained records and source references. Otherwise a restart might reconstruct a different story from a lossy prompt summary. State can point to large transcripts or payloads rather than copy them into every checkpoint. The referenced artifacts need their own durability and access contract. A pointer to a deleted temporary file does not make the state complete merely because the checkpoint itself was saved successfully.

Memory does not override the system of record. A prior note saying an order is refundable may be stale; the payment service supplies current captured and refunded amounts. State records what was observed at a time, not eternal truth about the outside world. On resume, re-fetch volatile facts before a consequential operation. Keeping these distinctions explicit prevents a summary or remembered preference from silently becoming transaction authority.

## What belongs in run state

Begin with identity: run, tenant, authenticated principal and released agent definition. Add the goal and acceptance criteria, plan steps with statuses, current position and accepted observations. Every observation needs a source, time and payload reference or bounded data. Keep pending approvals distinct from executed effects. The approval record identifies the exact proposal and its conditions; the effect record identifies accepted intent, submission and confirmed or uncertain result.

Budget state needs both configuration and consumption. Persist model-turn and tool-call limits, used amounts, token/cost records and deadline semantics. An absolute deadline should remain the same after restart. An active-time budget needs accumulated consumption and a new interval start, not an unconditional reset that erases earlier work. Record terminal reason and acceptance evidence. Model, instruction, tool and schema versions explain which contracts produced the decision.

Large data can live elsewhere, but critical exact fields should not depend on prose extraction during resume. A payment identifier, currency, amount and approved-effect hash are structured fields. A text summary explains them to people and models. This separation keeps checkpoints small without making their correctness depend on another generation. The handover test is simple: can a different authorized worker determine what may happen next using the state and its valid references?

```python
from dataclasses import dataclass, field

@dataclass
class RunRecord:
    run_id: str
    tenant: str
    principal: str
    agent_release: str
    goal: str
    status: str = "running"
    schema_version: int = 1
    last_event: int = 0
    deadline_at: float = 0.0
    usage: dict = field(default_factory=dict)
    accepted_intents: dict = field(default_factory=dict)
    observations: list = field(default_factory=list)
    pending_approvals: dict = field(default_factory=dict)
    terminal_reason: str | None = None
```

This teaching record names responsibilities, not a complete storage API. Real fields should have typed schemas and validation for their domain. A bare dictionary can be useful in a small example only when the reader knows which invariants its owning component enforces. Chapter 11 uses a compact explicit JSON contract with deterministic checks; a larger production system can use Pydantic or equivalent validation and more detailed typed records.

## Typed state, reducers and event-sourced updates

A reducer applies a validated event to a previous state and produces the next state. It centralizes update rules, so a model does not directly set approved or completed. Events can describe model response accounting, accepted tool intent, observed result, approval requested or run outcome. Verify the event's shape and legal meaning before applying it. Copy-on-update or another controlled mutation discipline makes the behavior testable and avoids undocumented edits scattered across hooks.

Event sourcing persists events as the authoritative history and derives current state by folding them through reducers. Snapshots speed startup, but their event position must be retained so replay begins at the correct offset. The event stream can reconstruct what the application knew at an earlier position, provided the reducer/schema versions and referenced artifacts are available. It cannot recreate a vanished external system or make a repeated side effect safe without a separate effect contract.

Not every application needs full event sourcing. A transactional state document plus an append-only audit stream may be sufficient when their consistency is explicit. Avoid using the term event sourcing merely because a list of log messages exists. Decide which record is authoritative, how updates are atomic and how conflicting positions are handled. The chart must have one trustworthy current version even when several derived dashboards display it.

## State transitions and graph state

Encode legal transitions rather than assigning strings anywhere. An approval resolution must inspect the decision, exact proposal binding, expiry and remaining pending work. Rejecting one approval does not mean the run may execute its financial effect. Resolving one of several approvals does not automatically make every pending action runnable. A duplicate or late signal must not restart a terminal run. These rules belong to the controller's transition policy and should appear in reducer tests.

```python
ALLOWED = {
    "running": {"waiting", "paused", "completed", "incomplete",
                "denied", "cancelled", "unknown", "limited"},
    "waiting": {"running", "denied", "cancelled", "expired"},
    "paused": {"running", "cancelled"},
}

def change_status(record, target):
    if target not in ALLOWED.get(record.status, set()):
        raise ValueError(f"illegal: {record.status} -> {target}")
    record.status = target
```

This helper enforces only the outer lifecycle. The caller must validate transition preconditions, and a reducer should invoke it rather than bypass it. In graph orchestration, nodes return typed updates and reducers define how fields merge: append observations, replace a scalar with version checks or combine sets. Parallel updates that conflict on an approved effect need a conflict rule, not whichever node finished last. Chapter 16 develops graph-level scheduling around these state contracts.

## Persistence, serialisation, checkpointing and resume

A checkpoint is a durable execution record at a known position. Save before an irreversible effect, including its accepted identity, and save after obtaining the result. Save before entering a wait and after advancing a completed step. Use a transaction or another proven atomic storage operation so a crash cannot leave a partially written document. JSON with explicit schemas is easier to inspect and migrate than serialized live clients or arbitrary executable object formats.

The crucial crash window lies between external success and local result persistence. On restart, the saved intent says submission may have happened but no confirmed result is available. Query the service's authoritative operation status, or retry with the same key only under its documented idempotency contract. If neither resolves the outcome, keep unknown and hand off. A local ledger prevents casual repetition; it does not prove what happened outside the process.

Storage choices reflect the contract. PostgreSQL can provide transactional records and queryable events. Redis is useful for hot state or coordination when durability and lease behavior are understood; it should not accidentally become the only copy of long-lived financial work. Object storage suits large retained payloads. A durable workflow engine can manage waits, timers and retries, but its determinism and activity contracts require deliberate integration. Choose by recovery requirements rather than convenience alone.

## Handoff records: resuming long-running work across sessions

A human-readable handoff complements machine state. It explains the task, completed work, acceptance checks, unresolved issues, retained artifacts and next action. This is valuable for a coding agent continuing tomorrow or an AegisOps investigation handed to another shift. State preserves exact execution facts; the handoff helps a new reader find them. Do not let the summary invent success or replace source evidence with a polished narrative.

On resume, read the record and inspect the current environment. Repository files, tickets, service status and policy releases may have changed while the task waited. Verify required dependencies and check results where they may have become stale. Reconcile uncertain effects before resubmitting work. Preserve source locators for details omitted from the handoff, and update the record when the next session ends. A summary without retrievable evidence is a fragile invitation to reconstruct facts from memory.

## Concurrency, conflicts and shared state

Two workers may claim the same run after a timeout or partition. A lease can express ownership, but a TTL alone does not stop a paused old worker from waking after expiration. A fencing token identifies the ownership epoch; state writes and downstream mutations reject stale epochs where that enforcement is supported. The important protection is at the system performing the effect, not only at the record that may be saved afterward.

Optimistic concurrency detects stale state updates by requiring the version the worker read. If another worker already advanced the record, the update affects no row and the caller reloads or aborts. This prevents lost updates; by itself it does not undo a side effect submitted before the rejected save. Combine state concurrency with single-writer execution and effect-level protection. The techniques solve related but different problems, so their limits belong in the design review.

External messages and approval signals should enter an inbox with their own identifiers rather than edit run state unpredictably. The controller consumes them at defined boundaries, checking binding and duplicate delivery. For shared state across agents, define field-level merge or conflict behavior and keep ownership of financial/destructive writes explicit. Append-only observations often combine safely; competing proposals to change one resource require coordination rather than ordinary list merging.

## State schema evolution

A run may outlive a deployment. Include a schema version, support known migrations and reject an unsupported future version before interpreting fields. Prefer additive changes with meaningful defaults; do not reinterpret a field's units or purpose in place. Keep agent/tool definitions pinned unless an explicit migration updates the operating contract. Store timestamps consistently and separate observation time from effective policy time where both matter.

```python
def upgrade_record(raw, current, migrations):
    version = raw.get("schema_version", 1)
    if version > current:
        raise ValueError("state comes from a newer schema")
    while version < current:
        if version not in migrations:
            raise ValueError("unsupported migration path")
        raw = migrations[version](raw)
        next_version = raw["schema_version"]
        if next_version != version + 1:
            raise ValueError("migration did not advance once")
        version = next_version
    return raw
```

Test migrations on retained representative documents with sensitive values replaced appropriately. Include pending approval and unknown-effect records, not only completed runs. A migration that drops an effect key or silently changes an amount unit can defeat recovery while passing a simple parse check. The migrated record should retain its accepted business meaning and explain the code/schema version now responsible for continuing it.

## Failure modes

State kept only in local variables disappears on restart. Huge checkpoints make writes slow and encourage skipped persistence. Unvalidated generated statuses create impossible states. Missing intent records hide uncertain effects. Concurrent writers cause lost progress or duplicate work. Unversioned schemas break resumed runs after deployment. These failures are ordinary distributed-systems problems intensified by model variability; solve their mechanisms before tuning the prompt that happens to expose them.

## Interview drills

Explain state, context and memory through one admission-style handover or one refund run. For crash recovery, identify the accepted intent, external authority and checkpoint position. For concurrency, distinguish version checks from fencing at the effect. For migrations, describe how unknown newer schemas are rejected and how pending work retains its meaning. A strong answer names what survives and what must be revalidated, not simply which database stores a JSON object.

## Key takeaways

Typed, versioned state gives a run a trustworthy current chart. Context is its per-call view, and a handoff is its human explanation. Record intent before effects and preserve unknown outcomes until authoritative reconciliation resolves them. Concurrency and migration controls protect that record across workers and deployments. The resulting recovery guarantee is only as strong as the external effect contract that the runtime uses.
