# 18. Human-in-the-Loop, Approval & Escalation

AegisOps has evidence that a recent checkout deployment caused a latency incident. It can propose a rollback, but the proposal affects production users and may interact with changes made since the investigation began. Asking a human to click an unlabeled approve button is not enough. The person needs to know what will happen, why it is justified and what exact operation their decision authorises. The runtime must then preserve that relationship until execution.

Human-in-the-loop design assigns people useful roles at specific decision boundaries. Some people clarify a missing fact, some approve a consequential operation and others take ownership when automation cannot proceed. This chapter connects those roles to risk policy, durable waits, exact proposal binding, current preconditions and feedback. The goal is effective oversight without turning every ordinary read into a confirmation request that eventually trains people to stop paying attention.

:::analogy A cheque awaiting a second signature
A prepared cheque records the payee and amount. It can wait in a tray until an entitled signer decides, without an employee standing beside it all afternoon. If someone changes the payee or amount, the old signature does not authorise the new cheque. An agent proposal, durable approval request and validated resume follow that pattern. Where it stops: a signature does not prove the payment is sensible or that its preconditions still hold. Software must check decision identity, current authority and resource state before executing.
:::

## Where humans belong

An approver decides whether a proposed action may happen. A clarifier supplies a missing fact, such as which of two orders the customer means. An escalation owner takes over a task that the agent cannot or must not continue. A reviewer examines sampled completed runs, while a corrector edits a draft. A policy owner changes future rules through a governed process. These roles have different interfaces, response times and authority; sending all of them to one vague human queue hides those differences.

Place human decisions where judgement changes the outcome. High-impact, irreversible, unusual or ambiguous operations may need an approval or escalation. Routine low-impact work can proceed under explicit policy, with sampling for later review. The decision should follow action class and context rather than the model's confidence alone. A model can sound certain about an unsafe action and uncertain about a harmless read. Confidence may be one signal, but it cannot determine the final permission boundary.

Oversight also costs attention. If every order lookup requests approval, reviewers may learn to click quickly without examining evidence. Conversely, allowing every financial operation automatically can expose customers to a mistake or manipulated request. Define which classes need fresh approval, which are covered by tested pre-approved rules and which are blocked outright. Measure whether the resulting queue lets approvers make informed decisions within the task's useful time window.

## Approval interrupts and resumable waits

An approval request is a durable record, not a temporary yes/no variable. It contains the run and proposal identifiers, exact action and arguments, evidence, expected impact, preconditions, required approvers and expiry. Persist the request and the run's continuation before releasing the worker. A notification points a person to that record; it is not the record itself. If chat delivery fails, the pending request should remain visible in the approval service.

A decision records who acted, which proposal they reviewed, the outcome, time and any explanation. Rejection, expiry and approval-with-modification are separate outcomes. A modification creates a new proposal with a new digest; it should not silently reuse the original approval. When the decision arrives, the resume service checks the record through an authenticated channel, validates the current approver entitlement and signals the waiting run. A worker on another host can then continue from durable state.

The exact proposal needs a canonical digest. Include the action, normalised arguments and relevant resource/version context. Hashing two stored hash fields against one another does not prove the current arguments are unchanged. Recompute the digest from the immutable proposal snapshot at validation time. Treat external identifiers and canonicalisation rules carefully: different dictionary key order should not create a new operation, while a different amount, recipient or environment must create one.

The following compact example illustrates binding and decision checks. Proposal and decision records are trusted immutable objects loaded from the service. The policy interface must verify approver roles, separation of duties and the required count of distinct approvers for this action. It is explicitly called rather than hidden in a comment. This function prepares an authorised operation; a downstream conditional executor still protects the resource-state check.

```python
import hashlib
import json

def proposal_digest(proposal):
    payload = {
        "action": proposal.action,
        "args": proposal.args,
        "resource_version": proposal.resource_version,
    }
    encoded = json.dumps(payload, sort_keys=True,
                         separators=(",", ":"), allow_nan=False)
    return hashlib.sha256(encoded.encode()).hexdigest()
```

```python
def validate_decision(proposal, decision, policy, now):
    if decision.outcome != "approved":
        return {"status": decision.outcome}
    if decision.proposal_id != proposal.id:
        raise ValueError("wrong proposal")
    if decision.run_id != proposal.run_id:
        raise ValueError("wrong run")
    digest = proposal_digest(proposal)
    if digest != proposal.digest or digest != decision.digest:
        raise ValueError("proposal binding mismatch")
    if now >= proposal.expires_at:
        return {"status": "expired"}
    policy.require_entitled_approvers(proposal, decision)
    return {"status": "authorised",
            "operation_id": proposal.operation_id}
```

Precondition re-validation checks that the facts authorising the action remain current. After validation, execute against the approved resource version or equivalent atomic precondition. A read of current state followed by an unconditional write has a race window: another actor can change the order or deployment between the two calls. An API that supports a version check, conditional update or transactional constraint can close that window. If the downstream system cannot enforce the required condition, choose a safer operation or reconciliation process rather than claiming that the local check guarantees freshness.

Idempotency addresses a different problem. The approved logical operation has one stable identity, reused after an uncertain response or worker restart. A downstream deduplication contract prevents repeating that same operation. It does not make a stale proposal appropriate, authorise a changed action or substitute for checking the decision outcome. Freshness, permission and duplicate prevention are separate conditions. Keeping them separate helps both the implementation and its tests identify which condition failed.

## Risk-based approval policies

A risk policy maps a proposed action and its context to a required decision. Useful inputs include side-effect class, amount, environment, affected resources, reversibility and anomaly signals. Define the policy in deterministic code or a policy engine, version it and test both allowed and denied cases. A model can extract facts or suggest that a request is unusual, but the final mapping must remain outside the model's authority.

For ShopAssist, ordinary order-status reads might proceed automatically. A low-value refund could proceed under a reviewed rule that checks eligibility, amount and aggregate refunded total. Larger or exceptional refunds might require one or two entitled approvers. Destructive production changes can be blocked or escalated when no approved recovery path exists. These are examples of policy structure, not universal financial thresholds. The service owner must define the actual limits and regulatory obligations.

Pre-approved runbooks are standing authorisations under explicit conditions. AegisOps might restart one stateless pod only when enough healthy replicas remain, the operation targets an approved service and no conflicting change is underway. The runtime evaluates those conditions at execution time. A runbook title or a model's claim that the action is routine is insufficient. If any required condition fails, the system returns to an approval or escalation path rather than weakening the check to finish the task.

A risk score is a compact value computed from the action's risk features and used to select an approval rule. It can help organise policy, but a single number loses detail: two proposals can receive the same score for different reasons and need different approvers. Retain the contributing features, policy version and resulting requirement in the request. Deterministic does not mean correct. Test the rule, review autonomy increases and never lower a safety requirement merely because budget or reviewer time is scarce.

## Escalation, override, rejection and correction

Escalation is a designed outcome. The receiving human needs the goal, known facts, evidence, attempted steps, blocked proposal and reason the agent stopped. Without that package, the person repeats the investigation and the automation saves little effort. Record the new owner and what the agent may still do. An agent that has escalated a financial dispute should not continue issuing alternative mutations while a human handles the case.

Rejection can lead to a revised proposal, a factual explanation or closure, depending on the reason. Feed the reason back as an observation, not as an instruction to evade the policy. Approval-with-change creates a new reviewed proposal. A manual override is an external action the agent must observe and reconcile with its state. If an operator already rolled back the deployment, the pending rollback should become stale rather than executing simply because its original decision later arrives.

Corrections to drafts have less authority than policy changes. A reviewer may rewrite a customer reply without changing which refunds are eligible. Preserve that distinction in event types and interfaces. Otherwise a sentence such as “next time refund immediately” can become an accidental permanent rule when the intent was only to repair one response. The system should route feedback through the reviewed improvement process instead of treating every human utterance as a global permission update.

## Approval UX: evidence for an informed decision

An approval card should lead with the concrete change. “Roll back checkout-api from release 5.14 to 5.13 in production” is clearer than “call rollback tool.” Show the exact parameters or configuration diff beside the plain-language explanation. The approver should be able to identify the service, environment and target without interpreting a long transcript or reconstructing tool arguments. Short does not mean vague; precise information prevents accidental approval of a different action.

Explain why the action is proposed through links to relevant evidence. AegisOps might show when latency rose, which release preceded it and which alternative causes were checked. Separate observations from hypotheses. A temporal association is evidence to investigate, not proof of causation. Include missing evidence and counterarguments so the card does not persuade by omitting uncertainty. The person needs a decision aid, not a sales pitch written to maximise approval rate.

Describe expected impact, affected users, reversibility and the verification plan. If rollback can itself fail, say so. “Undo” may mean a compensating operation rather than restoration of the exact prior world. Show alternatives considered and why they were rejected, along with the deadline and what happens if no one decides. When the proposal changes, the interface must make the change visible and obtain the required new decision rather than preserving an old approve button.

Track approval quality, not merely speed. Useful measurements include decision time by action class, rejection reasons, subsequent incidents and sampled review of whether the decision matched the evidence. A high approval rate can reflect good proposals or fatigue. A comment count is a signal, not a universal quality metric; some correct routine approvals need no prose. Investigate patterns using actual outcomes rather than inventing a benchmark curve for how quickly approvers ought to respond.

## Human feedback for evaluation and improvement

Every approval, rejection, edit and escalation can teach the team something about system quality. Capture the signal with its context: which proposal, evidence, policy and model version produced it. Rejection with a structured reason can reveal weak proposal quality or an overly broad tool. Draft edits can become style or factuality evaluation cases. Escalation patterns may expose missing knowledge or an interface that repeatedly asks people to supply the same facts.

Feedback is not automatically ground truth. Reviewers can disagree, misunderstand evidence or express preferences that apply only to one customer. Evaluate the quality of labels and protect sensitive data before placing production examples in a dataset. Changes to prompts, knowledge, risk policy or tool scope should pass through their ordinary review and release process. Writing a correction directly into long-term memory can overgeneralise a local decision and make a new injection channel.

## SLAs, expiry and reassignment

An approval service needs an owner and a time policy. Use group queues rather than a single person's availability where appropriate. Define reminders, reassignment and escalation before expiry, and choose a safe default when the request expires. Silent execution after a deadline defeats the purpose of the gate. Time policy should reflect the action's urgency: a proposed incident rollback may have a shorter useful lifetime than a customer draft awaiting review.

Separation of duties depends on verified identities, not name strings copied into model context. The requester or the user whose action needs independent review must not supply the required second approval. A two-person rule needs two distinct entitled principals; two clicks from one person are not two reviewers. Re-check role membership if the policy requires current entitlement. A person may leave a privileged group while a request remains pending, and old queue assignment should not grant continuing authority.

## Audit trails, accountability and failure modes

Record the proposal, decision and observed execution as separate events. Link them by run ID, proposal ID, operation ID and trace context, and retain exact hashes and policy versions. The audit should answer who requested the action, what evidence supported it, which entitled people decided, what arguments actually executed and what happened afterward. Store it under appropriate access control and tamper-evident protection rather than mixing sensitive decision records into unrestricted operational logs.

Test failure paths as deliberately as approval success. Reject a matching proposal, expire it during a wait, change the resource version before execution, alter arguments after approval and restart the worker after the downstream effect. The expected result differs for each fault. Rejection and expiry produce no mutation; stale facts require reconciliation; an uncertain response requires same-operation recovery. A final answer saying “handled safely” is not a substitute for proving the executor count and external state.
