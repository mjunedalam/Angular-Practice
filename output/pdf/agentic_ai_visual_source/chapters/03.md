# 3. Reasoning & Control Patterns

A tool-using model can be arranged in several ways. It can choose one route, choose every next operation, make a plan for an executor or review an answer before release. These arrangements determine where judgment enters the process and how often the application pays for it. The names are useful only when they make those decisions clearer. This chapter compares patterns as control flow, using the same ShopAssist task so differences remain concrete.

Consider a customer asking whether two captured payments represent a duplicate charge. Some work is predictable: the order and payments must be read, eligibility must be checked and any refund must pass policy. Other work may depend on discovery: a payment record could be missing, a policy may contain an exception or the customer's explanation may be ambiguous. We want judgment at those uncertain points without making the entire process an open-ended investigation.

:::analogy The editor organizing a reporting desk
An editor can assign a reporter to one specialist desk, approve an outline before research, let the reporter follow each new lead or ask another editor to verify the final story. Several reporters can cover independent parts and return notes. These are different ways of organizing the same work, not a ladder from weak journalism to strong journalism. Where it stops: a software critic may share the generator's errors, and an agent's evidence and permissions require explicit machine-enforced contracts. A second opinion is not independent merely because it comes from another model call.
:::

## The pattern landscape

A deterministic workflow fixes sequencing and known branches. A router chooses among predefined handlers. A plan-and-execute design makes a reviewable outline before execution. A ReAct-style loop chooses the next action using the latest observation. Reflection adds critique and revision. Parallel workers divide independent work; a hierarchy introduces delegation and coordination. These mechanisms can be combined, and their presence does not identify one universally superior architecture.

Separate two questions: how often does the model choose the next step, and how is work organized or checked? A router makes one sequencing choice, while a ReAct loop makes many. Reflection may operate inside a fully fixed workflow. A supervisor may delegate deterministic jobs rather than autonomous subagents. Drawing all these patterns on one autonomy scale obscures those distinctions. Describe the actual model calls and their authority instead of assuming the pattern name answers both questions.

## ReAct: the tool-use loop

ReAct is commonly used to describe alternating reasoning, action and observation. The original research expressed thoughts and actions explicitly. A modern tool loop can use native tool requests and short checkable justifications instead of printing private internal reasoning. What matters for control flow is feedback: the model chooses an operation, the runtime executes an accepted request and the returned observation changes the next decision.

ShopAssist first searches the duplicate-charge policy. The policy says captured duplicates are eligible within a stated window. The model then asks for the order's payment records and learns that two captures occurred two seconds apart. It can now explain eligibility, or propose another lookup if one capture has already been refunded. A fixed plan need not guess those facts, but it must include branches for them. ReAct makes discovering such branches part of the ongoing decision process.

Its strength is adaptation; its cost is repeated calls and less predictable trajectories. A model may search several nearly identical phrasings or alternate between tools without improving the evidence. Place a step allowance, a total cost contract and progress detection around the loop. When progress stops, do not force a confident answer merely to terminate. Check whether existing evidence meets the acceptance criteria; otherwise return incomplete or insufficient_evidence with the useful records collected so far.

The following complete teaching function receives a checked executor and a verifier. These interfaces are intentional: policy and completion are not hidden inside model behavior. The result envelope stays valid JSON because bounding happens inside the executor's fields before serialization. A production loop additionally needs durable state, cancellation, provider status handling and per-operation deadlines; Chapter 11 provides a working small version of those boundaries.

```python
import json

def react(model, messages, tools, execute, verify, turns=8):
    history = list(messages)
    for _ in range(turns):
        reply = model.generate(history, tools)
        history.append(reply.message)
        if not reply.calls:
            return verify(reply.text, history)
        for call in reply.calls:
            result = execute(call)
            history.append({
                "role": "tool", "tool_call_id": call.id,
                "content": json.dumps(result),
            })
            if result.get("status") == "waiting":
                return {"status": "waiting", "history": history}
    return {"status": "limit", "history": history}
```

## Routers: cheap, reliable specialisation

A router makes a structured classification: order_status, refund, product_question or escalate. Each route leads to a handler with an appropriate capability set and policy. An order-status workflow can be inexpensive and deterministic after routing. A refund handler can require approval, and a product handler can retrieve catalog passages. Separating them reduces tool ambiguity and prevents unrelated capabilities from appearing in every request.

Include an escape path for unsupported or ambiguous inputs. If a customer reports both an account takeover and a refund, the router should not confidently place the entire request into an ordinary refund workflow. Evaluate per-route precision and recall on representative labeled requests, including mixed intents and unfamiliar language. A small model is a candidate, not a guarantee of lower total cost: misrouting can consume downstream work and create harmful promises.

A generated confidence score may help define a routing feature, but an arbitrary threshold such as 0.6 is not calibrated reliability. Study confidence against actual errors and compare it with deterministic signals, disagreement or missing required information. The escape path contains uncertainty; it does not excuse careless classification. Measure how often it is used and whether its handler can safely resolve the request, rather than declaring every escalation a successful route.

## Plan-and-execute

A plan makes intended work visible before actions begin. Use short steps with stable identifiers, allowed actions, dependencies and reasons. A plan for ShopAssist might fetch the order, inspect captures, evaluate refund eligibility, propose review and notify the customer after verified execution. The deterministic executor checks that identifiers are unique, dependencies exist, the graph is acyclic and every action fits the task's capabilities. A fluent plan is still untrusted proposed control flow.

References between steps need typed resolution. If step 3 needs the payment identifier returned by step 2, do not let a generated string silently become an arbitrary lookup into runtime objects. Define permitted references and validate their types before execution. Resolve them only after the dependency produced an accepted result. Missing or failed dependencies should trigger an explicit branch rather than allowing later work to continue with empty or guessed values.

Planning is useful when reviewability and progress tracking outweigh the larger initial call. Its weakness is staleness. An order may already have a refund, a tool can fail or a new policy passage may invalidate the amount calculation. Replan remaining work using the original goal, completed effects and the surprise. Preserve completed action identities; replanning does not make earlier work disappear. Bound the number of replans and require renewed approval if the proposed financial effect changes.

A useful hybrid has a short outer plan with a small ReAct loop inside each uncertain step. The plan supplies a reviewable direction, while each local loop can search or diagnose within its own allowance. Avoid writing an eight-step outline merely to wrap eight unrestricted agents. Nested budgets must compose into a run-level budget, and the supervisor must know whether a local step completed, exhausted its allowance or returned uncertainty.

## Reflection, critics and evaluator-optimizer loops

Reflection asks for critique followed by revision. An evaluator-optimizer makes the loop explicit: generate, evaluate against a rubric and revise until accepted or the allowance ends. The evaluator is most useful when it brings a check the generator did not already perform. For a refund explanation, that could mean opening the cited policy version or comparing amounts with the payment record. For a code change, it could mean executing the relevant tests.

A critic reading only the same draft with the same unsupported assumptions can rubber-stamp an error or invent objections. Explicit criteria improve consistency, but model scoring remains an estimate. Define the output as accepted, rejected or unverified and retain the reasons. If the final revision has not been evaluated, do not return it in the same shape as an accepted draft. Return a result containing the text and its verification status so downstream code cannot accidentally promote it.

Deterministic checks should come first where they are sufficient. A parser can check a schema, and a business service can verify a refund cap more directly than a second model. Model critique may still help with coverage, relevance and clarity. Measure its incremental benefit on the same cases with and without reflection. Extra calls are justified by observable improvement or reduced harm, not by the reassuring appearance of a second pass.

## Parallel workers, map-reduce and hierarchy

Parallelism helps when subtasks are independent. Several workers can extract relevant facts from separate documents and a reducer can synthesize their attributed results. It reduces wall-clock delay when capacity is available; it does not inherently reduce total token cost. Each worker may repeat instructions and request overhead, and the reducer adds another operation. Limit concurrency and aggregate the same run-level resource accounting across all workers.

Partial failure must survive reduction. If one of four sources could not be processed, the reducer needs both the missing source's identity and the resulting coverage gap. Do not simply drop exceptions and produce a confident complete answer from the remaining notes. Each partial result should retain source references and verification status. If the missing document could alter the answer, return partial or request another retrieval rather than claiming complete coverage.

Hierarchy adds a supervisor that assigns subgoals and combines outcomes. It is useful for meaningful specialization, such as an AegisOps metrics investigator and a change-history investigator. It also adds coordination, duplicated context and potential ownership conflicts. Keep writes under one owner, define handoff contracts and decide whether a worker is allowed to delegate further. Chapter 17 explores those boundaries; here, treat hierarchy as a decomposition choice rather than automatic sophistication.

## Comparing the patterns quantitatively

Run candidate patterns on the same task set and compare accepted outcomes, failure types, model calls, input/output tokens, cost and latency distributions. Include straightforward requests, ambiguous cases, tool failures and insufficient evidence. A pattern that wins on easy examples but fails expensive edge cases is not necessarily preferable. Measure p50 and tail latency separately, because replanning and reflection can produce a long tail even when average behavior looks attractive.

Synthetic diagrams can explain shape, but they are not performance evidence. If you draw example call counts, label them as assumptions and explain which operations were counted. For a measured comparison, publish the model versions, prompts, tool behavior, dataset and scoring procedure. That makes the tradeoff inspectable and repeatable. Model choice, retrieval quality and runtime limits can change the result, so keep the conclusions scoped to the evaluated workload.

## When a deterministic workflow beats an agent

Use a workflow when the route is known, the rules are stable or every branch must be inspectable before execution. ShopAssist can deterministically calculate refundable balance after the necessary facts arrive. It need not ask a model how to subtract already-refunded amounts. Classification or drafting may still use models while orchestration stays fixed. This concentrates probabilistic judgment where it contributes value and gives ordinary code responsibility for invariant calculation.

Use model-directed exploration when the next useful step depends on discoveries too varied to enumerate economically. An incident investigation often fits because new symptoms point to different sources. Even then, keep resource access, mutation policy, approval and verified outcomes deterministic around the investigation. The simplest sufficient pattern is a design result, not an ideological preference. A workflow and a bounded agent should be compared against the same goal and operating constraints.

## Failure modes

ReAct can wander; routers can misclassify; plans can become stale; critics can accept unsupported claims; parallel reduction can conceal missing sources; hierarchies can duplicate work or overwrite shared changes. Diagnose the pattern's actual failure before adding another layer. For example, reflection does not fix an unauthorized tool boundary, and more workers do not repair a missing source. Add a control that addresses the mechanism and verify its effect on representative cases.

## Interview drills

To compare ReAct with planning, explain the timing of sequencing decisions, the role of observations and the resulting cost and reviewability. To explain reflection, identify the evaluator's new evidence or rubric and its acceptance contract. To justify parallelism, show task independence, the concurrency cap and partial-result handling. A useful answer follows one concrete request through the chosen shape and names what happens when its strongest assumption fails.

## Key takeaways

Control patterns organize judgment. They do not replace the runtime's authority or guarantee a particular quality level. Choose decision frequency, planning, verification and decomposition separately, then combine only what the task needs. Preserve evidence and explicit statuses through every branch. Evaluate the smallest plausible candidates on the same workload, and let observed outcomes justify additional calls rather than treating complexity as progress.
