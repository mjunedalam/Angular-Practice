# 1. LLM Runtime Fundamentals for Agent Engineers

A customer tells ShopAssist, "I was charged twice." A language model can interpret that sentence, propose a payment lookup and write a clear explanation. It cannot make the refund legitimate merely by describing it confidently. Someone must identify the customer, obtain records, check policy and decide whether money may move. The software performing those jobs is the runtime. Understanding this boundary is the starting point for every agent we will build.

This chapter follows one model request from preparation to response. We will connect tokens, structured output, tools, streaming, errors and cost to the responsibilities of the surrounding application. Our goal is a useful engineering model of an LLM endpoint, not a complete account of neural-network training. Once the boundary is clear, later chapters can add control loops without pretending that a prompt supplies permissions, durable memory or reliable execution.

:::analogy The consultant and the case folder
Imagine hiring a knowledgeable consultant who receives one case folder at a time. The folder contains your brief, relevant records and forms for requesting work from other departments. The consultant returns an explanation or a completed request form. Your office checks the request and performs any authorized work. For the next consultation, you prepare another folder containing the information needed to continue. Where it stops: the consultant represents a model endpoint, not a person with intentions. A model has knowledge learned during training, and provider services may retain conversation or reasoning state. Your application must understand those services rather than assume the folder contains every kind of state.
:::

## What the model actually does

A token is a unit used to represent content. For text it may be a word, a word fragment, punctuation or another small piece. The exact split depends on the tokenizer, so a character count is only an estimate of token count. An identifier that looks short to a person can occupy many tokens. This matters because providers commonly meter input and generated output in tokens, and because a request must fit the model's permitted context.

For a conventional autoregressive text model, generation repeatedly chooses a next token from a distribution conditioned on the available context. Each generated token becomes part of what conditions the next choice. This explains both fluent continuation and sensitivity to an early mistake: a guessed order number can influence later tool arguments. It does not explain away all useful reasoning as "just autocomplete." The engineering point is that a plausible continuation is a proposal whose factual and operational consequences still need checking.

Temperature, where supported, changes how concentrated the sampling distribution is. A lower setting generally reduces variation; it does not turn an LLM service into a deterministic business function. Backend execution, model revisions and other settings may still change output. Some reasoning endpoints do not expose the same sampling controls as ordinary chat models. Select parameters supported by the endpoint and evaluate them on the task, rather than assuming that one setting works everywhere.

The context window is a limit on the content available to one inference operation. Treat learned general knowledge separately from current evidence. The model may know what a refund is, yet have no reliable knowledge of this customer's current payments. In the case-folder analogy, general expertise belongs to the consultant; the exact payment records belong in the folder. Reserve room for the requested output and any provider-specific reasoning budget, and count the serialized request rather than only the visible user sentence.

A provider's stop reason tells the runtime why generation ended, for example an ordinary end, a tool request, a length limit or a refusal. Normalize these outcomes without losing their operational meaning. A response cut off by its output limit is not a complete JSON decision. A refusal is not an invitation to keep repairing the same request. Inspect status before parsing or scheduling work, and preserve provider-specific distinctions needed by the controller.

### Messages and roles

Chat interfaces often organize content into messages with roles such as system, developer, user, assistant and tool. Their precise hierarchy is provider-specific. The application supplies standing instructions; the user supplies a request; earlier assistant messages contain model outputs; tool messages contain observations returned by the runtime. Preserve these distinctions when adapting providers. Combining every field into one anonymous string can lose both provider-required structure and useful provenance.

A role is not a sufficient security boundary. A tool response may contain a customer email, and that email may contain instructions telling the agent to send private data elsewhere. Calling the containing message "tool" does not make its contents trustworthy. The runtime should know which fields are verified records and which are external text. The model can be told to treat external text as data, but permission checks and data-egress controls must still live outside it.

## A short bridge from learning to generation

Machine learning fits parameters from examples rather than writing every decision rule by hand. Deep learning uses multiple learned transformations to build representations: numerical features that help a model perform its task. A text transformer begins with token identifiers and learned representations plus position information. Attention combines information from permitted positions, while other learned layers transform those representations. In a causal language model, a prediction position cannot attend to future answer tokens. A final projection produces scores over the vocabulary; normalization and the decoding policy turn those scores into a next-token choice.

Training evaluates a learning objective on examples and uses an optimizer to update weights. Inference uses the deployed weights to process a request and produce output. Adding a policy passage to a prompt changes the request context; it is not ordinarily a weight update. Fine-tuning performs additional training, whereas retrieval supplies selected external facts at inference time. An endpoint can separately store conversations or collect data under its service policy, so unchanged inference weights do not imply that no data is retained anywhere.

Think of weights as a practiced way to read the consultant's folder and context as this case's contents. Where this extension stops: weights are distributed numerical parameters, not a filing cabinet of exact propositions, and attention weights are not a reliable explanation of why a claim is true. We need neither a human intention nor an exact stored quotation to explain generation. For engineering, the distinction tells us why a newly retrieved order can guide an answer without retraining, and why a plausible answer still needs a source check.

Prerequisites: basic Python functions and HTTP request/response vocabulary are enough for this chapter. After it, you should be able to separate learned weights, request context and runtime authority. Chapter 12 develops comparable retrieval representations; Chapter 30 develops adaptation choices. The [original Transformer paper](https://arxiv.org/abs/1706.03762) explains the architecture's foundations; its encoder-decoder design is not identical to every present-day causal model.

## Structured outputs: making the model speak in contracts

Programs need decisions they can inspect reliably. A refund router might return an intent, an order identifier and a short explanation. Prompting for JSON is a useful starting point, but the result may contain prose, missing fields or an unexpected value. JSON mode, where available, improves syntactic validity without necessarily enforcing the application's schema. Schema-constrained output adds another layer by restricting supported output shapes. Providers differ in the JSON Schema subset and strict-mode conventions they accept.

Shape and meaning are different checks. A field can be a valid integer and still name an order belonging to another customer. A positive refund amount can exceed the remaining captured balance. Use schema validation to eliminate malformed requests, then use domain checks against current authoritative records. A provider's decoding constraints do not replace either application validation or authorization. They reduce avoidable parsing failures and make the boundary easier to inspect.

The following working schema uses Pydantic 2. It validates the decision locally; an adapter must separately transform its JSON Schema into the provider's supported form. The after-model validator checks the complete object, including fields supplied through defaults. This avoids relying on a field validator that may not run for an omitted default-valued field.

```python
from typing import Literal
from pydantic import BaseModel, Field, model_validator

class TriageDecision(BaseModel):
    intent: Literal["refund", "order_status", "escalate"]
    order_id: str | None = Field(
        default=None, pattern=r"^ORD-\d{6}$"
    )
    reason: str = Field(max_length=300)

    @model_validator(mode="after")
    def require_order(self):
        if self.intent == "refund" and self.order_id is None:
            raise ValueError("refund requires an order_id")
        return self
```

Validation failures can sometimes be repaired by giving the model the rejected object and a concise description of the errors. Bound that process. Two repair attempts mean at most three logical generations, not necessarily three network attempts: each generation may also contain transport retries. Record usage for every completed response, including rejected ones. A cost counter that sees only the final valid object hides the most expensive part of a difficult request.

## Tool calling is intent, not execution

A tool call contains a capability name, arguments and usually an identifier tying the eventual result to the request. ShopAssist might propose list_payments for ORD-104233. Nothing has happened to the payments system yet. The runtime first confirms that the tool exists, validates its arguments and checks whether this principal may access that order. It then invokes the implementation and returns the observation associated with the call identifier.

On the next model request, the payment observation becomes part of the available context. The model can now distinguish two captures from one authorization and one capture. If it proposes issue_refund, the runtime applies a different gate because money may move. Authorization, approval, preconditions, idempotency and execution budgets belong here. This is why the distinction between a form and the work requested by that form is useful: the same model output can be accepted, denied, deferred or escalated.

Never send an arbitrary generated string directly to a shell, interpreter, database or unrestricted HTTP client. A typed capability should expose the narrow operation the application intends to allow. Even a read tool needs resource authorization, result minimization and a deadline. Reads can reveal private information, consume quotas or trigger billable services. Tool calling makes operations easier to structure; it does not make their consequences automatically harmless.

## Streaming, latency, rate limits and provider behaviour

A streamed response delivers pieces before the full output is available. This helps a person see progress and can let the runtime detect the shape of an intended tool call earlier. It does not make partial arguments safe to execute. Assemble the complete request, check the response's completion status and validate its arguments before acting. If the stream fails halfway, distinguish an incomplete response from a successful decision rather than trying to guess the missing suffix.

Measure time to first token from the client's request start. That measurement normally includes network, provider queueing and initial processing visible to the client. After the first token, the remaining generated content adds time at a variable throughput. A useful approximation is client-measured TTFT plus remaining generated tokens divided by observed generation rate. Do not add queueing again if TTFT already includes it. Tool loops multiply these costs because each decision may require another model round trip.

Provider failures need different responses. A rate limit may justify delayed retry with jitter and Retry-After support. A transient service failure may justify a bounded retry or evaluated fallback. A malformed request or unsupported schema is usually an application error. An oversized context needs pruning, not identical repetition. A safety refusal should be surfaced or handled through an appropriate alternative, not treated as malformed JSON to repair until the model complies.

Retries need one owner and one allowance. If the SDK permits four total attempts and the application permits four total attempts, one logical operation can produce sixteen downstream attempts. Here an attempt cap includes the initial call: four extra retries at each layer would instead permit (1 + 4) x (1 + 4) = 25 attempts. Set a request deadline and a maximum attempt count across the chosen owner. Respect cancellation during backoff. A retry policy should improve availability without turning a provider incident into a quota or cost incident. Provider responses may be billable even when the application later rejects them.

## Hallucination, uncertainty and grounding

Hallucination is useful shorthand for content that is unsupported or false despite sounding plausible. In ShopAssist, a fabricated policy sentence is damaging because it may become a promise or a refund proposal. Grounding supplies relevant evidence: current orders, payment records and policy passages. It does not guarantee that the model interprets them correctly. The runtime must still verify consequential facts and distinguish supported conclusions from guesses.

Use evidence identifiers that resolve to retained source records. Ask for short, checkable justifications, such as the payment identifiers and policy section supporting a refund. Include an explicit insufficient_evidence outcome so the model has a valid way to stop. A self-reported confidence score can be studied as a routing feature, but it should not be the sole basis for moving money. Calibration requires labeled examples and measurement, not merely a number between zero and one.

## The stateless model and the stateful runtime

For ordinary independent requests, continuity comes from the application supplying relevant history and state. Losing that application record can lose the explanation of what happened, even if the next model is highly capable. Provider conversation storage is useful, but understand its retention, retrieval and failure semantics. The application still needs enough durable information to audit actions, recover work and move between providers when those are requirements.

Do not reduce every modern endpoint to plain text alone. Reasoning APIs may require opaque reasoning items or other provider-specific fields to be carried between tool turns. A normalized interface should preserve such required continuation information without exposing private reasoning as a user-facing transcript. Provider substitution is therefore a tested capability, not a promise that swapping a model name preserves every behavior. Context compatibility and evaluation matter alongside message serialization.

## Provider abstraction and basic routing

Put provider differences behind an adapter. The rest of the application should receive its own message, tool-call, response-status and usage types rather than a scattered collection of SDK objects. Normalize refusal, truncation, rate limits and invalid requests carefully: a convenient common type must not erase a distinction the controller needs. Retain required provider extension data in a controlled field when complete normalization would lose information.

Basic routing chooses a model policy for a task class. A small model may handle a measured classification workload; a stronger one may improve diagnosis or planning. The choice depends on evaluated success, latency, token use and operational limits. Fallbacks also need evaluation. A cheaper provider that interprets the same tool contract differently can create a more expensive failure. Start with a small routing policy whose reasons can be explained and observed.

## Build it: a minimal typed model client

Begin by defining the information every completed logical generation must provide. This compact interface is a teaching contract, not a complete vendor adapter. The production adapter owns schema transformation, streaming assembly, required continuation fields and classified transport retries. The usage callback is invoked for every returned response, so a structured repair wrapper cannot accidentally omit earlier rejected generations from accounting.

```python
from dataclasses import dataclass
from typing import Callable, Protocol

@dataclass(frozen=True)
class Reply:
    text: str
    status: str
    input_tokens: int
    output_tokens: int
    cost_usd: float

class Adapter(Protocol):
    def generate(self, messages: list[dict]) -> Reply: ...

class ModelClient:
    def __init__(self, adapter: Adapter,
                 account: Callable[[Reply], None]):
        self.adapter = adapter
        self.account = account

    def generate(self, messages: list[dict]) -> Reply:
        reply = self.adapter.generate(messages)
        self.account(reply)
        return reply
```

Test this contract with a fake adapter returning scripted responses. First return invalid decision text, then a valid object, and check that both responses appear in the usage ledger. Separately force a rate limit and prove that only the adapter owns transport retries. A fake cannot measure model quality, but it can establish the runtime's response handling without an API key. Chapter 11 develops that separation into a runnable harness.

## Failure modes and how to recognise them

A sudden token bill increase can mean growing history, repeated repair or duplicated retries. Diagnose those mechanisms separately before changing the model. A wrong resource identifier points toward missing semantic validation or unsupported evidence. A broken JSON fragment points toward truncation or unsafe character slicing. A behavior change after a provider upgrade points toward contract compatibility and evaluation. These symptoms are actionable because the adapter and runtime record their decisions.

## Production lens

Every model call should have a correlation identifier, model/version information, completion status, elapsed time and usage records under an appropriate privacy policy. Retry and repair allowances must be visible and separate. Do not log credentials or indiscriminately retain raw customer records to achieve observability. A compact context manifest and controlled source references often explain a decision with less sensitive material. Chapters 8 and 26 develop these records in detail.

## Interview drills

If asked where an LLM application's state lives, distinguish application records, provider service state and the context available to one inference. If asked why a valid tool call is insufficient, trace schema, resource authorization, preconditions and execution. If asked how to handle invalid JSON, begin with completion status and provider constraints, then describe bounded local validation and repair. Each answer should identify the owner of the guarantee rather than merely name a framework feature.

## Key takeaways

The useful boundary is between a generated proposal and an authorized operation. Tokens and context limits explain important cost and latency behavior, while explicit records explain continuity. Structured output improves the shape of decisions; evidence, business rules and permissions determine whether those decisions may be used. A provider adapter makes those distinctions available to the controller. It succeeds when failures remain understandable, bounded and recoverable.
