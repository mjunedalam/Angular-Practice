# 11. Build a Mini Agent Harness From Scratch

We have described the responsibilities of a harness. Now we will connect them in a working example small enough to inspect without a framework. The companion examples/mini_harness.py uses Python 3.11 or later and only the standard library. Its deterministic model is a stored script, its run record is SQLite JSON and its fake payment service uses a separate SQLite database. The tests exercise actual persistence and payment records rather than relying on a successful-looking final reply.

The example's scope matters. One writer advances each run. Operations are local and synchronous; the harness does not provide a hard timeout for arbitrary network code, distributed leases or an HTTP identity service. Callers supply authenticated identities, and a current-scope lookup can be injected. Its absolute deadline and usage survive restart. The fake service atomically deduplicates effect identities and checks balance. That explicit downstream contract makes the demonstrated crash recovery possible.

:::analogy Building a small working model railway
A model railway can teach signals, track ownership, station holds and a control-room record without carrying real passengers. Each added component should demonstrate a specific behavior: a signal prevents a train entering, a station hold preserves its position and a journey record explains completion. Where it stops: a working model is not a certified railway. This harness establishes its local contracts through deterministic checks; real providers, credentials, network deadlines, distributed ownership and production retention need further implementation and evidence.
:::

## Stage 0: the twenty-line loop

The naive loop calls a model, executes its named tools and repeats until no calls remain. That shape explains the appeal of agent demos: a few lines produce apparently useful behavior. It also lacks argument validation, resource authority, review, limits, retained intents and independent completion checks. Those defects are consequences of missing boundaries, not merely insufficient prompting. We keep the loop's simple shape while introducing an explicit owner for each decision.

Do not deploy the baseline or call it safe because its sample tools are friendly. A scripted response can request a foreign payment, generate hundreds of calls or falsely finish. These cases make useful tests before a live model is involved. The point of building in stages is to see why each boundary exists and how it changes observable behavior. The finished companion replaces the baseline rather than requiring readers to guess how disconnected excerpts fit together.

## Stage 1: typed messages and decisions

A model adapter normally receives role-aware messages and returns a response with content, call identifiers, arguments, status and usage. This example intentionally uses a smaller internal decision dictionary: either calls or final. A call has id, name and args. The script is already structured, so it demonstrates controller behavior rather than vendor serialization. A live adapter must still assemble valid provider messages, preserve tool/result associations and handle refusal/truncation distinctly.

validate_call checks the local contract. The only tools are get_payment and refund. A refund requires payment_id, currency INR, positive integer amount_minor and bounded evidence text; extra fields are rejected. Using type(amount) is int deliberately rejects a boolean, which Python otherwise treats as an integer subtype. This teaching schema is narrow, but its exact-unit and unknown-field behavior is observable. A production adapter can use Pydantic and a provider-compatible JSON Schema around the same intent.

## Stage 2: the model interface

The stored script is a deterministic model replacement. Its cursor lives in run state, so a new process does not need a hidden mutable model object to remember which decision comes next. Each scripted response costs one illustrative accounting unit, declared in the contract. That lets tests prove reservation and usage behavior exactly. It is not a measured price or token model, and the example does not pretend that a live provider always charges a fixed amount.

The controller advances the cursor and records usage before saving its resulting decision queue. A live model boundary would additionally record every completed/rejected generation and implement classified transport retry policy. Its expected maximum cost must be reservable if a hard cost cap is required. The fixed fake makes that mechanism easy to see; replacing it with an endpoint requires a compatible usage, continuation and deadline contract, not only a generate function returning text.

## Stage 3: tool registry, validation and executor

The small registry is an explicit two-tool allowlist in validation rather than an extensible catalog class. It keeps the example focused on behavior while preserving the production responsibility. allowed checks the currently supplied scopes and reads payment ownership from the fake service. Both principal tenant and user must match the payment record. A caller can name refund while lacking the execution scope; the request is denied rather than honored because the tool exists.

The executor checks arguments and authority before interpreting ledger state or asking for approval. Unknown tools and malformed values produce invalid; foreign resources or missing scope produce denied. It checks the absolute deadline at the operation boundary and a tool-call allowance before an actual invocation. Results are small structured records, so no arbitrary character slice breaks their serialization. A production registry would add versions, output schemas, effect policy and resource-specific service adapters.

## Stage 4: loop controller, budgets and stop conditions

start records positive limits, absolute deadline, usage and a script cursor. The run method checks remaining model turns and reserves the next fixed accounting unit before another response. The executor checks tool allowance before each invocation, including the call resumed after approval. A response with several calls cannot bypass max_tool_calls simply because the controller performed one earlier check. Duplicate confirmed effects can return retained evidence without another external operation.

Limits survive through the stored record. Restarting or resuming does not renew deadline_at or reset consumed turns/cost/tool calls. A run deadline can expire during approval waiting, and approval has a separate expiry. They produce different states: limited for exhausted run allowance, expired for a stale review. This example has no token counter because its fake produces no billable tokens. Adding a live model requires token accounting at that adapter boundary, including repairs and retries.

A tool-free final script response invokes verified. The verifier requires at least one accepted intent, confirmed ledger entries and matching authoritative payment-service results. Therefore an early final claim is incomplete. This acceptance rule is specific to the demonstration's refund goal; a product needs task-specific coverage such as required notification or ticket update. Verification establishes the accepted fake effects, not the semantics of an arbitrary free-text goal. The harness does not claim that one payment receipt completes every possible support task.

## Stage 5: state, events and checkpoints

Store saves a versioned JSON document transactionally in SQLite. Its load method rejects unknown schema versions. The document contains principal, limits, deadline, cursor, queued calls, pending approval, accepted effects, observations and events. These fields survive a new Harness instance and a real process exit. Database connections are explicitly closed; a transaction context manages commit/rollback rather than being mistaken for connection cleanup.

Events have per-run sequence positions and record lifecycle, model calls, approval requests and tool results. This implementation stores an event list inside the checkpoint. It is not a fully independent event-sourced system: current state is authoritative, and external multiwriter append consistency is outside scope. That is a deliberate size tradeoff. Chapter 7's fuller event/reducer architecture can replace this store when its replay, concurrency and audit requirements justify it.

## Stage 6: authorisation and approval interrupts

The first eligible financial proposal creates pending with its exact call, run-specific approval binding and expiry. State changes to waiting and is saved before returning. No worker sleeps waiting for the reviewer. The demo recognizes a trusted reviewer identity supplied by its caller; a real application must authenticate that identity and enforce review permissions. The code is a callable teaching API, not a network service with built-in login or access-token verification.

resume requires a waiting run, an actual boolean decision, the configured reviewer and a binding matching both the pending record and the reviewed proposal. This approval digest includes run identity, principal tenant/user, tool name/version and canonical reviewed arguments. Narrative evidence belongs in the review digest even though it stays out of the stable business effect key. Accepted intents remain keyed by the effect identity, with approver, decision time and approval digest retained in their audit record.

Rejection terminates denied without payment execution. Accepted review still checks the absolute run deadline and proposal expiry. The executor then rechecks current scope and payment ownership. Approval cannot override revoked authority or a changed resource precondition simply because a person said yes earlier.

The companion permits injection of current_scopes so the caller can consult a live authority source. Its default uses the supplied principal's scope list, suitable for the local demonstration. Do not mistake that default snapshot for a complete enterprise revocation mechanism. Chapter 20 supplies the identity/delegation design. Here the important extension point and its execution-time invocation are explicit, so the limitation is visible rather than hidden behind a reassuring authorize name.

## Stage 7: error envelopes, idempotency and the executor

The effect key includes tenant, payment, currency and exact amount, excluding narrative evidence. The fake payment identity supports one logical refund per tenant/payment/currency/amount tuple. It does not support repeated legitimate equal-value partial refunds as separate transactions. The demonstration permits one full refund of its seeded captured payment, so these fields identify the intended effect within this narrow domain. Another domain allowing repeated legitimate equal-value transactions needs a business-operation identifier as well. The companion's balance check also prevents over-refunding across different keys, which key deduplication alone would not establish.

Before submission, resume persists accepted[key] as pending. Payments.refund uses a separate SQLite transaction, taking a write lock, checking whether the key already exists, validating ownership and remaining balance, updating the payment and inserting the result. Deduplication and balance change commit together. A lost local result checkpoint can therefore be resolved by reading the fake service's key record. The local ledger is useful, but the atomic downstream contract provides the single-effect property demonstrated here.

If a restarted run finds a pending intent whose service result already exists, it records that result and continues without another effect. If no result exists, the accepted key can be submitted under this fake service's idempotent contract, subject to remaining limits.

If the absolute deadline has passed or current authority was revoked, this small executor stops before reconciling the pending effect. It schedules no new mutation and preserves the pending intent for separately authorized manual reconciliation. Do not infer that every crash automatically reaches completed. Real APIs may have key expiration, nonqueryable outcomes or non-idempotent operations. Those need an explicit unknown/reconciliation policy and may require human handoff rather than the local fake's continuation behavior.

## Running it

Extract the PDF's `Agentic_AI_Engineering_companion.zip` attachment as described in the preface. From the extracted folder containing `examples/` and `chapters/`, run the companion file and its checks below. No model API keys or third-party dependencies are required for this harness. The demonstration uses a temporary directory and cleans it up afterward; the process-crash test supplies retained database paths so another process can reload them. To study manual continuation, retain your own database paths and run identifier.

```bash
python examples/mini_harness.py
python -m unittest discover -s examples -p 'test_mini_harness.py' -v
```

```text
before review: waiting
after review: completed verified
refunds: 1
```

The shipped deterministic checks cover rejected approval, foreign ownership, restart persistence, deadline and approval expiry, unauthorized/mismatched signals, cross-run approval replay, review audit, false completion, multi-call limits, cost reservation, changed evidence wording, actual process exit after service commit, cancellation, revoked execution scope, post-deadline reconciliation records and unsupported state schemas. They inspect payment records and run state directly. Live-model quality is a separate evaluation problem; passing these tests does not establish how well an endpoint interprets real customers.

### Reading a result

Inspect status and reason before reading the attractive final explanation. Waiting means no financial operation has been scheduled for the pending proposal. Denied or expired means the reviewed effect did not execute through that path. Limited may still retain an earlier completed effect and therefore requires a truthful partial outcome. Completed is supported by the demo's verifier. A database or environment error can leave a persisted intent needing recovery; it must not be translated casually into a claim that nothing happened.

## Stage 8: packaging the harness as reusable interfaces

Extract interfaces when a second implementation needs them. Model, state store, policy lookup, tool registry/executor, acceptance verifier and event reader are natural boundaries. Keep exact accepted intent and result contracts stable. Adding provider/network support requires response statuses, accounting, deadlines and valid conversation assembly. Adding distributed workers requires ownership/fencing beyond this single-writer demo. Adding retention requires classification, deletion and audit storage policies.

A generic platform should not put refund balance logic into its loop. Replace Payments with a domain adapter enforcing the same documented authority and effect contract, or change the contract explicitly when the provider differs. Replace Store with a suitable durable implementation while preserving absolute deadlines and exact proposal binding. Interfaces make these responsibilities replaceable; they do not ensure the replacement meets them. Contract checks need to run against each supported implementation.

## Comparing with frameworks

Frameworks offer loop execution, graph state, tool plumbing, sessions, persistence adapters, interrupts and tracing in differing combinations. Map each feature to its actual contract rather than treating a session transcript as an accepted-effect checkpoint. An interrupt can pause work while leaving approval authentication/binding to the application. A recursion or maximum-turn setting can bound model loops while leaving tool batches and business cost to additional controls. Chapter 31 compares the framework implementations directly.

The lesson is not to keep this small harness forever. Building it once makes framework behavior inspectable: which state survives, who resumes a wait, how calls are counted and how a final claim is verified. Keep the domain invariants, identity policy and effect contracts under application ownership even when libraries implement the machinery. A framework migration should be tested against the same behavior cases, especially the crash window and late approval.

## Interview drills

Describe the complete refund path from a stored scripted decision through bound review, intent checkpoint, atomic fake-service transaction and independent verification. Explain why the key excludes prose and why the balance rule remains necessary. State the single-writer and synchronous limits before proposing a distributed production version. If asked what to swap first, choose the component whose required contract exceeds the demonstration, then name the checks proving its replacement preserves behavior.

## Key takeaways

A small harness can establish real local behavior when its scope is precise and its tests cross the important boundaries. Durable state does not imply distributed ownership; a local ledger does not imply an external single effect; a final model reply does not imply task completion. The companion combines explicit downstream deduplication, retained intent, unchanged budgets and acceptance reads. That makes it a useful foundation for the larger runtime rather than a miniature production platform with unearned guarantees.
