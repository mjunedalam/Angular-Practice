# 26. Observability for Agent Systems

A customer says ShopAssist took too long and gave an unclear answer. The final response alone cannot reveal whether the agent waited on a tool, searched repeatedly, used an outdated policy or spent most of the run awaiting approval. An ordinary HTTP access log says a request happened, but the decisions are distributed across model calls, retrieval, state updates and external services. Observability makes that path inspectable without reproducing the whole incident by guesswork.

An observable agent records what happened, which inputs and versions mattered, how resources were used and what outcome was observed. It does not expose a model's private internal reasoning merely by storing a transcript. This chapter designs traces, metrics, events and provenance around the run while protecting sensitive content. The goal is useful evidence for debugging, evaluation and operation, with a clear distinction between recorded decisions, inferred causes and verified effects.

:::analogy A parcel's tracking history and the depot dashboard
A parcel has a tracking identity and a sequence of scans showing collection, sorting, waiting and delivery. Depot managers also watch aggregate delay and throughput across many parcels. A trace resembles one parcel's path; metrics describe the fleet. Where it stops: an absent scan does not prove an event never happened, and tracking does not reveal every internal decision. Agent telemetry can be sampled or incomplete, so consequential audit and effect records need their own retention and integrity contracts.
:::

## The telemetry model

Traces describe one connected operation through spans. A span records a bounded piece of work with start/end time, parent or links, attributes and events. Metrics aggregate measurements such as duration, tokens or failures across operations. Logs/events capture discrete facts, such as a denied tool request or resolved approval. Provenance records which configuration and source versions produced a decision. These signals answer different questions and should connect without forcing every detail into one log line.

Use a stable run ID for the application's durable record and trace context for distributed telemetry. Propagate the relevant context through queues, workflow activities, remote calls and resumes. A trace ID is not an entitlement or task identity; the remote operation still needs its own authenticated identifiers. Long-lived runs can use several linked trace segments if backend retention or sampling makes one enormous trace impractical. Keep the durable run link so an operator can navigate between them.

Do not put each run ID on metric labels. That creates unbounded time-series cardinality rather than a useful aggregate. Put detailed identifiers on access-controlled spans/logs and use exemplars or links to connect a metric to a representative trace. Choose bounded dimensions such as approved model tier, tool name, outcome and agent release. Large-scale tenant cost attribution may belong in a dedicated ledger or controlled aggregation rather than one metric series for every customer and run combination.

## Span design for agents

Create a run or run-segment span, with child spans for actual steps, model calls, tools, retrieval and policy decisions. A model call records provider/model identity, relevant request settings, input/output usage, caching usage where available, duration, time to first token and stop reason. A tool span records tool version, side-effect class, validated argument reference or digest, result status and operation identity. Do not infer a tool's success from the fact that the model requested it.

Retrieval spans should show source, filters, result count, evidence IDs and the context-selection relationship. Query hashes can reduce content capture, but they are not automatically anonymous; short or predictable queries can sometimes be guessed. Policy spans record the actual policy version and allow/deny reason. Checkpoint spans record state version and persistence outcome. These attributes should let the operator distinguish failed retrieval, rejected policy and missing persistence rather than treating them as one generic agent error.

Approval waits need special handling because no worker should hold a process span open for days solely to represent waiting. Record the wait request and outcome with durable timestamps and link the resume segment to the proposal and run. An agent-native view can display the full waiting interval from those records. Causality is important: a decision arriving on another worker should not look like a concurrent unrelated operation just because the original process released its resources.

OpenTelemetry provides portable instrumentation APIs and semantic conventions, including GenAI conventions. Pin the convention version used by the implementation because names and stability can evolve. Adopt standard fields where the selected version defines them and keep additional application fields namespaced. A custom attribute is acceptable when its meaning is documented. Claiming compliance while silently mixing conventions from different versions makes dashboards and adapter comparisons less reliable.

## Build it: instrumentation with OpenTelemetry

Instrument at the boundary where the application already validates and executes an operation. The code below assumes an SDK tracer, exporter and metrics pipeline configured by the application. It deliberately avoids raw prompts, tool arguments and exception messages. It is a teaching wrapper, not complete telemetry deployment. The model object must expose an approved model name and normalised response usage; a metric helper must use bounded labels and documented units.

```python
from time import perf_counter
from opentelemetry.trace import Status, StatusCode

def traced_model_call(model, messages, tools, context,
                      tracer, measurements):
    started = perf_counter()
    with tracer.start_as_current_span(
        "agent.model.call", record_exception=False,
        set_status_on_exception=False,
    ) as span:
        span.set_attribute("gen_ai.request.model", model.name)
        span.set_attribute("agent.run_id", context.run_id)
        span.set_attribute("agent.prompt_release", context.release)
        span.set_attribute("agent.context_ref", context.context_ref)
        try:
            response = model.generate(messages, tools)
        except Exception as error:
            span.set_attribute("error.type", type(error).__name__)
            span.set_status(Status(StatusCode.ERROR))
            raise
        span.set_attribute("gen_ai.usage.input_tokens",
                           response.input_tokens)
        span.set_attribute("gen_ai.usage.output_tokens",
                           response.output_tokens)
        measurements.record_model_call(
            context.metric_bucket, response,
            elapsed_s=perf_counter() - started)
        return response
```

Both flags matter. By default, an exception escaping an OpenTelemetry span context can create an exception event and set an error status whose description includes the message. Catching the exception and recording only its type does not prevent that automatic recording when the code rethrows it. This wrapper disables both automatic paths, then explicitly records the approved error type and an ERROR status without a description. The regression uses a synthetic private marker and inspects the exported span, including events and status, rather than assuming a safe-looking catch block is enough.

The opt-out protects this span only. The same exception still leaves the function, so an enclosing span with default settings can record its message and stack. Apply the same policy at parent and framework instrumentation boundaries, or translate to an approved safe error representation before crossing them; review automatic logs and exporters too. Even an exception class name needs an approved taxonomy if applications generate sensitive names dynamically. The existing wrapper assumes ordinary approved error classes and safe context fields. Collector filtering remains defence in depth.

The selected semantic-convention version must validate the standard fields, while application attributes such as context_ref retain their own schema. The metric bucket is a bounded approved dimension, not a dynamic run or unrestricted principal string. This wrapper does not automatically record errors from every nested service; those boundaries need their own spans. Likewise a trace export failure must not decide whether an already committed payment occurred. Record consequential effects in the durable audit/effect path even when tracing is unavailable.

Trace propagation across a remote boundary needs both sender injection and receiver extraction through the supported carrier. An HTTP header, queue metadata or workflow context can carry it depending on the integration. Do not place a private transcript in propagation headers. Correlation metadata should be bounded, authenticated where appropriate and separate from authorisation. A malicious caller choosing a trace ID must not gain access to another customer's trace or state record.

## Metrics that matter

Outcome metrics include correct task completion, escalation, partial results, unsafe effects and false completions. Latency metrics distinguish first response, active processing, completion and human waiting. Model metrics include time to first token, generation pace and errors by class. Tool metrics include latency, failure class, dedupe hits and retry counts. Behaviour metrics include steps, tool mix, no-progress detections and repeated searches. The precise definitions need denominators and units, not just metric names.

Cost metrics need both usage and price provenance. Input/output/cache rates can change by provider and contract; non-model APIs, retrieval and sandbox compute can matter too. A ledger should reconcile to actual billing where available, while fleet metrics show trends. Cost per successful task includes unsuccessful work needed to obtain successes. A prompt change that raises calls per run may explain an invoice increase even if the provider's price stayed the same.

Safety and human metrics connect operation to oversight. Track denials, attempted forbidden actions, observed violations, approval expiry and decision time by action class. A growing denial rate can signal an attack, a broken client or an overly restrictive policy; the metric alone does not identify the cause. Use linked traces and audit to inspect the population. An alert should lead to a defined investigation or containment action rather than simply adding another chart.

## Provenance: prompt, context and configuration versions

Record the agent release, instruction manifest, model snapshot or resolved identifier, tool schemas and policy versions. Routing and fallback decisions also matter because the same agent name can use different models under different conditions. Keep source IDs, document versions and context selection so a reviewer can see why a clause was available to the model. Without this, an intermittent mistake may appear random when it actually follows one stale source or configuration release.

A context manifest is a map, not the full territory. It can identify selected items and token counts, but exact deterministic replay requires the corresponding immutable/versioned content or a permitted retained snapshot. If a wiki page changes in place, its current text may no longer reproduce the old run. State that retention limitation explicitly. Avoid claiming every decision is reconstructable while retaining only a hash that cannot recover the evidence used.

Provenance should also connect proposals and effects. The tool schema or prompt may explain why a proposal was generated, while a policy version and approval record explain why it was permitted. An observed external result explains what happened. These are distinct causal questions. A model-generated rationale can help communication, but it should not replace the recorded facts or be presented as access to the model's internal decision process.

## Redaction and privacy in telemetry

Default to the minimum metadata needed for operations. Capture full prompts or outputs only for an approved debugging/evaluation purpose, with access control and short justified retention. Apply classification before recording content. Redacting later in a backend can miss copies already buffered, exported or forwarded. Hashes, IDs and scores can still be sensitive metadata, so do not describe metadata-only telemetry as inherently anonymous or unrestricted.

Sensitive content can enter exception messages, stack frames, log arguments and nested attributes as well as a known prompt field. A redaction helper with a short denylist is therefore only one layer. Prefer an allowlist of permitted fields, safe error categories and controlled content references. Test both normal and error paths. Recording an unfiltered exception that includes the original SQL or customer email can defeat otherwise careful prompt redaction.

Use a Collector redaction/transform layer as defence in depth before backends, but do not rely on it to repair every source mistake. Ensure it actually runs on every export route and test its policy. Restrict content stores and trace viewers by entitlement, audit sensitive access where needed and establish deletion/retention procedures. The observability platform is itself a data destination under Chapter 22's governance model.

## Agent-native trace views

A generic span timeline shows timing and causality, but an agent investigation also needs a conversation/decision view, context view and state-diff view. Show the recorded tool requests, evidence selections, policy decisions and changes in state. Make the distinction between proposed and executed operations visible. A cost view should attribute usage by step so repeated planning or an oversized observation can be identified without inspecting every token.

A durable-wait view can show when a proposal entered the queue, when an approver decided and which worker resumed. A remote-delegation view connects caller operation and remote task identity. These views should draw from authoritative records or clear telemetry references, with gaps labelled. A missing sampled span cannot establish that no call happened. Where completeness matters, use an unsampled audit/effect record and expose its relationship to the sampled trace.

## Linking traces to evaluations and incidents

Attach evaluation results through linked records containing case/grader/version information, rather than burying them in a mutable span after the fact. Operators can then inspect runs where groundedness failed or a trajectory exceeded its budget. Incident records should link the relevant runs and release versions. Production failures can become reduced evaluation and replay cases through a reviewed privacy process, preserving the conditions needed to reproduce the issue without automatically exporting every sensitive transcript.

Keep measurement uncertainty visible. An online judge score is evidence about sampled quality, not an authoritative statement that every answer in the release was correct. A customer complaint may reveal a case the sampler missed. Combine traces, outcomes, review and business signals. The trace helps investigate a particular run; aggregate evaluation determines whether a change affects a broader population. Connecting them is valuable precisely because they answer different questions.

## Debugging a bad trajectory: a worked example

Consider a constructed ShopAssist run with 14 steps and 11 near-duplicate policy searches. The final answer is vague, and the no-progress detector ends the investigation. The trace reveals that early searches were fast, so dependency latency is not the main issue. The context view shows an archived clause contradicting current order data. Later queries keep varying the wording while returning the same stale source. This is a plausible teaching case, not a claimed production incident.

The operator compares the source version with the retrieval filters and sees that one superseded document remained searchable. The fix removes or correctly versions that source, records a contradiction state for the controller and adds the case to the regression set. A context-budget change alone would not solve the stale policy. A stronger model might still see the contradiction. Provenance makes a targeted knowledge/control correction possible rather than treating every loop as a model weakness.

After the fix, run the paired evaluation under the same fixtures and grader. Check correct outcome, steps, cost and whether the agent honestly escalates when genuine policy conflict remains. A trace showing fewer searches is not sufficient if the answer became confidently wrong. Preserve the original failure as a replay test for context assembly and as a live-model case where relevant. Observability should lead to a verified correction, not merely a more attractive dashboard.
