# 34. Specialized Agent Systems

A research agent, a coding agent and an incident commander can share a controlled loop while requiring very different evidence of success. A cited answer is not a tested patch. A passing test is not proof that a production service recovered. Specialization changes the environment, tools, timing and failure consequences. It should also change the acceptance checks, while preserving ownership, authority, budgets and recovery in the harness.

We will follow a service organization that assigns specialists to different jobs. Each specialist receives a task, the permitted workspace, a budget and an acceptance test. The supervisor does not judge every result by how confident the report sounds. It uses evidence suited to the work. This chapter develops that distinction so a team can reuse its platform without pretending every agent is the same product.

:::analogy A specialist field-service team
A service company sends an investigator to understand a fault, a technician to repair equipment and an analyst to reconcile records. They share dispatch, identity and reporting rules, but carry different tools and demonstrate completion differently. The investigator supplies supported findings; the technician supplies measured operation after repair. Where it stops: software agents can be manipulated by text, images or tool results, and their tools can expose sensitive data at machine speed. Human job titles are not access controls.
:::

## Research agents and evidence synthesis

A research agent plans subquestions, searches approved sources, reads relevant material, extracts evidence and writes a supported synthesis. Its result must show what was checked and what remains unknown. Source quality includes authority, relevance, publication time and applicable version. A primary source can still be incomplete or outdated; a recent secondary source can help locate the right record. Do not replace source analysis with a fixed score that makes every official-looking page trustworthy.

Use an evidence ledger containing stable IDs, source locators, observed time, document version and the exact supporting passage or query result. Draft claims reference those entries. A citation verifier checks both existence and support: a real citation beside an unsupported sentence is still a defect. Conflicting sources should remain visible until a stated precedence rule settles them or the answer presents the unresolved disagreement.

```python
from pydantic import BaseModel, Field

class LedgerEntry(BaseModel):
    evidence_id: str
    source_ref: str
    version: str | None
    supporting_text: str = Field(max_length=500)

class SupportedClaim(BaseModel):
    sentence: str
    evidence_ids: list[str] = Field(min_length=1)

class ResearchAnswer(BaseModel):
    claims: list[SupportedClaim]
    gaps: list[str]
```

This schema supports sentence-level mapping but cannot establish entailment alone. The validator must load the named ledger entries, verify allowed provenance and check support. The writer should label interpretation separately from observed fact. For numerical questions, preserve units and denominator definitions. “Refund rate rose” needs a time interval, population and query, not merely a passage about a new returns policy.

Research is often read-only, but it is not harmless. Searches can reveal private questions, and fetched material can contain prompt injection. Give the researcher scoped source access, controlled outbound requests and no unnecessary mutation channel. Stop when subquestions are covered, new retrieval produces no useful evidence, or a budget is reached. An honest partial answer names the searched sources and gap; a failed search does not prove that no answer exists anywhere.

## Coding and repository agents

A coding agent works in a repository through search, file reading, patch application and executable checks. Begin by reproducing the problem and identifying the relevant conventions. Then make a small change, run the acceptance checks and review the diff with the results. A second model can critique a patch, but tests, type checks and real state provide information that rereading the same explanation does not.

The execution environment must be disposable and isolated. Avoid production credentials, restrict network access to approved package mirrors, cap time and output, and give the process only required files. A read-only root prevents writes; it does not prevent reading everything visible in that filesystem. Isolation needs an explicit mount and access policy. Candidate code and repository test scripts remain untrusted executable content even when the goal is legitimate.

Repository instructions can help the agent orient itself. An approved AGENTS.md-style entry point describes build commands and constraints; architecture notes explain deliberate design decisions; a check script defines repeatable verification. Load these as trusted instructions only from a reviewed owner and ref. A user-supplied repository or a dependency README can contain hostile guidance. Provenance decides instruction authority; a familiar filename does not.

Across sessions, keep a progress record with the task, completed checks, attempts, current branch, uncertain effects and next step. On resume, reconcile that record with actual files and external systems. It may be stale because the prior worker crashed before writing it. A pull request created without a recorded response should be found by its logical identity, not recreated blindly. Progress prose supports orientation, while durable effect records support safe recovery.

Protect tests and CI configuration through a harness-owned guard when the task's policy forbids changing them. Compare the final diff to a trusted base, including renames, links and generated files. Hidden tests should run in an equally isolated environment: executing a patch outside the sandbox simply because it is being judged defeats the boundary. A dependency-upgrade task needs an explicit reviewed mode that permits the corresponding manifest and lockfile changes.

## Data and SQL agents

A data agent needs agreed metric definitions before it needs clever SQL. Expose governed views or a semantic layer that defines revenue, returns, units, time zones and join relationships. A question about refund rate should specify eligible orders and counted refunds. Without those definitions, a syntactically correct query can produce an authoritative-looking number answering a different question.

Schema-discovery tools expose only authorized objects and useful descriptions. Compile semantic requests to SQL or validate the full parsed query tree. Reject writes, forbidden functions, unapproved relations and excessive work. Row limits control returned data, but do not necessarily limit scan cost. Use read-only database roles, row-level security, statement timeouts and query-cost controls as the actual enforcement layers. Parsing is defense in depth, not a replacement for database permissions.

Show the query, definitions, time range and evidence reference with the answer. Cross-check totals, units, nulls and unexpected population changes. Execution-based evaluations compare result sets with reference queries, not just generated SQL strings. Include questions whose requested dimension is missing, periods outside retention and ambiguous business terms. Refusal should describe the specific limitation. A missing seller-type column cannot establish that marketplace orders were excluded from the view.

Write access is a separate product mode. Preview affected rows, bind approval to the exact intended change, run transactional validation and support recovery. Do not expand a read-only analyst's permissions merely because the model proposes an UPDATE. In the service-team analogy, reconciling a stock report and authorizing a stock adjustment are different jobs. They may share data but have different authority and evidence requirements.

## Browser and computer-use agents

A browser agent observes pages or screenshots and acts through clicks, typing and navigation. The UI is an unstable surface: controls move, state changes and on-screen text can be adversarial. Prefer a scoped API when it exists and meets the task. UI automation is useful when no suitable API is available, but its success must be checked by reading resulting state, not inferred from the input event.

Use isolated profiles or disposable desktops with only approved accounts and applications. Restrict domains, downloads and file access. Untrusted content on a page remains data even if it claims to be a system instruction. For a consequential submission, the harness applies the user's authorization and action policy; the agent presents the concrete values being submitted when confirmation is required. A screenshot can show the intended operation but does not authorize an unrelated action.

After submitting, inspect the resulting record, receipt or account state. A click on “save” can fail silently, create a duplicate or navigate away. Store the receipt and correlate it to the logical effect. If the result is unknown, stop repeated submissions and reconcile. Recording screenshots can aid audit, but redact personal information and apply retention. Do not let diagnostic convenience turn every UI step into indefinite storage of sensitive screen content.

## Voice and real-time agents

A voice agent adds turn-taking and perceived delay to the same authority problem. A user speaking an order number expects acknowledgment quickly, but a payment still needs verified identity, clear values and an authorized decision. Stream recognition, model output and audio where supported. Use a fast path for known structured tasks, and explain when a slower lookup is underway. Fillers should reflect actual progress rather than conceal a stuck run.

An illustrative latency budget for first audible response is one second. One possible allocation is 250 milliseconds for end-of-speech detection, 150 for a final transcript, 350 for first model tokens, 150 for first audio and 100 for network transit. These are planning numbers, not universal measurements. Some stages overlap in streaming systems. Measure actual end-to-end percentiles with accents, background noise and realistic tool delays before choosing the product's target.

Handle interruptions explicitly. Cancel speech generation and read work where safe, but do not assume cancellation can undo a submitted refund or change. An in-flight mutation may finish after the caller interrupts. Reconcile it and tell the user its actual outcome before taking another action. Read back critical amounts, dates and recipients. Voice is not strong identity proof; use suitable step-up verification for sensitive operations and preserve an audit record of the confirmed values.

## Event-driven, scheduled and long-running agents

An event-driven agent begins from an alert or business event rather than a fresh conversational request. Assign an owning team and policy before enabling the trigger. Transport event identity prevents repeated delivery from creating new work; correlation groups related events into one incident. A scheduled run also needs a stable occurrence identity. “Every night” is insufficient if two schedulers can start the same job or a retry recreates its effects.

Use durable execution for waits, timers and continuation. An event storm needs admission control, priority and backpressure before model calls multiply. Define which work can be delayed or summarized and which alerts must still reach humans when the agent platform is unavailable. Every autonomous run needs a reportable status and a way to stop it. Absence of a human at the beginning is a reason to make the authority boundary clearer, not broader.

Keep notifications factual and scoped. An alert can create a draft incident update; publishing externally may require a different policy. Long-running work should carry remaining budgets and version information across sessions. A delayed approval is validated against the current world, including resource preconditions. Scheduled reminders should not silently renew an expired approval. Time extends the number of things that can change, so continuation must refresh volatile facts before effects.

## IoT and operations agents

Operations agents consume telemetry and propose changes to physical or production systems. Summarization tools should return bounded windows, units, observation time and source references. A model can help explore causes, but physical limits and production safety envelopes are enforced outside its reasoning. A valve's permitted range, minimum replica count or maintenance restriction should remain checked even if the model's explanation is persuasive.

Use simulation or dry-run where meaningful, then bind real execution to resource scope and preconditions. High-impact actions may require distinct approvers or a privileged role. The executor uses short-lived authority for one operation, and records applied, rejected or unknown outcome. Verification checks independent signals after the action. A command accepted by a controller is not proof that the physical state changed safely or that users recovered.

For AegisOps, restart, scale, feature-flag change and rollback all belong in the production-change map. Assign risk by action and blast radius rather than by one generic tool label. A pre-approved runbook exception applies only to the precise action class and conditions permitted by policy. Unknown or destructive actions are blocked and escalated. Confidence helps prioritize investigation; it does not expand the allowed operating envelope.

## Multimodal agents

Images, audio, scans and diagrams add evidence channels, not instruction authority. A screenshot may contain a fake instruction; a voice message may impersonate someone; a photo can be edited. Record source, capture time and quality alongside extracted fields. Keep confidence meaningful: a model's confident text is not a calibrated probability. Validation should check business rules and reconcile uncertain fields against approved records where possible.

Extract to structure early when that makes the task easier to verify. For an invoice scan, identify supplier, invoice number, currency and amount, then compare them with the procurement record. Retain the original under access and retention policy when audit requires it. Resizing, cropping and caching can reduce cost, but must not discard a field needed to decide eligibility. Track extraction versions so a changed model does not silently alter the same source record.

Build evaluations across image quality, document type, language, accents and manipulated inputs. Include failure cases that require clarification rather than a guessed value. Privacy review should account for incidental people, account details and background audio, not merely the field the user asked to extract. The specialist team may carry a camera and microphone, but its permissions still govern what it records, sends, retains and acts upon.

## What changes and what stays universal

Research verifies claims against evidence. Coding verifies artifacts through isolated executable checks and review. Data verifies query meaning and result sets. Browser work verifies resulting application state. Voice verifies critical values and authority while meeting turn-taking requirements. Operations verifies independent post-action signals. Multimodal work verifies extraction and provenance. Each product should name its own false-completion condition, because a generic “the agent answered” metric cannot reveal these distinctions.

The agent harness supplies the universal controlled lifecycle: an owned goal, permitted capabilities, bounded context, state, budgets, authorization, recorded effects and observable completion. Reuse those mechanisms behind interfaces, then supply environment-specific adapters and acceptance checks. Specialization may require harness extensions, such as streaming media or a sandbox, but those extensions should have clear contracts. Do not copy an entire runtime for every new job when only its tools and verifier differ.

The cost model changes too. Research may spend on repeated retrieval; coding on sandbox time and long outputs; voice on streaming latency and session duration; operations on multiple evidence sources. Account for the whole task, including verification and failed attempts. A cheap answer that repeatedly fails its acceptance test is not necessarily cheaper work. Compare cost per successful outcome, and report safe escalations separately from unverified claims of completion.

## Interview drills

To compare two specialized agents, explain their environment, action surface, evidence and dominant failure. Then identify the harness contract they share. A coding agent can run tests but must not control the protected judge; a browser agent can click but must verify the resulting record. This makes the answer specific without treating every specialization as a new architectural universe.

For a voice or operations design, separate responsiveness from authority. State the latency or recovery target, the external evidence that decides success and the policy that authorizes effects. Explain an interruption or unknown outcome. For a research design, show an unsupported question and the exact partial response it should produce. The strongest demonstration is often the boundary where the agent correctly stops instead of improvising.

## Key takeaways

Specialists differ most in what they can observe, what they may change and how they prove completion. Reuse ownership and control, but choose verification suited to the environment. Read-only work still needs confidentiality and injection defenses; test execution remains untrusted execution; cancellation does not undo a committed effect. A field-service team is effective because shared dispatch and specialist evidence work together, not because every worker carries every tool.
