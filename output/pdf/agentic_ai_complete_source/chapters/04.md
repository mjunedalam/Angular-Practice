# 4. Prompt & Instruction Architecture

ShopAssist's refund behavior changes when its instructions change. A sentence that once said "propose a refund" may become "issue a refund," altering tool selection and user promises even when application code is unchanged. That makes instructions an operational artifact: they need ownership, tests, versions and a way back. Their importance does not make them a substitute for policy enforcement. They tell the model how to work within a contract whose hard boundaries remain in software.

This chapter organizes instructions into a maintainable structure, then follows them from authoring to release and runtime composition. We will separate trusted configuration from customer text, use examples deliberately and test behavior against meaningful cases. The resulting system should explain both what the agent was instructed to do and what the runtime actually allowed. Those are related records, and they should never be confused.

:::analogy The operations handbook
A support company gives staff a handbook. Different owners maintain its chapters: payments owns refund rules, privacy owns disclosure rules and customer experience owns reply style. A shift lead assembles the approved edition for the job. Letters from customers and documents found during investigation go into the case file, not into the handbook as new management orders. Where it stops: a model can misinterpret or follow hostile text despite this organization. Handbook structure guides behavior; authorization, data access and financial invariants still require checks outside the model.
:::

## The instruction hierarchy

An application trust hierarchy describes which sources may define behavior. Reviewed standing policy and trusted task configuration can supply instructions. A user's request describes desired work within that policy. Retrieved documents, tool results, emails and web pages provide information whose authority must be assessed. A document containing "ignore the refund rules" is a statement found in a document, not permission to override the application. This is an architecture rule, not a claim that formatting makes every model follow it.

Map the application's policy to the actual provider's message hierarchy. Providers differ in system/developer roles, supported fields and precedence. Do not assume that combining the roles makes them interchangeable. Keep business policy ownership independent of the wire format, then let the adapter put reviewed instructions into supported fields. Trusted task-specific guidance should come from validated runtime configuration; user-supplied strings must not become high-authority instructions simply because a template inserted them there.

## Anatomy of a production system prompt

Begin with role and purpose. ShopAssist helps authenticated customers with their orders, returns and eligible refunds. State scope and an escape path: it does not handle account-security changes or legal advice, and those requests go to escalation. Define what successful work looks like, such as an evidence-backed answer or a reviewed financial proposal. This gives the model a useful destination without asking it to invent the operating rules along the way.

Next explain policies and tool guidance. Describe when to read the order, when to search the current policy and what must be verified before proposing a refund. Make reasons concrete: order identifiers must not be guessed because doing so can expose another customer's records. Explain uncertainty behavior and distinguish drafting from execution. The runtime must still enforce these rules, but clear instructions reduce invalid proposals and make the agent's normal trajectory easier to understand.

Finally specify evidence and output requirements. The model should cite retained evidence identifiers, admit missing information and produce the format the next consumer expects. A customer reply might have a short length limit and a chosen language; a routing decision needs a machine-readable schema. Avoid asking one giant output to serve incompatible consumers. The operations handbook can contain common principles, while the particular task adds the appropriate report form.

A useful starter instruction is: "Look up an identified order using the permitted order tool. Use current payment and policy evidence for refund decisions. Propose financial actions with the exact effect and evidence required by the runtime. Do not claim a refund succeeded until the payment system confirms it. If evidence is missing or conflicting, state the gap and use escalation." This is a behavioral brief, not the financial authorization mechanism itself.

## Templates, variables and task policies

Separate reviewed wording from runtime values. Tenant brand, locale, current date and configured refund-policy version can vary without copying the entire prompt. Define required variables and validate their types and permitted values before rendering. The current date should have an explicit time zone appropriate to the decision. A missing policy version is a configuration error to surface, not an invitation for the model to guess a default rule.

User-controlled content may be useful, but belongs in the request or data portion. A customer name or subject line is not trusted merely because it is a normal business field. If an instruction template says "Follow the policy supplied in $subject," an attacker can supply instructions through that variable. Keep trusted parameters narrow and place free text in a lower-authority message with attribution. The composition manifest should record which reviewed template and validated configuration were used.

```python
from dataclasses import dataclass
from string import Template

@dataclass(frozen=True)
class PromptTemplate:
    name: str
    version: str
    body: str
    required: frozenset[str]

    def render(self, values: dict[str, str]) -> str:
        missing = self.required - values.keys()
        extra = values.keys() - self.required
        if missing or extra:
            raise ValueError(f"invalid variables: {missing}, {extra}")
        return Template(self.body).substitute(values)
```

This complete renderer checks variable names, not whether values are trustworthy. Its caller must validate the source and content of values. That distinction is intentional: a generic template cannot know which tenant settings are authorized. Keep source validation in a configuration boundary and use render tests to cover absent, extra and unsupported parameters. This allows the template to stay simple without hiding the trust decision.

## Few-shot examples and behavioural constraints

A few-shot example demonstrates the response pattern or trajectory the model should imitate. Show a normal case, a decision boundary and an uncertainty or refusal case rather than several nearly identical easy answers. For ShopAssist, useful examples distinguish duplicate captured payments from a pending authorization, and a refund proposal from a confirmed completed refund. If the output includes tools, show tool order and evidence use as well as the final customer message.

Examples can also teach mistakes. A fictional identifier may be copied into a real response; an obsolete tool name may keep appearing after deprecation. Review examples with the same owners as the policy they express and test for unwanted verbatim copying. Keep them short enough that their purpose is clear. The goal is to demonstrate a reusable behavior, not to fill context with a parallel library of cases that silently becomes another policy source.

Prefer testable constraints. "Use no more than 120 words" can be measured, while "be concise" needs interpretation. Even measurable constraints should have a reason and a failure response. If a required disclosure cannot fit the length limit, define which rule has precedence rather than letting the model decide randomly. Separate style checks from factual and permission checks: a beautifully formatted reply may still contain an unsupported promise.

## Prompt decomposition and role-specific packs

Instruction packs make ownership visible. A pack might define identity, refund guidance, privacy, order-tool use or customer-reply format. Each has an identifier, version, owner, applicability and reviewed text. A composer selects the packs for the role and records their exact versions in a manifest. This lets a privacy change be reviewed once and deployed to applicable agents without rewriting every prompt. Shared ownership does not eliminate the need to test the composed result.

Reject ambiguous compositions. Two versions of the same pack should not both enter the body while the manifest records only the last one. Define a stable order, reject duplicate identifiers and detect conflicting output contracts. Automated lint can catch obvious duplicates or forbidden variables, but semantic contradictions often need human review and behavioral cases. The manifest is an audit artifact: it must faithfully describe the text the model actually received.

```python
def compose(packs, role):
    chosen = [p for p in packs if role in p.roles]
    chosen.sort(key=lambda p: (p.priority, p.name))
    seen = set()
    for pack in chosen:
        if pack.name in seen:
            raise ValueError(f"duplicate pack: {pack.name}")
        seen.add(pack.name)
    manifest = {p.name: p.version for p in chosen}
    body = "\n\n".join(p.text for p in chosen)
    return body, manifest
```

## Versioning, provenance and change control

Store reviewed instructions in version control or another controlled source with equivalent traceability. A runtime registry can serve immutable releases, but production should reference an exact approved version or content hash. A version range is useful during dependency resolution; it is not an immutable record of what a run used. Record the resolved pack manifest, model identifier, tool-schema versions and relevant configuration hash with the run.

Treat the release as a behavior change. Review the wording, run render/contract tests, evaluate on a fixed case set, stage it and canary it within a controlled traffic slice. Compare business outcomes as well as parser success: refund proposals, escalation, unsupported promises and user-language handling. A wording fix can alter behavior as much as a policy addition, so a semantic-version label is organizational shorthand rather than proof that a patch is harmless.

Rollback selects a previously approved composition. It should not require discovering an old string in logs or editing the current prompt by hand. Runs already in progress need a defined pinning rule: continue under their original version or explicitly migrate with a recorded reason. A rollback changes future instructions, not completed effects. Use provenance to identify affected runs and inspect their actual operations before deciding whether further reconciliation is necessary.

## Trusted and untrusted content

Delimit external material clearly and keep its provenance. A wrapper can mark a passage as a document with a source identifier, escape delimiter characters and bound its text. It helps the model recognize where case material begins and ends. It does not authenticate the passage or guarantee resistance to prompt injection. Least-privilege capabilities, authorization and external-action gates remain necessary when the model reads untrusted content.

```python
import html

KINDS = {"document", "tool_result", "email"}

def wrap_data(kind, source, text, limit=6000):
    if kind not in KINDS:
        raise ValueError("unsupported data kind")
    source = html.escape(source, quote=True)
    body = html.escape(text[:limit])
    return (
        f'<{kind} source="{source}" trust="untrusted">\n'
        f'{body}\n</{kind}>'
    )
```

This function protects its own tag structure by restricting the tag name and escaping the source/body. It does not remove hostile semantics. A passage can politely request a data leak without any malformed tag. Make the provenance visible, avoid promoting its statements to policy and constrain what actions can follow. Sanitization is a formatting and minimization tool within a broader boundary; confusing those roles creates a false sense of security.

## Writing instructions for today's models

Use clear goals, applicable constraints and concrete reasons. Specify when a tool is required rather than emphasizing "always" without context. ShopAssist should search refund policy before deciding refund eligibility, not before answering "hello." Ask for a short justification tied to evidence instead of a private reasoning transcript. Reasoning effort controls, when supported, belong in the adapter's evaluated model policy rather than in a universal incantation to think harder.

Prompt behavior is model-specific. Advice about calm wording, examples, document ordering or reasoning controls should be validated against the actual model and version. Put stable content first where provider prefix caching benefits from it, and volatile case material later when the contract permits. Attention needs and cache efficiency can conflict; measure both. A source's recommendation about one provider is a useful starting hypothesis, not a law that every frontier model follows.

## Testing instructions

Render tests catch missing variables, duplicate packs and deterministic composition errors. Format tests check the output contract. Behavior cases inspect tool proposals and outcomes for ordinary, ambiguous and out-of-policy requests. Injection cases place hostile instructions inside case material and verify that protected effects remain denied. Conflict cases deliberately combine incompatible guidance and confirm the release is rejected or produces the documented precedence, rather than silently accepting whichever sentence happens to win.

Run stochastic behavior cases more than once and report rates with case coverage. A single successful refusal is not proof that a policy is enforced, and a single invalid proposal need not mean the gate failed. Separate model behavior from runtime protection in the results. The model may propose a forbidden refund while the executor correctly denies it; that is a behavioral defect with a functioning safety boundary. Keeping those records distinct makes remediation more precise.

## Failure modes

Monolithic prompts make ownership obscure. Unversioned edits make regressions difficult to date. Conflicting examples create inconsistent trajectories. User data in trusted template slots opens an instruction path. Delimiter-only defense fails when hostile meaning survives clean formatting. Diagnose these mechanisms through composition manifests and representative runs. Often the fix is a smaller owned contract or an external invariant, rather than another paragraph telling the model to behave better.

## Interview drills

Explain the difference between business policy, its instruction expression and its enforced invariant using one refund example. Describe how trusted dynamic configuration enters the prompt without elevating user text. For rollback, name immutable versions, run manifests and in-flight pinning. For testing, distinguish deterministic composition checks, probabilistic behavior evaluations and guaranteed runtime denial. Those distinctions show that instructions are part of an engineered system rather than a string of wishes.

## Key takeaways

Instructions deserve the care given to other behavior-changing artifacts: structure, ownership, provenance, tests and releases. Reviewed packs explain the job; case material supplies evidence. Compose them without ambiguity, record the exact result and test it against meaningful boundaries. The handbook analogy remains useful only while we remember its limit: a model can misunderstand a rule, so important consequences require enforcement at the runtime and service boundaries.
