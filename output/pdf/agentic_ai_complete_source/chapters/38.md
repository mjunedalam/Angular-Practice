# 38. Hardening, Evaluation & Game Days

An approved rollback can be correctly executed while the incident remains unresolved. A healthy-looking demonstration can conceal a missing permission, an uncertain effect or a model change that worsens rare cases. Phases 11 through 15 complete AegisOps by connecting action to recovery, measurement, release decisions and realistic failure rehearsal. Production-oriented work becomes credible when the team can inspect both its successes and its limits.

Keep the bad-deployment scenario narrow enough to reason about, but make its failures real. A worker can disappear, a provider can throttle, approval can arrive late, and a metric source can return no data. These are separate outcomes with different responses. The capstone should handle them truthfully before its scope increases. A finite evaluation suite and portfolio score are useful evidence; neither certifies that a live system will never cause harm.

:::analogy Observing a patient after treatment
A procedure being completed does not establish recovery. The care team observes the patient, checks for new problems, and records whether the treatment helped. It also practices unusual situations and reviews failures so the next case improves. AegisOps similarly separates applied change from sustained service recovery and turns rehearsal findings into regression tests. Where it stops: software SLOs and medical outcomes are different. The observation window and acceptance criteria here are explicit service contracts, not clinical rules.
:::

## Phase 11 - Verification, compensation and failure recovery

Define recovery before remediation. The proposal names metrics, units, thresholds, affected service and dependencies, the post-action window and required sample coverage. For the worked incident, require ten covered one-minute buckets after the rollback completes, with p95 latency at most 300 milliseconds and error rate at most 0.5% in every bucket, adequate request counts, resolved relevant alerts and no defined new failures. These are illustrative criteria to adapt to the real service.

The full window begins after confirmed action completion, not at the time approval was requested. A verifier called after two minutes should return pending, not reuse eight minutes of pre-action data. Missing buckets, delayed telemetry or too little traffic mean insufficient evidence. A ten-minute aggregate can conceal a poor interval, so state whether the product requires each bucket to pass or accepts an aggregate. Here we require sustained per-bucket performance.

```python
from datetime import timedelta
from math import isfinite

def evaluate_window(start, now, buckets, alerts_ok):
    end = start + timedelta(minutes=10)
    if now < end:
        return "pending"
    expected = [start + timedelta(minutes=i)
                for i in range(10)]
    if [b["start"] for b in buckets] != expected:
        return "insufficient_evidence"
    for bucket in buckets:
        if bucket["requests"] < 100:
            return "insufficient_evidence"
        if not bucket["evidence_ids"]:
            return "insufficient_evidence"
        latency, errors = bucket["p95_ms"], bucket["error_rate"]
        if not (isfinite(latency) and isfinite(errors)
                and latency >= 0 and 0 <= errors <= 1):
            return "insufficient_evidence"
        if bucket["p95_ms"] > 300:
            return "not_recovered"
        if bucket["error_rate"] > 0.005:
            return "not_recovered"
    if not alerts_ok:
        return "not_recovered"
    return "recovered"
```

This is a pure teaching verifier for the stated criterion. The observation adapter must provide authorized, correctly unitized, complete buckets and reject invalid numeric data. The durable coordinator schedules polling until the complete window is available or its deadline passes. Dependency and new-alert checks cover an explicit service set supplied by the proposal policy. An empty optional list must not accidentally make those required checks disappear.

If verification fails, add the action and failure signals to the evidence ledger. Choose bounded replanning, approved compensation or human escalation. Compensation itself has authority, current preconditions and effect identity. Reverting a flag may be appropriate after it creates a new failure, but blindly undoing an uncertain action is unsafe. Reconcile applied state first. Preserve both the original effect and compensation as separate linked records.

Reserve RESOLVED for evidence-backed recovery in this blueprint. A human can accept residual risk or end automated work, but record that as an escalated disposition rather than incrementing verified-resolution statistics. Otherwise the requirement that every RESOLVED incident passed verification would conflict with a human override. The phase exits when partial success, missing telemetry and failed compensation produce distinct observable paths without invented recovery.

### Turn observations into the exact covered window

The companion makes the adapter boundary concrete. Action completion is 00:00:37. Its ten intervals are [00:00:37, 00:01:37), continuing through [00:09:37, 00:10:37). Ordinary minute scrape summaries do not match these boundaries and cannot be relabeled to fill them. The fake returns exact interval results; a real backend must support the equivalent range queries with verified coverage or return insufficient evidence. A thirty-second ingestion watermark makes the first eligible evaluation time 00:11:07, second 667. At 666 the adapter returns pending.

Each fixture interval contains 100 requests, zero errors and two compatible instance histogram increments. Each instance reports cumulative counts [45, 49, 50] at bounds [0.1 seconds, 0.2 seconds, infinity]. Sum the counts to [90, 98, 100]; the 95th request lies in the bucket ending at 0.2 seconds. The adapter uses its conservative 200-millisecond upper bound against the 300-millisecond criterion. This is sufficient to pass the illustrative threshold, without pretending to measure an exact p95. The error fraction is 0/100 = 0, compared with 0.005, not 0.5.

The adapter retains `metrics-0` through `metrics-9`, verifies tenant/service labels, rejects missing or duplicate intervals, low traffic, nonfinite counts, nonmonotonic histograms and not-yet-available results. All clock and interval timestamps must be finite, nonnegative numeric seconds on the same fixture clock; a complete interval cannot be available before its end. Invalid time values produce insufficient evidence. Alert and dependency acceptance are separate inputs to the pure verifier; the happy fixture explicitly supplies healthy values. One failed interval returns failed, leaving the incident open for bounded replanning or escalation. It never slides the original ten-minute window until a pass appears. A new observation policy requires an explicit recorded decision.

For classic Prometheus histograms, a production query template can sum compatible bucket rates by `le` over the authorized service, then apply `histogram_quantile(0.95, ...)`; convert seconds to milliseconds. The error-rate query divides 5xx request increase by total request increase over the same interval. Rate extrapolation, scrape gaps and counter resets still need coverage checks and backend-specific tests. The fixture uses exact interval increments and deliberately rejects malformed data rather than claiming that a query expression proves complete coverage. [Prometheus histogram guidance](https://prometheus.io/docs/practices/histograms/) explains why averaging instance p95 values is unsuitable.

## Phase 12 - Add AgentOps, SLOs and cost controls

AgentOps is the discipline of operating behavioral systems over time: releases, outcomes, authority, incidents, budgets and recovery. Instrument model and tool latency, failures, retries, token use, cost, handoffs, approval wait and complete incident duration. Keep one correlation chain across workers and remote services. Redact before export, and keep authority/effect audit records independently of trace sampling. One useful trace explains why a particular rollback was proposed and what actually happened.

Dashboards need both platform health and task outcomes. Ingestion, queues and worker availability explain capacity. Time to triage, evidence sufficiency, safe action and verified recovery explain service value. Track safe escalation separately from false completion. Zero successful unauthorized actions is a hard invariant to monitor; denied attempts remain security evidence. Unsupported report claims, excessive approvals and stale decisions reveal quality problems that a green infrastructure dashboard cannot show.

Route model work by measured task needs. Classification and bounded extraction often fit smaller tiers; hypothesis generation can justify a stronger tier; communication should remain factual and templated regardless of model size. Use an independently calibrated evaluator when it contributes information. Per-run and per-tenant admission and usage budgets should prevent an incident storm from consuming all capacity. Provider failure or budget exhaustion degrades to scoped useful work or explicit human ownership.

The phase exits when one dashboard shows platform health, one trace reconstructs a critical action, and operator drills demonstrate safe budget and provider-limit handling. Reconcile the usage ledger with billing under the actual provider's cached-token and pricing rules. Include verification, failed attempts and sampled evaluation in per-incident model spend. A quality-preserving routing change can reduce costs; a cheaper unresolved run cannot be advertised as the same outcome at a discount.

## Phase 13 - Build the evaluation and regression suite

Start a regression set with one hundred labeled scenarios as a teaching minimum. Include twenty clean single-cause cases, twenty ambiguous cases, ten false alerts, ten tool failures, ten approval/stale/idempotency cases, ten injection/exfiltration cases, ten cross-tenant denials and ten long-running restart cases. The categories deliberately include work that should stop safely. An agent trained only on incidents it can repair learns to force a fix even when escalation is the correct outcome.

Deterministic tests cover tool contracts, authorization, state transitions, effect identity and restart. Trajectory evaluations examine evidence gathering, forbidden calls, plan length, required approval and verification. Outcome evaluations examine correct repair or escalation, claim support, communication and recovery. Safety evaluations include cross-tenant access, secrets, destructive requests and compromised inputs. Run candidate and baseline under the same task and grading conditions, with repeated trials measuring instability.

Choose gates per critical slice, not just the headline average. Use slice analysis and report confidence intervals over independently labeled cases and disclose how repeated outcomes are aggregated. Ten cases in a critical slice cannot establish a very low universal failure rate; expand coverage for deployment risk and observed gaps. Freeze a holdout for release decisions, keep training or prompt examples separate, and version additions from game days. Prevent a good demo from becoming a leaked evaluation answer.

A judge needs human calibration and a pinned measurement version. Check deterministic citation and proposal properties before invoking it. Do not upgrade both the behavior and an uncalibrated judge, then interpret a larger score as improvement. A new judge requires a separate calibration record and a comparable measurement transition. Track production human spot-checks so drift becomes visible. The release report should name the behavior bundle, dataset and grader versions together.

The phase exits when major known failure modes have reproducible cases and CI blocks critical regressions. Produce slice-tagged reports, cost and latency comparisons and inspectable failed trajectories. A passing suite authorizes the next stage of shadow and canary release observation, not an assertion of complete safety. Repeat evaluations when models, tool schemas, context policy or runbooks change. These artifacts alter behavior even if the application's Python source remains identical.

## Phase 14 - Productionise on Kubernetes/OpenShift

Deploy entry, orchestration and workers with independent scaling and ownership. Keep durable records outside ephemeral pods, using an operated database and restore policy. Apply resource limits, disruption budgets, readiness and liveness checks suited to each role. Queue-depth and latency-driven scaling needs maximum concurrency and downstream capacity limits. More workers cannot fix an exhausted model quota or an overloaded telemetry backend, and can make that failure worse.

Workload identity and network policy restrict model, tool, workflow, state and telemetry access. Explicitly include the flag service and secret-issuance path when workers use them, or document the sidecar/control-plane route. Container image files remain readable unless additional confinement is applied; omit sensitive mounts rather than assuming a read-only root hides them. Separate production-change credentials from ordinary investigative workers and test the actual enforcement point.

GitOps pins a behavior bundle and stages rollout. Keep active incidents on compatible versions and rehearse rollback with waiting approvals and recorded effects. An emergency mutation kill switch fails closed at the execution boundary while diagnosis and approved factual communication remain available. The switch stops new effects; it cannot unsend a committed rollback. Operators must still reconcile in-flight outcomes and report them accurately after the switch changes.

The phase exits when canary and rollback preserve owned incidents, a killed worker resumes, and the stop control denies new mutations without losing visibility. Test restore from backups, not only rolling restart. Record recovery objectives for domain state, audit and search separately. A cluster manifest can name a high-availability database without proving its restoration or retention configuration; operating evidence belongs with the deployment record.

## Phase 15 - Run enterprise game days

A game day exercises realistic combinations of dependencies, permissions, timing and human response. Begin in a safe environment with synthetic incidents and reviewed effect limits. Collect traces, timeline, operator observations and outcome scores. Fakes are useful for precise contract tests, but a live rehearsal may expose an incorrectly scoped token, an alert channel nobody sees or telemetry arriving too late. Each discovered defect becomes a reproducible regression case.

Run six core scenarios. First, the bad release follows evidence, privileged approval, rollback and verification. Second, partial telemetry outage reduces confidence and leads to fallback or escalation. Third, a malicious log or runbook instruction remains untrusted and cannot execute forbidden work. Fourth, approval after a changed revision is rejected by current preconditions. Fifth, an accepted rollback leaves the service unhealthy, so verification fails. Sixth, duplicate delivery finds or correlates existing work without another effect.

Debrief without treating the model as the only possible cause. A missing approval route or mistaken retry policy is a system defect. Update runbooks and skills through versioned review, and distinguish observed failures from suspected causes. The phase exits when every deviation has an owner and regression evidence, with repeat rehearsals confirming repair. Do not invent an improving chart; publish the actual number of scenarios following their expected safe path and explain the remaining gaps.

## The end-to-end recipe: bad deployment incident

The alert records order-api latency and errors. Ingestion finds or creates the owned incident and triage identifies affected users and environment. The commander selects observations, changes and knowledge in parallel within scope. Evidence shows symptom onset after a release and concentration on new pods, while competing dependency explanations are tested within their actual coverage. The resulting hypothesis remains qualified by the available observations rather than promoted to absolute certainty.

Remediation drafts a rollback from the live revision to an approved target, with evidence, blast radius, expected revision, rollback-of-rollback plan and verification. Risk 4 requires two distinct privileged approvers. Precondition re-validation is part of execution: it validates the current proposal and consumes or reserves authority, then the change service atomically checks revision and applies the persisted effect identity. A lost response enters reconciliation. A confirmed applied result starts the complete post-action verification window.

After all covered criteria pass, the incident becomes RESOLVED. Otherwise it remains open for bounded replanning or is escalated with residual-risk disposition. Communications derives facts from state; the postmortem links timeline, evidence, authority, action and outcome. The usage ledger records the cost, and evaluation scores the trajectory. The channel's short message is useful because the deeper records exist, not because the message itself establishes the result.

## Definition of done

The capstone is complete when the supported end-to-end cases reach verified resolution or safe escalation repeatedly, with inspectable evidence. Scoped tools, reusable capabilities, durable waits, bound approval and effect recovery are implemented, not merely described. MCP and a real or faithfully simulated remote-agent boundary demonstrate the curriculum where justified. The number of specialist processes is not an independent safety criterion; explain merges that preserve contracts.

Required failures include injection, cross-tenant denial, stale and replayed approval, process loss, provider uncertainty and failed recovery. CI gates behavior, the deployment supports bounded rollout and emergency stop, and game-day findings are retained as tests. Reviews record exceptions and residual risk. A learning build can use fakes honestly; production use additionally needs organization-specific integration, operating evidence, governance and an authorized release decision.

## The capstone scorecard

Use a weighted portfolio rubric: problem framing 10%, architecture/contracts 15%, evidence/reasoning 15%, safety/control 20%, reliability 10%, evaluation 15%, operations/cost 10% and communication 5%. Score one for a demonstrated basic path, two for explicit contracts with repeatable tests, and three for stronger negative evidence and operating rehearsal. Weighted scores help find weak areas; hard safety and recovery gates cannot be averaged away.

For example, three on safety, evaluation and reliability and two elsewhere yields 2.45. Improving evidence to three adds 0.15. These numbers describe the portfolio rubric, not a certification threshold for live production. Attach evidence behind each score: a reviewer should be able to reproduce the denial, restart or verification rather than trust the author's self-assessment. An impressive diagram and a weak uncertain-effect contract still leave the capstone unfinished.

## Final interview / demo walkthrough

Begin with the users and why adaptive investigation helps. Draw the control plane, then follow one incident from alert through evidence, competing causes, bound approval and verified recovery. Show a forbidden request and a crash rather than hiding them behind a happy-path video. Explain which records survive, which principal authorizes the effect and which criterion resolves the incident. Close with the most important trade-off and what you would simplify.

## The portfolio package

The README runs the fake scenario quickly and names its limitations. Architecture views explain owners and boundaries; decisions explain rejected alternatives; safety evidence shows negative tests; quality evidence reports slices and intervals; operations evidence shows dashboards, budget and game-day results. Add a short demonstration and a story bank covering stale approval, hostile evidence and a measured cost regression. A reviewer should understand the artifact before opening every source file.

## Extension challenges

Extend only after the core evidence holds. Regional failover adds region-aware risk and verification. AegisOps monitoring itself adds agent-platform symptoms without granting self-modification. A security handoff transfers ownership and stops inappropriate remediation. Self-hosted triage needs measured quality and total operating cost. Multi-tenancy adds negative scope tests. A learning loop opens reviewed procedure changes as pull requests rather than updating production instructions automatically.

## Interview drills

Explain why an API response cannot resolve the incident and why missing telemetry cannot count as recovery. Explain how a model upgrade passes the same baseline comparison and rollout as other behavior changes. Explain stale approval and immediate replay as different tests. For an executive metric, show time to verified recovery against an appropriate baseline alongside unsafe-action count and workload scope. Speed without these qualifiers can reward the wrong behavior.

## Key takeaways

Hardening joins applied effects to independent recovery evidence, then joins releases to calibrated measurement and real rehearsal. Keep pending, unknown, failed and verified states distinct. Operate budgets, authority and emergency controls at the enforcement boundary. Game days turn surprises into repeatable checks, while portfolio evidence states its limits honestly. Trust grows from records that survive failure and explanations that remain true when the demonstration's assumptions break.
