# 2. What Is an AI Agent? Anatomy, Autonomy & Boundaries

ShopAssist could answer a refund question by following a fixed script: fetch the order, check a policy and draft a reply. It could also investigate a less predictable problem, choosing another payment lookup when the first result reveals something unexpected. Both systems may use the same language model. What changes is who chooses the next step and how much freedom that choice has. This chapter turns that distinction into an architecture you can inspect.

We will use a deliberately narrow working definition: an LLM agent is a goal-directed software system in which a model repeatedly chooses among bounded capabilities, observes results and continues until verified completion or an explicit stopping condition. Other fields use broader meanings of agent. Our definition is useful because every part maps to something an engineer must implement, test and operate. It also makes autonomy a design decision rather than a marketing label.

:::analogy A taxi with a destination and operating rules
A taxi passenger chooses a destination, while the driver chooses turns using current traffic and road conditions. A fixed train route chooses the path in advance. The taxi company still sets operating rules: licensed driver, permitted area, fare limits and a way to stop the journey. An agent resembles the taxi when discoveries change its route; a workflow resembles the train when known steps determine the path. Where it stops: software authorization must be enforced before actions, and a model is not a licensed person exercising accountable professional judgment. A driver analogy does not prove that a generated decision is safe.
:::

## Chatbot, LLM app, workflow or agent?

A chatbot is an interaction pattern: the user asks, the system replies. That interface may conceal a simple model call, a fixed workflow or an agent. An LLM application is the broader category of software that uses a model; it does not imply autonomous control. A workflow defines its sequencing and available branches in application code. The model may classify a ticket into one of those branches while the workflow retains overall control.

An agent repeatedly decides what to do next from observations. The number and order of useful operations may not be fixed beforehand. ShopAssist investigating duplicate charges might first inspect payment records, then consult a refund policy, then ask for clarification if the records contradict the customer's account. The capability set and boundaries remain authored. Model-directed sequencing does not require unrestricted tools or the ability to invent new privileges.

Most useful systems mix these shapes. A fixed support workflow can contain one bounded investigation node. Conversely, an agent can call a refund skill whose eligibility checks and transaction sequence are deterministic. Ask where a decision benefits from fresh judgment and where a stable rule already describes it. Add freedom at that boundary. This is more precise than arguing whether the entire application deserves the word agent.

## Choose the smallest useful architecture first

Before adding a loop, ask whether one model call with a checked output contract solves the task. Use a fixed workflow when sources and decision branches are known. Add retrieval when the answer depends on current or private facts. Add a bounded agentic investigation when observations genuinely change which authorized source or operation should come next. Multiple agents add coordination and ownership obligations; they need a concrete division of work and evidence of value. Chapter 35 returns to this design review with the full operating picture.

Model adaptation answers a related but different diagnosis. Unclear instructions or malformed output suggest improving prompting, schema and validation first. Missing or changing facts suggest retrieval and source lifecycle work. A stable recurring behavior with reviewed training examples may justify evaluating fine-tuning. Serving cost or latency may suggest routing, caching, distillation or serving changes, all under the same quality gates. These interventions can coexist and none guarantees improvement. Chapter 30 supplies the detailed adaptation discussion; start with a measured failure, not a favorite technique.

## The anatomy of an agent

Start with a task specification. It describes the desired result and how the controller can verify it. "Resolve the duplicate charge" is incomplete unless resolution means something observable: the duplicate capture was identified, an allowed refund was recorded, the customer received the outcome and the support ticket contains evidence. Some tasks have softer completion criteria, such as a sufficiently supported research answer. Their verifier needs a documented rubric rather than pretending that every outcome is mechanically provable.

The controller runs the loop and decides whether work may continue. It asks a context builder for the current view, invokes a model adapter, checks proposed operations and collects results. A tool registry names available capabilities and their contracts. A policy component checks identity, resource scope and risk. State records what is true about the run; memory may contribute governed information from earlier runs. Telemetry explains which steps occurred and why the run stopped.

These components have different kinds of uncertainty. Controller logic can be deterministic while a database result changes between reads. A tool may call an unreliable network service or even another model. Therefore "outside the main model" is not the same as "always deterministic." The goal is explicit contracts and owners: deterministic checks enforce invariants, while variable external behavior is bounded, recorded and reconciled. Pretending all tools are predictable makes recovery harder to design.

## The agent loop: observe, decide, act, update

Observation begins before the model speaks. The runtime assembles the user's request, current goal, relevant state, allowed tool descriptions and fresh evidence. ShopAssist handling ORD-104233 starts with customer identity and an order lookup permission. It does not start with permission to refund an arbitrary payment merely because the user mentioned money. The context records what is known and what remains to be checked so the model does not reconstruct progress from guesswork.

The model then proposes list_payments for the order. The controller validates the identifier and confirms that the authenticated customer may inspect that resource. If allowed and within budget, the executor calls the payment service. Its result contains two captures of 2499 minor units, each with a stable payment identifier and timestamp. The runtime records the observation, its source and its retrieval time. Only then can the next decision reason about a duplicate capture.

Suppose the next proposal is a refund. The same loop now encounters a financial action requiring stronger checks. The runtime confirms the captured and already-refunded amounts, derives the remaining refundable balance and creates an approval proposal bound to the exact payment, currency and amount. It checkpoints the pending work and returns a waiting outcome. The model has changed the route, but it has not bypassed the route's gates. Chapter 18 develops approval binding and review in detail.

## Deterministic boundaries around probabilistic decisions

A prompt can tell ShopAssist never to refund more than the captured amount. That instruction helps the model propose sensible actions. The refund service must enforce the same invariant against current records because another input, another model version or an injection may produce a different proposal. Put checks where their protected consequence occurs. The service boundary is also valuable because the invariant still holds when a human tool or another application uses the service.

Checks before the model govern what information and capabilities it receives. They include task schema, authenticated identity, tenant isolation, data classification and allowed tools. Checks after the model govern whether a proposal may become work: argument validation, resource authorization, risk routing and available budget. Checks after execution govern what may be recorded as fact or success. This three-part structure avoids making the model the last line of defense at any important boundary.

A useful review test is to replace the model with an adversarial scripted source. Let it propose every registered capability, oversized amounts, foreign order identifiers and false completion. What remains protected? If a dangerous operation now executes, the architecture relied on cooperative generation rather than enforcement. This test does not prove the application is universally secure, but it reveals missing boundaries cheaply and without a live model.

## Autonomy levels

Autonomy describes how decisions become actions. In an assisted mode, the system provides information and a human performs the operation. In a propose mode, it prepares an exact action for human approval. In a supervised mode, some bounded actions proceed automatically while riskier ones require review. In an autonomous mode, an evaluated action class proceeds within policy, with monitoring, audit and a fast way to suspend further work.

Choose these modes per action class, not once for the whole agent. ShopAssist may autonomously retrieve the customer's own order, propose a refund for review and always escalate an account-security change. Read access still requires entitlement and egress controls. A low-risk internal ticket note may have a different policy from an external message, even when both tools look like text writing. Classify consequence, reversibility and blast radius rather than treating every write alike.

Promotion needs evidence relevant to the action's harm. Approval acceptance rate is one signal, but a high rate can conceal rubber-stamping or rare severe errors. Combine representative evaluation, rejection detection, incident history, review quality and governance requirements. Define how promotion is reversed. A configuration change should stop scheduling the action class promptly; active operations still require their own cancellation or reconciliation. More autonomy is useful only when it creates value at an acceptable operational cost.

## Termination: budgets, loop limits and completion criteria

Success is an outcome supported by acceptance evidence. A model saying "done" is a claim to inspect. For a refund task, ask the payment service whether the intended refund exists and record its status. For a coding task, run the agreed checks and inspect the resulting artifact. For research, verify coverage and support according to the stated rubric. Different task types require different verifiers; the controller must not hide those differences behind one universal completion string.

Limits are another kind of termination. Bound model turns, executed tool calls, tokens, financial cost and elapsed time. Check remaining allowance before each operation, not only at the top of the loop. A model can return several tools in one response, and one slow tool can consume the whole deadline. An observed-cost counter can exceed a monetary limit by the cost of its last call; a hard cap requires conservative reservation or provider-side enforcement. Name the actual contract honestly.

Progress detection catches pathological work before a hard limit arrives. Repeated canonical tool arguments may indicate a stall, but repeated reads can also be legitimate polling. Define progress in the domain: new relevant evidence, a completed plan step or a changed external status. Store enough history to explain the decision. If the same payment lookup is returning unchanged data, schedule bounded waiting or escalate instead of charging for an endless model loop around it.

Every exit needs a reason and an appropriate next action. Completed, incomplete, waiting_for_approval, denied, cancelled, deadline, no_progress and outcome_unknown describe different realities. A safe stop does not undo effects already completed, nor does it guarantee that an in-flight external transaction never happened. Preserve partial results and uncertain intents so another worker or a human can reconcile them. Clear terminal states are as important to users as to incident investigators.

## Build it: a mocked decision/action loop

Before adding a live model, exercise the control boundaries with a script. The following complete function uses explicit interfaces supplied as arguments. decide returns either a finish claim or a tool request; checked_execute performs argument validation, authority checks and bounded invocation. The verifier independently assesses a finish claim. The sample is intentionally synchronous and has a turn limit; it is not yet the durable multi-budget harness built in Chapter 11.

```python
def mock_run(goal, decide, checked_execute, verify,
             max_turns=8):
    history = [{"kind": "goal", "text": goal}]
    for turn in range(max_turns):
        decision = decide(history)
        if decision["kind"] == "finish":
            evidence = verify(goal, history)
            return {
                "status": "completed" if evidence else "incomplete",
                "evidence": evidence,
                "history": history,
            }
        result = checked_execute(decision, turn)
        history.append({"kind": "observation", **result})
        if result.get("status") in {"waiting", "unknown"}:
            return {"status": result["status"], "history": history}
    return {"status": "limit", "history": history}
```

First script a valid lookup followed by a false finish claim. The verifier should return no acceptance evidence and the run should end incomplete. Then script a forbidden resource and assert that the tool counter remains zero. Finally script a mutation requiring approval and confirm that the run returns waiting without blocking for a person. These checks establish the owners of completion, authority and waiting before model variability makes failures more difficult to reproduce.

## Failure modes

An unbounded agent consumes resources without reaching a useful outcome. An overpowered agent reaches capabilities its task did not need. A premature-completion agent gives the user a confident message while the external record remains unchanged. A prompt-only policy works in happy-path demos and fails under manipulation. Each failure suggests a different repair: operational budgets, filtered capabilities, independent acceptance verification or enforcement at the action boundary. Changing the model cannot substitute for these missing mechanisms.

Another failure is choosing an agent for a stable process. If all refund steps are known and eligibility is deterministic, a workflow with classification and drafting may be simpler to operate. Conversely, a brittle workflow can fail an investigation whose next useful source depends on new evidence. Compare the smallest designs that meet the goal. The right question is where judgment improves the path, followed immediately by how that judgment is contained.

## Interview drills

When asked what makes a system agentic, identify the model's control over the next step rather than listing features such as memory or multiple tools. When asked where autonomy lives, point to concrete action classes and their gates. When asked how to prevent infinite loops, describe both hard resource allowances and domain-aware progress, then explain what record survives the stop. A good design answer connects each control to the failure it prevents.

For a support-agent design exercise, state the task and acceptance criteria first. Then name its permitted reads, proposed writes, external authorities and failure outcomes. Explain why a workflow suffices or why discovery requires a bounded agentic loop. Only after that choose a framework. This ordering makes the design review useful even when the model vendor or orchestration library changes, because reviewers can inspect the operating contract directly.

## Key takeaways

An agent is a controlled system, not merely a model with tools attached. The model may choose the route while the controller owns permission, budgets, state and stopping. Autonomy belongs to evaluated action classes. Success needs acceptance evidence, and unsuccessful runs need explicit outcomes that preserve partial work and uncertainty. These principles give the next chapter a foundation for comparing reasoning patterns without confusing flexibility with reliability.
