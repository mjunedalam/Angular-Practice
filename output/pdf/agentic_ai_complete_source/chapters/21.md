# 21. Sandboxing & Safe Execution

A data-analysis agent can turn a CSV file into a useful chart by writing and running Python. That same ability can read files, open sockets, consume memory or run unwanted processes. The model's instruction to produce a chart does not constrain what the generated program can do. Even a plausible script may contain a mistake or malicious dependency. The execution environment must therefore enforce the limits the task requires.

A sandbox is a constrained environment for running untrusted work. It separates the generated program from the harness, credentials and other users, limits resources and controls how inputs and outputs cross the boundary. This chapter examines isolation models, lifecycle, browser execution, packages and artifact release. You will design a code-interpreter tool whose useful computation remains available while the consequences of hostile or mistaken code are bounded by explicit system controls.

:::analogy Work inside a laboratory glovebox
A technician handles uncertain material inside a glovebox rather than placing it on the office desk. The chamber has controlled openings, limited equipment and a procedure for removing samples. The surrounding laboratory maintains the chamber and inspects what comes out. A sandbox similarly contains execution and mediates inputs and artifacts. Where it stops: a chamber can be flawed, and permitted openings can carry harm. Isolation depends on correct host/runtime configuration, patching and release rules; destroying the box does not erase external copies.
:::

## Why application-level validation is not enough

Static checks can reject obvious dangerous code, but they do not cover every equivalent program. A blocked import can be expressed indirectly; an allowed library can expose native code or a vulnerability; an innocent loop can allocate excessive memory. Reviewing generated code or asking another model to approve it may reduce accidents, but neither is an operating-system boundary. Assume an accepted snippet can still behave unexpectedly and design the environment accordingly.

The harness should not execute a generated script directly on its own host. That host may have service credentials, deployment access and other customers' data. A separate execution tier gives the program a restricted filesystem and network view. The harness fetches authorised inputs and passes them through the sandbox interface. This distinction allows the analysis to use customer data without giving arbitrary generated code the credential that can fetch all customer data.

Isolation also protects availability and cost. A program can be harmful without stealing anything: it can create thousands of processes, emit endless output or consume all CPU. The model should receive a clear resource-limit result rather than a platform-wide outage. Place limits where they are enforced during execution, not only in a final report. Truncating a huge captured string after the program finishes does not prevent the capture buffer from exhausting memory first.

## Isolation models and their trade-offs

A restricted process can use a separate OS user, syscall restrictions and resource limits. It may suit trusted scripts under a controlled application, but it still shares substantial host mechanisms. Containers add namespaces and cgroups to separate filesystem and process views and account for resources. They commonly share the host kernel, so an escape vulnerability can cross the intended boundary. Hardening and deployment context matter more than the word container.

A user-space kernel such as gVisor intercepts much of the application's system interface and implements it in a separate sandbox kernel. A microVM such as Firecracker uses hardware virtualisation with a reduced guest/device model. A full virtual machine offers another guest boundary with a broader operating environment. These are different attack-surface and compatibility choices, not a universal ladder where every later item is stronger under every threat and workload.

For hostile multi-tenant code, consider a managed execution service or a carefully configured user-space-kernel or microVM environment. Check required system calls, native libraries, storage access and performance. A fast startup benchmark under one small image does not predict the startup of a large analysis environment. The operational decision includes image distribution, runtime patching, host isolation, scheduling and cleanup, as well as the boundary used while the program runs.

The surrounding host remains part of the security design. Firecracker's production guidance includes its jailer or equivalent restrictive constraints; gVisor has deployment choices that affect its isolation. Do not give the sandbox privileged host mounts, the container runtime socket or broad cloud metadata access. Separate execution nodes can reduce shared exposure, but their identity and network policy still need review. Stronger isolation does not compensate for intentionally mounting the wrong secrets inside it.

## Resource controls: files, network, CPU, memory and time

Give every run a read-only base image and a bounded writable scratch area. Input datasets should be read-only where possible. Avoid exposing a broad host directory merely because the program needs one CSV file. Validate paths and reserved names before copying inputs; an input called main.py must not replace the script the harness intends to execute. Protect the output collection path from symlink escapes and other attempts to export files outside the approved workspace.

Deny network by default. When the task needs an API or package source, use an approved proxy with destination and data-flow rules, enforced by network policy. DNS checks and application allowlists are useful but insufficient if code can open another socket or follow a redirect to an internal address. The program should not reach cloud metadata services, internal control planes or the public internet simply because Python networking libraries are installed.

Set CPU quotas, hard memory limits, process-count limits and wall-clock deadlines. Decide how a resource limit appears in the tool result so the agent can simplify its analysis or explain the limitation. A timeout should terminate the sandbox or its controlled execution group, not leave child processes running. Include storage and output-byte limits too. A small stdout cap can coexist with separately bounded artifact files; the two limits protect different resources.

Measure limits under hostile tests. A fork bomb tests process control; an allocation loop tests memory handling; endless logging tests streaming output caps; repeated file writes test scratch quotas. An environment that advertises a limit but applies it only after execution has not enforced the intended boundary. Record exit reason, resource usage and whether cleanup completed without leaking sensitive code or input contents into general telemetry.

## Ephemeral workspaces and cleanup

Create a workspace for one run or tightly scoped task, and do not share it across users or tenants. Destroy it after completion, error and timeout. A local finally block handles ordinary control flow, but a killed worker may never reach it. Use a reaper or provider lifetime limit that removes abandoned environments. Record cleanup failures and treat them as an operational issue rather than assuming every requested destroy succeeded.

Warm pools can reduce latency by preparing clean environments before a task arrives. A prepared instance should be assigned once and then discarded or restored through a verified reset process. Reuse must not leave prior files, credentials, process state or browser profiles behind. The strongest simple policy is single-use instances. If cost requires reuse, make the reset mechanism and its isolation tests part of the provider contract rather than casually calling the environment fresh.

Destroying a workspace removes the execution copy according to the provider's guarantees. It does not delete input data in the source system, an exported chart, provider logs or backups. The governance retention policy needs to track those copies separately. Temporary files can contain sensitive values even when the final answer does not. Encrypt and restrict execution storage where required, and specify how failed runs and forensic evidence are retained without indefinite uncontrolled accumulation.

## Browser and computer-use isolation

A browser agent runs code from remote pages, reads attacker-controlled content and can interact with real accounts. Use a disposable profile with no inherited high-privilege session or saved passwords. Give it the task's approved network and download policy. A browser-control interface should expose the required operations without exposing the host desktop, personal files or unrestricted credential store. The user-visible page is not the only content the agent may ingest through DOM or accessibility data.

Separate browsing from consequential submissions. Reading a public policy page may need no confirmation; purchasing, uploading a private file or changing an account needs the task's explicit authority and applicable policy. Show the concrete effect before an approval if one is required. A page instruction to “upload your customer export” does not establish that authority. Browser observations follow the same untrusted-content rules as tool results in Chapter 19.

When login is necessary, use the supported dedicated-account, protected credential or human-login mechanism. Do not give the model a password to paste wherever a page asks. Enforce destination and account scope, and prevent accidental navigation into privileged administrative sessions. Scan downloads, restrict their size and avoid executing downloaded content in the browser environment. Account for screenshots and trace captures as sensitive copies under the retention policy.

## Package installation and dependency controls

Package installation adds a supply-chain boundary. A model may choose a typo-squatted name, an unreviewed repository or a dependency with install-time code. Prefer pinned images containing the approved libraries needed for common tasks. If runtime installation is necessary, route it through an approved mirror with allowed packages, locked versions and hashes. A malware scan helps, but an installation mechanism that executes arbitrary setup code still needs sandbox containment and restricted network access.

Pin the base image by an immutable digest and record it with the run. Keep the image build process reviewed and patched; pinning a vulnerable image indefinitely preserves the vulnerability. Native extensions can affect compatibility and escape risk, so assess them in the chosen runtime. “Python only” is a tool-interface choice rather than a complete security boundary because Python can invoke native code when the environment allows it.

## Artifact scanning and output validation

Artifacts leaving a sandbox are untrusted. A filename ending in png does not prove that a file is a safe image, and SVG can carry active content depending on its renderer. Validate expected type using parsing, bound file and total sizes and reject unexpected formats. Sanitize active content in HTML and documents or convert through a controlled path when appropriate. Files that users download or share may also need malware scanning and destination-specific protections.

Structured results need semantic validation. A CSV can contain unexpected columns, another tenant's records or spreadsheet-formula injection when opened elsewhere. A JSON result can meet its schema while claiming an impossible total. Validate against the analysis task and known input scope before presenting it. Retain code, input and image provenance through protected references so the team can reproduce or investigate an artifact without exposing all source content in ordinary logs.

Secret scanning is another layer, not a guarantee that any file without a detected token is public. Customer data may be confidential without resembling a credential. Classification and purpose checks should determine whether the output may be released to this user or external location. A useful chart can still reveal information outside the user's entitlement. The artifact gate needs the same identity context as the input fetch.

## Egress control and secret separation

If code needs private data, the harness fetches the permitted slice and passes it as files. If it needs a live API, expose a narrow authorised proxy rather than the broad credential. The proxy must check request semantics and response scope; a generic forwarder that adds the token to any URL recreates the problem. Limit calls and bytes so the sandbox cannot drain a protected API or encode an arbitrary export through allowed requests.

Network denial should exist outside the generated program. A Python check can be removed by the same code it is supposed to constrain. The runtime and network enforce the permitted paths, while the executor supplies only approved data. This separation follows the glovebox principle: the material inside cannot redesign the chamber's openings. Still review the allowed opening itself, because a permitted destination can receive data it should not have if the payload policy is incomplete.

## Build it: an isolated Python execution tool

The following pseudocode makes the provider contract explicit. The provider must enforce all limits during execution, bound streamed stdout/stderr and output collection, expose no host credentials, and support reliable teardown plus a lifetime reaper. The file service supplies authorised inputs with safe names. `scan_and_authorise` parses artifacts and checks release entitlement. These are essential mechanisms, not empty helper names to be assumed after copying the function.

```python
def run_analysis(code, inputs, principal, provider, policy):
    if "main.py" in inputs:
        raise ValueError("reserved input filename")
    policy.require_safe_input_set(inputs, principal)
    sandbox = provider.create(policy)
    try:
        sandbox.write_file("main.py", code.encode())
        for name, content in inputs.items():
            sandbox.write_readonly_input(name, content)
        result = sandbox.execute(
            ["python", "main.py"],
            timeout_s=policy.timeout_s,
            stream_cap_bytes=policy.output_cap_bytes,
        )
        artifacts = sandbox.collect_bounded_outputs(
            "out", max_bytes=policy.artifact_cap_bytes)
        released = policy.scan_and_authorise(
            artifacts, principal)
        return {"exit_reason": result.exit_reason,
                "stdout": result.bounded_stdout,
                "artifacts": released}
    finally:
        provider.destroy_and_record(sandbox.id)
```

For a sales CSV task, the tool receives file IDs, resolves only the requester's files and writes them read-only. The script produces chart and summary outputs under out. A blocked network call should appear as a bounded failure or logged denial rather than causing the tool to enable internet access automatically. If the analysis exceeds memory, the agent can propose a smaller dataset or chunked method within the same security policy. It cannot increase its own quota by rewriting generated code.

## Failure modes and design review

Review the largest gaps first: host execution, inherited credentials, open network, shared workspaces and unbounded resources. Then review provider cleanup, file paths, dependency updates and artifact release. A sandbox can contain computation successfully while its output gate leaks data. A hardened image can still be unsafe if a host directory is mounted into it. The complete design includes creation, input staging, execution, collection, release and destruction, with observable failures at every stage.

The design question is not “is this code safe?” in isolation. It is “which behaviours can this environment permit, and are their consequences acceptable for this principal and task?” Code review and static checks are still useful because they catch errors early and inform alerts. They supplement the containment boundary. Testing should demonstrate the limits with hostile snippets rather than relying on reassuring configuration names.
