# 23. Reliability Engineering for Agents

ShopAssist sends a refund request and receives a timeout. The customer may already have received the refund, or the request may never have reached the payment service. Those possibilities require different recovery decisions. Retrying with a new operation identity can issue a second refund. Giving up without recording uncertainty can leave the case unresolved. Reliability engineering begins by preserving what is known, what may have happened and which recovery action is safe.

Agents inherit ordinary distributed-system failures and add behavioural ones. Providers rate-limit, tools fail, workers restart and people respond late. A model can also repeat an unhelpful search, select a wrong tool or keep revising a plan without progress. This chapter combines bounded calls, safe retries, durable operation records, compensation and clear terminal outcomes. Reliable does not mean nothing fails; it means failures are contained, visible and recoverable under an explicit contract.

:::analogy A delivery desk with tracking and recovery
A delivery desk assigns each shipment a tracking identity, waits only a bounded time for updates and distinguishes delayed, delivered, returned and missing parcels. It does not send another parcel merely because a phone call dropped. If a trip cannot finish, staff arrange documented returns and escalate unresolved items. Where it stops: a tracking number prevents duplicates only if the carrier enforces it. Compensation may not restore the original situation, and records can lag behind effects. Recovery must reconcile that uncertainty.
:::

## The failure landscape

Classify failures by where they occur and what is known about effects. A model call can fail with a transient network error, a refusal, a context-length problem or invalid output. A tool can fail before an effect, after an effect or with an outcome the caller cannot determine. Infrastructure can lose a worker or delay a queue message. Human decisions can expire. Behaviour can loop or terminate with a false claim of success. One retry rule cannot handle all these cases correctly.

Separate transient failure from invalid assumptions. A temporary provider error may improve after a short delay. A denied credential will not become appropriate because the agent tries again. A schema mismatch may require corrected arguments or a different contract. An unavailable resource can invalidate the plan. Record an error class and effect certainty in the observation so the controller can choose retry, replan, compensation or escalation without inferring the meaning from an arbitrary exception string.

The run state should preserve the goal, last completed stage, pending operation and known effects. Reliability mechanisms depend on these records. A final response claiming success cannot substitute for a result ledger, and a failed HTTP request cannot establish that no effect occurred. Design the states before selecting retry libraries: pending, outcome-unknown, effect-observed, compensation-pending and verified-complete describe different recovery obligations.

## Timeouts, retries, backoff and retry budgets

Every external call needs a deadline appropriate to the operation. Streaming calls also need a bound on idle time so a stalled stream cannot hold a run indefinitely. The per-call timeout belongs inside the larger run budget. If a tool normally takes two seconds, giving it an hour because the overall investigation can last an hour hides a dependency failure. Conversely, a legitimate asynchronous task should not be forced into an unrealistically short synchronous deadline.

Retry only classified errors that are likely to improve and operations whose effects remain safe under retry. Transient provider rate limits or availability errors can be candidates; respect documented retry guidance such as a server-provided delay. Validation, entitlement and context-length errors need correction or replan, not blind repetition. A mutating timeout requires same-operation deduplication or status reconciliation. It is not safe merely because TimeoutError appears in a retryable exception list.

Exponential backoff increases the delay between attempts, while jitter spreads callers over time so they do not all return simultaneously after an outage. A bounded full-jitter delay can be selected uniformly between zero and an exponentially growing cap. The exact parameters depend on latency goals and provider behaviour. Also limit attempts and total elapsed time. A well-spaced retry can still violate a user deadline if the sequence has no overall bound.

Use retry budgets beyond a single request. If every failing request sends two retries, an outage can receive roughly triple the attempted traffic before other limits intervene. A dependency-level budget restricts retries relative to ordinary traffic or available recovery capacity. Its implementation must be shared and concurrency-safe when workers are distributed. A local mutable token counter demonstrates the idea but cannot enforce a system-wide allowance across several processes.

```python
import random

def full_jitter_delay(attempt, base_s=0.5, cap_s=8.0):
    upper = min(cap_s, base_s * (2 ** attempt))
    return random.uniform(0.0, upper)

def retry_allowed(error, operation, budget):
    if not error.is_transient:
        return False
    if operation.has_effect and not operation.safe_to_retry:
        return False
    return budget.try_reserve_retry(operation.dependency)
```

This code defines two decisions, not an entire retry wrapper. `safe_to_retry` must come from the operation contract, such as a supported downstream deduplication key, rather than a model-provided flag. The budget service atomically reserves a retry allowance. A wrapper still needs RPC timeout, overall deadline, attempt cap and audit. Keeping these responsibilities explicit prevents a small teaching helper from being mistaken for crash-safe financial execution.

## Idempotency keys and duplicate side effects

An idempotency key identifies the same logical operation across attempts. Persist it with the exact intent before the first mutation, then reuse it after a timeout or restart. The downstream service must atomically recognise that identity and return or reconcile the original outcome under a documented retention policy. A new proposal with changed arguments needs a new identity. Reusing one key for different actions is also unsafe because it can conceal the mismatch or replay an unrelated result.

A local executed-action ledger is valuable but cannot alone prevent a duplicate external effect. The worker can crash after the payment service commits and before the ledger records success. On recovery, that gap must be reconciled through the downstream operation identity or authoritative status. A read-then-write check can race with another worker and therefore is not a substitute for an atomic uniqueness or deduplication constraint. Where such support is unavailable, choose manual or bounded reconciliation rather than promising exactly one effect.

Deduplicate triggers too. The same alert or webhook can arrive twice and create two runs that each believe their refund is new. Map a triggering event identity to a run through an atomic submission contract. Downstream deduplication may also need a business-operation identity that is stable across duplicate runs, depending on the workflow. Review the retry horizon: recovery after a backup restore is unsafe if the effect ledger or downstream dedupe record has expired while the run still permits retries.

## Circuit breakers, dependency health and fallbacks

A circuit breaker stops repeatedly calling a dependency that is persistently unhealthy. In its closed state calls flow normally. When the configured failure condition is met it opens and fails fast. After a cooldown it permits controlled half-open probes; successful probes can close it, while failures reopen it. Define which error classes count and avoid allowing every concurrent worker to perform its own probe surge. The breaker needs a shared or coordinated policy consistent with deployment scale.

A fallback changes how the task proceeds while a dependency is unavailable. Search can return an explicitly stale approved cache; a reranker can be skipped under an evaluated reduced-quality path; an optional specialist can be omitted with a partial-result warning. A model fallback must satisfy the task's quality, data and risk requirements. It is not acceptable to switch a restricted-data request to an unapproved provider solely to preserve availability.

Mutations require special caution. Do not silently substitute another payment route or infrastructure action after an uncertain effect. The first operation may still complete, and the replacement can create a conflicting second effect. Expose dependency failure as a structured observation so the agent can stop, reconcile or escalate. The fallback plan should describe what remains useful without the failed capability, not invent a different side effect to avoid admitting the failure.

## Compensation and saga-style recovery

A multi-system change may reserve inventory, create a shipment and charge a fee. These actions cannot usually share one database transaction. A saga records their progress and uses compensating actions when a later stage prevents the goal from completing. Compensation is a business correction, not perfect time reversal. Canceling a shipment can fail or become impossible after dispatch, and a refund may carry its own rules and timing.

Persist each step's intent and stable operation identity before executing it, then record its observed result. If the result is unknown, reconcile before deciding which completed steps need compensation. Persist a compensation phase and the remaining work, using stable identities for compensating operations too. On restart, read this journal and resume the outstanding phase rather than initialising a new in-memory completed-step list and restarting the entire saga.

The journal's ordering must be recoverable. If a crash follows a completed effect but precedes its result event, the next worker must use the step's operation contract to establish the outcome. If a compensation fails, keep that step pending or mark it for manual recovery. An irreversible completed step similarly needs a named owner and recovery plan. Calling the overall state failed-safe while unresolved harmful effects remain hides the very obligation the saga was introduced to manage.

The following pseudocode assumes a durable journal and an executor whose operation IDs have downstream deduplication or reconciliation support. The journal supplies the next outstanding compensation from persisted state. It records outcome-unknown separately from completed compensation. This is the central crash-resume mechanism; storage transactions, fencing and retry scheduling are production interfaces rather than implied features of an in-memory Python list.

```python
def resume_compensation(journal, executor):
    while (step := journal.next_pending_compensation()) is not None:
        if step.compensation is None:
            journal.require_manual_recovery(step.id)
            return {"status": "manual_recovery_required"}
        journal.record_compensation_intent(step.id)
        result = executor.perform_or_reconcile(
            step.compensation,
            operation_id=step.compensation_operation_id,
        )
        if result.status == "unknown":
            journal.record_unknown_compensation(step.id)
            return {"status": "compensation_pending"}
        if result.status != "succeeded":
            journal.record_compensation_failure(step.id, result)
            return {"status": "manual_recovery_required"}
        journal.record_compensated(step.id, result)
    return {"status": "compensated"}
```

For the replacement-item example, reserve inventory and create shipment using separate operation IDs. If the shipping-fee charge is declined before taking effect, cancel the shipment and release the reservation under their compensating IDs. If shipment cancellation fails, report manual-recovery-required and show the outstanding shipment. If the charge response is unknown, reconcile it first; assuming a decline and compensating other steps may leave a charged customer with no replacement.

## Checkpoints and resume for long-running tasks

Persist state at useful node boundaries and around consequential effects. A checkpoint records the next stage, current facts, pending decisions and operation ledger. Long waits should use a durable workflow mechanism rather than a sleeping worker. When a new worker resumes, it must revalidate facts that may have changed and preserve release/policy provenance. Resumption continues an obligation; it does not prove that old assumptions remain true.

Concurrency control protects the run from competing workers. Expiring leases need owner-aware renewal and release, fencing at relevant state/effect boundaries and defined behaviour when ownership is lost. An optimistic version check can reject a stale state write but does not automatically protect an external payment call. Use the downstream operation identity as well. Durable state, ownership and effect deduplication solve related but different problems, so test their combination rather than claiming one mechanism covers all three.

## Dead-letter handling and manual recovery

Some runs cannot recover automatically: poisoned inputs, repeated crashes, unsupported contracts or failed compensations. Move them to a dead-letter queue after a declared attempt policy instead of retrying forever. Preserve state, error classification, trace references and outstanding effects. Give the owning team an inspection interface and an explicit choice to repair/resume or close with a reason. A queue that nobody monitors is deferred failure, not a recovery strategy.

Manual replay needs the same safeguards as initial execution. Corrected data can create a different proposal, so an old approval may no longer apply. A known completed effect must not be repeated under a new identity simply because an operator presses retry. Show pending operations and resource versions to the operator. Audit who changed the state and why, and use the supported resume mechanism rather than editing arbitrary database fields without validation.

## Loop detection and multi-dimensional budgets

Behavioural reliability needs more than retry counts. Bound steps, calls, tokens, cost and wall-clock time, and measure progress through new evidence or resolved obligations. Detect repeated tool/argument pairs and near-duplicate searches, but allow legitimate rechecks after the resource version or observation window changes. A stagnant run should produce a partial explanation and escalation, not spend its remaining tokens restating the same plan.

Reserve headroom for safe exit. The allocation below is an illustrative 10,000-token run allowance, not a measured benchmark or a universal recommendation. It shows why allocating every token to investigation can leave no space to verify an effect or prepare the recovery record. Emergency compensation may have a separately governed allowance, but that allowance must remain bounded and visible rather than allowing a model to bypass cost policy by declaring every step urgent.

## Graceful degradation and partial success

A degraded mode delivers a narrower useful result under the remaining capabilities. If the logs service is down, AegisOps can report metrics and change evidence while explaining that logs were unavailable. If mutations are disabled, it can diagnose and prepare a handover rather than pretending to remediate. If all capable models are unavailable, an approved deterministic path or human queue may still serve the user. Each alternative needs its own quality and permission assessment.

Partial success belongs in state and the final explanation. Say which systems were checked, which effects occurred and what remains unresolved. Do not let an “ok” flag from one tool become a claim that the whole task completed. Verification is especially important after recovery because a compensation or fallback can change the expected result. User communication should match observed outcomes rather than the controller's intention to help.

## Retry versus replan

Retry repeats the same safe logical operation after a likely transient failure. Replan selects a different approach because the assumptions or capability availability changed. Compensation corrects known completed effects when the original goal can no longer be reached appropriately. Escalation transfers an unresolved obligation to a human owner. Choose using error class, effect certainty and policy; do not let a model's desire to finish turn an uncertain mutation into a new alternative action.
