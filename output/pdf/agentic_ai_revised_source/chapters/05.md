# 5. Agent Harness Architecture

Two teams can give the same model the same refund task and obtain very different operational behavior. One loses work when a process restarts; another pauses for review and resumes from an explicit record. One reports "done" when the model stops calling tools; another verifies the payment outcome. These differences belong to the harness: the runtime shell that converts model proposals into controlled, recorded work. Choosing a model or framework does not remove the need to design that shell.

This chapter puts the components from the first four chapters into one architecture. We will define its public surface, internal ownership, lifecycle, policy hooks and stop behavior. ShopAssist remains the concrete case, but the same separation supports AegisOps investigations and later capstones. Our goal is an understandable contract that can be implemented by several technologies while retaining the same important behavior.

:::analogy A railway control room
A railway control room coordinates journeys using schedules, track availability, operating rules and recorded signals. A driver's judgment matters, but it does not independently grant access to an occupied section of track. A train's planned journey can change without replacing the control room. Controllers retain the journey record and manage stops, holds and completion. Where it stops: a software harness cannot physically stop every external operation once it has begun. Cancellation, uncertain effects and authorization require explicit contracts with the systems performing the work.
:::

## Harness, model, agent, framework, runtime

The model is the component producing a proposal from available context. An agent definition configures a goal-directed behavior: instruction releases, capabilities, model policy, limits and evidence requirements. The harness executes that definition using a loop and shared operational controls. A framework supplies libraries or execution machinery that may implement some harness parts. The platform hosts the workers, stores, identity services, queues and gateways needed to operate them.

These distinctions reduce accidental coupling. ShopAssist's refund agent can use the same harness as its order-status agent with a different capability set and approval policy. A framework migration should not change the business meaning of refundable balance. A provider migration should not erase retained state. However, "agents are configuration" is a design goal within supported contracts, not a claim that every future domain needs no new extension. New acceptance verifiers or capability classes may legitimately require new code.

Treat the agent definition as a released artifact. It needs an identifier, resolved version, instruction manifest, tool-contract versions, model policy and limits. Record that release on the run so an investigator can explain behavior later. Avoid mutable latest references in records describing completed work. A new configuration release can affect future runs while existing work remains pinned, or it can trigger an explicitly recorded migration. Either policy is defensible when its consequences are understood.

## Prompt, context and harness: three layers of agent engineering

A prompt explains how the model should behave. Context supplies what it can know for this decision. The harness governs how the system acts, retains work and stops. These layers interact, but their failures differ. Poor tool guidance may cause the wrong proposal; missing current payments may cause a bad conclusion; a lost intent checkpoint may cause an uncertain or repeated effect. Diagnose the missing responsibility before adding more instruction text.

Follow one failed refund to make this concrete. If the model chooses an order tool for a product question, inspect routing and the capability contract. If it promises a refund using yesterday's balance, inspect freshness and context selection. If the payment service completed a refund but the runtime lost its response and repeated the write, inspect effect identity and recovery. A stronger model may reduce the first two error rates, but it cannot make the last mechanism durable by itself.

## The components of a harness

The controller owns step sequencing and lifecycle decisions. It asks a context manager for a bounded view, invokes the model adapter and handles returned proposals. The adapter owns provider serialization, required continuation fields, error classification and model-call retry policy. A registry supplies reviewed capability contracts. The executor validates and performs accepted operations with their deadlines and result envelopes. Domain invariants remain in the relevant service so they hold even outside agent use.

Policy is a separate responsibility. It evaluates the authenticated principal, requested resource, operation, arguments and risk. It can deny, allow or require approval. The controller turns waiting into a durable lifecycle state rather than blocking a worker for a person. State storage retains the run record and progress position. A memory manager handles governed cross-run information, while telemetry records enough events and evidence to explain decisions under the application's retention rules.

The context manager does not need to own persistence, and the executor should not invent permission based on what the model wrote. Keep interfaces narrow but carry the information each boundary needs. Resource authorization cannot happen if the request contains only a tool name and no authenticated principal or target. Conversely, the model should not receive credentials simply because an executor needs them. Shared components make policy consistent only when their inputs are explicit and validated.

## The run lifecycle

A run is one attempt to meet a goal under a released definition. A step is one decision with its controlled consequences. An event records something that happened: a request was accepted, a model responded, approval was required or an effect returned a result. Named states make those records operable. Running, waiting, paused, completed, incomplete, denied, cancelled and outcome_unknown should not collapse into one ambiguous done status.

Legal transitions depend on the operating contract. A running refund proposal may enter waiting_for_approval. An approved, unexpired, unchanged proposal may resume execution after fresh authorization and precondition checks. Rejection should produce a denied record or an allowed explanatory path, never execute the mutation. A cancelled or completed run should not resume merely because a duplicate signal arrives. State transitions are owned by runtime logic, not by a generated status string.

Events form an append-only explanation of the run. Assign per-run sequence positions and stable identifiers so readers can identify duplicates and resume projections. The state can be rebuilt from validated events when event sourcing is the chosen design; snapshots avoid replaying an entire history. Not every small harness needs full event sourcing, but every resumable harness needs a clear authoritative record. Logging messages at the end of a run is not equivalent to retaining accepted intents before effects.

## A framework-neutral runtime interface

Expose a small public API: start a task, inspect status, read events, pause, cancel and resume with an authenticated signal. A step method can help tests and interactive tools advance work deterministically. Do not expose provider SDK objects or framework callbacks as the public contract. A task identifier and released agent definition should be enough to locate the implementation details behind the boundary.

```python
from typing import Protocol

class Runtime(Protocol):
    def start(self, task: dict, principal: dict) -> str: ...
    def step(self, run_id: str) -> dict: ...
    def status(self, run_id: str) -> dict: ...
    def events(self, run_id: str, after: int) -> list[dict]: ...
    def pause(self, run_id: str) -> None: ...
    def cancel(self, run_id: str, reason: str) -> None: ...
    def resume(self, run_id: str, signal: dict) -> dict: ...
```

This is an interface declaration, not a runnable service. Define who may call each method, whether start accepts a caller-supplied idempotency identity and how concurrent advancement is prevented. An approval signal must be authenticated and bound to the exact pending proposal; a plain boolean from an arbitrary caller is insufficient. The API also needs a stable event cursor and explicit responses for waiting and terminal runs. Small does not mean vague.

## Where cross-cutting concerns live

Give each retry type one owner. The model adapter handles provider-call retries according to classified failures. The tool executor handles retries permitted by a capability's effect contract. The controller handles replanning and decides whether a failed step needs a new action. If all three automatically retry the same write, the composed system can multiply attempts. The responsibility boundary is more valuable than a generic retry decorator added everywhere.

Budgets belong to the controller's authoritative accounting, with checks at every relevant boundary. Authorization belongs to the policy/service boundaries. Approval routing belongs to policy, waiting belongs to the controller and the proposal belongs in retained state. Context minimization and egress policy belong before information reaches the model; telemetry has its own redaction and retention boundary. A shared concern may have enforcement in several layers, but its contract and primary owner should remain explicit.

Business logic belongs to domain services. Refund balance, order ownership and existing-payment reconciliation are not generic graph-node behaviors. Putting those rules inside framework callbacks makes another integration path or framework migration a possible bypass. A domain service can enforce the invariant for every caller. The harness then handles generic lifecycle behavior and explains the policy result, which makes both layers easier to test and reuse.

## Cancellation, pause and resume

Cancellation stops scheduling future work as soon as the controller observes it. Check before context building, model invocation and each tool operation, not merely between large steps. In-flight calls need their own timeout or cancellation support. An irreversible operation might finish after cancellation is requested, so record its identity and reconcile the result. Tell the user whether work stopped, whether an effect completed or whether the outcome remains unknown.

Pause preserves resumability without necessarily indicating an external decision. Waiting is a specialized pause for an expected signal such as approval, a webhook or a timer. Save the pending position and all information needed to continue before releasing the worker. Resume reloads the record, checks the signal and revalidates the environment. A provider or tool version changed during a wait must be handled under an explicit version/pinning policy rather than silently altering the approved work.

Choose deadline semantics deliberately. An absolute run deadline includes review waiting; an active-execution allowance may exclude it. A daily task can be limited by both. Persist timestamps and consumed allowances in forms meaningful after process restart. Resetting a monotonic start value can be legitimate for a new active interval, but it must not erase total consumed time or make an absolute deadline renewable on every resume. Chapter 7 develops durable records for those choices.

## Hooks for policy, tracing and evaluation

Hooks provide named extension points, such as before_model, after_model, before_tool, after_tool, step_end and run_end. They let a platform add context checks, accounting, tracing and online evaluation without copying the controller. Define their order and contracts. A before_tool authorization hook must either allow an exact operation or fail closed. A telemetry hook's failure may have a different availability policy, but that choice must be explicit rather than inherited accidentally.

Keep critical controls mandatory, not optional plugins a run can omit. Extensibility should not allow an agent definition to bypass authorization or mutate state outside the transition rules. Record hook versions when they influence behavior. Bound the time and data consumed by online evaluation so observability cannot become a new runaway path. An extension point helps maintainability only when its failure behavior and authority are visible.

## The execution loop, end to end

Trace ShopAssist's cancellation request. The controller loads state and remaining limits, then assembles permitted context. The model proposes cancel_order. The policy component checks ownership and current cancellability, and the executor persists the accepted intent before submitting the effect. After execution, it records the result and the controller verifies the actual order status. A final drafting call explains the outcome without granting itself permission to change it.

A final model response is a completion claim, not necessarily success. Invoke the task's acceptance verifier using external records and retained evidence. If the order is cancelled but notification is pending, record that partial outcome instead of claiming the whole task completed. For another task, such as an evidence-backed answer, the verifier may apply coverage and support rules. The harness supplies the invocation point; the domain supplies what acceptance means.

## Failure modes

Symptoms point to different components. Wrong tool choices suggest overlapping contracts or poor guidance. Missing facts suggest context selection or freshness failures. Duplicate effects suggest unstable identities, missing intent persistence or a downstream deduplication problem. Continued action after cancellation suggests boundary checks or active-call semantics. False completion suggests missing acceptance verification. Build diagnostics around these mechanisms rather than categorizing every problem as a bad model response.

## Production lens

An operable harness has one understandable lifecycle, exact released definitions, explicit authority inputs, bounded dependencies and recoverable records. Operators can identify the current state, the last accepted intent and the reason advancement stopped. Frameworks may implement storage, interrupts or tracing, but their exact guarantees require configuration and testing. The public contract should stay stable while implementation choices change, and the limitations of a small teaching harness should remain visible.

## Interview drills

Explain the harness by walking through a proposed operation: context, model, policy, intent record, execution, result, verification and terminal state. Identify who owns retries and why cancellation differs from undo. Describe how a new agent definition can reuse the runtime while adding a domain verifier where necessary. If asked whether a framework supplies reliability, distinguish its mechanics from the application's identity, effect and acceptance contracts.

## Key takeaways

The harness is the shared operating system for a family of agent definitions. It controls what the model receives, which proposals may become work, what survives failure and how the task ends. Clear ownership keeps prompts, context, domain rules and framework plumbing from absorbing one another's responsibilities. A trustworthy confirmation requires verified external evidence, while a trustworthy stop requires a record of partial and uncertain work.
