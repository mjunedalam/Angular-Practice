# 28. Cost, Latency & Model Routing Engineering

A six-step agent run pays for more than its final answer. It may send growing context several times, wait on tools, retry malformed output and ask another model to judge a proposal. A cheap individual call can therefore produce an expensive task, while a stronger model may cost less overall if it reduces retries and errors. Cost engineering needs to follow the complete outcome rather than selecting the lowest advertised token price.

Latency follows the same structure. A user waits for serial dependencies, queueing, model generation and sometimes a human decision. Some work can overlap; some cannot because the next step depends on the previous observation. This chapter measures those costs, routes work within quality and data constraints, uses caches deliberately and enforces budgets atomically. The aim is a measured trade-off whose limits are visible, not automatic downgrading whenever an invoice becomes uncomfortable.

:::analogy Choosing transport for each part of a trip
A short local errand and a difficult mountain journey need different transport. The cheapest vehicle is a poor choice if it cannot complete the route, and taking several unnecessary detours can cost more than the fare saved. Agent routing likewise chooses an appropriate model for each task while reducing wasted steps. Where it stops: model competence is measured on tasks, not guaranteed by a size label. A budget cannot make an inadequate model acceptable for a high-risk decision.
:::

## Where the money goes

Attribute spend to the calls and services that created it. Model charges can include input, output and provider-specific cache categories. Retrieval, paid APIs, sandbox compute, storage and evaluation also consume resources. Repeated context can dominate some runs, while long generation or expensive tools dominate others. Measure rather than assuming one universal largest component. Record the provider/model, applicable price version, units and whether the cost is estimated or reconciled to actual billing.

A step often sends earlier context again so the stateless model can continue. A growing transcript therefore increases later input processing unless the application compacts it or the provider reuses supported prefixes. Server-side state and caching can change the exact transport/accounting pattern, so do not assume every provider charges identical full resend cost. What matters operationally is the usage the adapter reports under its documented contract and the context policy that produced it.

Measure cost per successful task as total attributable work divided by successful outcomes under the stated population. Failures and retries belong in that cost, rather than disappearing because they have no completed answer. Also report escalation and partial-result costs when they are valid service outcomes. A team can otherwise appear cheaper by refusing difficult tasks or labeling unsuccessful runs outside its denominator. Align the metric with the service definition from Chapter 27.

## Token and tool-call cost accounting

A cost ledger stores usage events linked to run, tenant, intent, release and service. Use an idempotent accounting event identity so duplicate telemetry delivery does not double-charge the internal ledger. Separate reserved estimated spend from settled usage. Late provider records and uncertain timed-out calls may need reconciliation. A telemetry counter is useful for trends, but it may be sampled or lost and should not automatically become the authoritative financial ledger.

The following helper demonstrates one billing shape: total input includes cached input, and cached input has a separate rate. It is not a universal provider formula. Adapters must normalise the actual billable categories, including any separate cache-write or reasoning categories, without double-counting. Rates are per million tokens and represented with Decimal; production records also need currency, contract and price-version provenance.

```python
from decimal import Decimal

def token_cost(input_tokens, output_tokens, cached_tokens,
               input_rate, output_rate, cache_rate):
    counts = (input_tokens, output_tokens, cached_tokens)
    if any(type(value) is not int or value < 0
           for value in counts):
        raise ValueError("token counts must be nonnegative integers")
    if cached_tokens > input_tokens:
        raise ValueError("cached input exceeds total input")
    rates = tuple(Decimal(str(value)) for value in
                  (input_rate, output_rate, cache_rate))
    if any(not rate.is_finite() or rate < 0 for rate in rates):
        raise ValueError("invalid rate")
    regular = input_tokens - cached_tokens
    return (regular * rates[0] + output_tokens * rates[1]
            + cached_tokens * rates[2]) / Decimal(1_000_000)
```

Track non-model costs with the same care. A search provider may charge per request; a sandbox charges for runtime and capacity; an evaluation judge adds its own calls. The final user answer may cost less than the investigation that supports it. Use the ledger to compare releases and intents, then examine traces when a distribution shifts. Optimisation should follow measured excess work, not an unsupported claim that semantic caching or model replacement always saves the most.

## Model tiering and task-aware routing

Narrow classification, extraction and query-rewriting tasks can often use a lower-cost model when evaluations show it meets the bar. Ambiguous diagnosis or complex planning may need a stronger route. The labels small, mid and large are convenience categories, not fixed competence guarantees. A model can be excellent at one structured task and weak at another. Define acceptable routes by measured task/risk performance, supported features and data policy.

Routing begins with eligibility. Filter candidates by tenant-approved provider/region, required tools or output format, task quality floor and risk policy. Then choose among eligible routes using cost, latency and current health. A budget limit can reject an expensive candidate, but it must not lower the quality floor merely because remaining allowance is small. If no acceptable route fits, use the declared degraded outcome or escalate. This preserves the same safety policy during economic pressure.

A cascade tries a lower-cost candidate first and escalates when a reliable check detects inadequate output. Structured extraction with deterministic validation can be a good fit, although correct shape does not prove factual correctness. For open-ended diagnosis, the failure detector may itself need evidence and calibration. A model's self-reported confidence is not automatically a reliable trigger. Include the detector's false accepts and added cost in the evaluation of the whole cascade.

The pseudocode below shows eligibility before economic selection. `require_quality_floor` uses approved task/risk evaluation evidence, while data policy uses trusted context. `try_reserve` is an atomic allowance reservation for estimated usage, not a read-only check of the last balance. The reservation must be settled or reconciled after the request. A real router also needs current health, global quotas and a clear explanation of why a route was selected.

```python
def choose_route(request, candidates, policy, budgets):
    eligible = []
    for route in candidates:
        if not policy.allows_data(request, route):
            continue
        if not policy.meets_quality_floor(request, route):
            continue
        if not route.supports(request.required_features):
            continue
        eligible.append(route)
    for route in sorted(eligible, key=lambda item: item.cost_rank):
        reservation = budgets.try_reserve(
            request.tenant_id, request.run_id,
            route.estimated_cost(request))
        if reservation is not None:
            return route, reservation
    raise RuntimeError("no acceptable route within capacity")
```

## Provider and model fallback policies

Fallback changes behaviour even when the API looks compatible. Evaluate the fallback on the same task slices and include its data-handling terms and region in policy. A different provider may interpret tools, structured output or reasoning settings differently. A route that handles routine status questions can still be inappropriate for a high-risk incident proposal. Define a candidate list per task/risk class rather than one universal alternate model.

Handle provider errors according to their meaning. A transient rate or availability error can select an approved alternate with sufficient capacity. A request invalid under the contract should be corrected, not sent blindly to every provider. An unsupported restricted-data destination stays forbidden during an outage. If all qualified routes are unavailable, the service may use a deterministic narrow flow or human queue with clear limits. Preserve user communication and audit around that change.

Track fallback frequency and outcomes. A frequently used fallback is effectively part of the service's ordinary model mix and needs ongoing quality measurement, not merely a one-time emergency test. Plan its quota and budget capacity so it can absorb the intended failover. Unknown usage from a timed-out primary call may still need accounting; a failed response does not prove zero cost. Chapter 30 develops the gateway contract that handles these distinctions.

## Prefix, exact, semantic and tool caches

Prefix caching reuses processing for identical supported prompt prefixes. It can reduce input cost or prefill latency without intentionally substituting another answer. Stable prompt structure helps, but actual benefit depends on provider rules, supported lengths, expiry and request mix. Shared caches also have security considerations: timing can disclose information about cached content. Use the selected service's tenant/trust-group isolation controls and review retention; exact processing reuse is not “free of risk.”

An exact response cache reuses a full result under a key that includes everything relevant to correctness and entitlement. That can include model snapshot, tokenizer/template, prompt/tool schema, data/knowledge versions, locale, tenant and principal scope. Time-to-live controls staleness but does not replace invalidation after permission or source changes. Restrict response reuse to appropriate read-only, non-personalised intents or explicitly scoped personalised contracts. Do not let one tenant's similar question retrieve another tenant's answer.

A semantic cache uses similarity rather than exact identity. “Can I return an opened item?” and “Can I return an unopened item?” may be close in embedding space while requiring different answers. A high similarity threshold reduces some false hits but cannot prove equivalence. Use curated domains, critical-field checks and evaluated false-hit rates if the application adopts it. For actions or high-impact personalised decisions, decline semantic reuse rather than trusting linguistic resemblance as authorisation.

Tool-result and retrieval caches belong near the authorised capability boundary. Key them by resource, canonical arguments, tenant/entitlement context and relevant freshness/version policy. Embedding caches for dense retrieval need the embedding model/version and preprocessing contract as well as the text identity. Reusing a vector generated by a different model can silently damage retrieval. A cached result must still pass the current access rule when served; revoking permission should not leave an old cache as an alternate access path.

Do not confuse action-response caching with idempotent operation recovery. Returning the stored result for the same logical approved operation under a downstream deduplication contract is a reliability mechanism. Reusing a refund result because another request looks similar is a different and unsafe shortcut. Preserve exact operation identity, proposal binding and status reconciliation. Caching may save computation, but it cannot manufacture permission or replace a fresh resource constraint.

## Context compression and loop detection

Reduce unnecessary context before assuming a cheaper model will solve the bill. Project needed fields from tools, bound observations, retain structured state and compact old material with references. Preserve facts that matter to safety and recovery: active proposal identity, approval binding, observed effects and unresolved uncertainty should not disappear inside a vague summary. Evaluate compression for outcome and grounding, because a smaller context can omit the exception that determines the right decision.

Loop detection targets wasted decisions. Repeated unchanged searches, redundant reflection and delegations without new evidence can inflate both latency and cost. Track meaningful progress, impose per-tool/run caps and return an honest partial result when the agent stalls. A repeated request after new data arrives can be valid, so include resource/version context in the detector. Prefer removing needless work to charging the same unproductive trajectory at a lower per-token rate.

## Batching, parallelism and latency

Parallel independent calls can reduce elapsed time while leaving total work roughly similar or increasing contention. Protect shared quotas and merge partial results explicitly. Provider batch interfaces can suit offline evaluation, enrichment and backfills where completion delay is acceptable. Their actual pricing and turnaround are provider contracts to verify. Do not put interactive tasks into a slow batch merely because its unit cost looks attractive.

Streaming improves perceived responsiveness by revealing progress or text before the full operation ends. It does not automatically reduce total compute cost or validate a partial answer. Avoid presenting incomplete structured output as an authorised action. Speculative execution starts likely future work early and can waste resources when the guess is wrong. Restrict it to work whose authority and cancellation consequences are acceptable; never speculatively perform a financial or production mutation before its required gate.

## Budget enforcement per user, tenant and run

Run budgets bound calls, tokens, time and spend, with capacity reserved for verification and safe exit. User/session limits bound abuse over a period. Tenant limits enforce contractual spend and capacity. A concurrent admission service must atomically reserve allowance rather than allowing several requests to observe the same last balance and all proceed. Include outstanding reservations in the limit, then reconcile to actual usage under a declared policy.

Soft limits can trigger warnings or select a cheaper eligible route. They cannot override high-risk quality or data requirements. Hard limits can defer, reject or escalate with an explanation, while governed recovery work uses its explicit bounded allowance. Define inclusive rate boundaries: if sixty runs are permitted, admission after sixty recorded/reserved runs must not accidentally allow the sixty-first due to a greater-than instead of greater-than-or-equal comparison.

Account for imperfect estimates. Before generation, exact output usage is unknown, so reserve a bounded maximum or a defensible estimate with a policy for overruns. Financial accounting and concurrency permits have different settlement rules. A permit is released when the request finishes, while known token spend remains charged. Unknown primary usage after failover should be recorded and reconciled rather than erased to make the budget look tidy.

## Quality versus cost versus latency

Measure candidate configurations on the same evaluation set with appropriate paired uncertainty. Plot or tabulate success, critical failures, cost per successful task and relevant latency. Identify configurations that meet the quality bar; among them choose the economic/latency trade-off for the intent. A frontier is descriptive evidence from those conditions, not a universal curve that says cascades always match a strong model at a fraction of its cost.

Revisit the decision when models, prices, task mix or knowledge change. A previously useful cache can become stale, a cascade's detector can drift and a narrow model can stop meeting its floor. Record routing reasons and outcome by route so the trade-off remains auditable. The final design question is whether the service pays for useful, permitted outcomes at a predictable cost, not whether every individual call uses the cheapest model available.
