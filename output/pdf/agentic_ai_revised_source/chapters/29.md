# 29. Production Agent Platform Architecture

AegisOps can begin as one process, but its responsibilities may outgrow that process. Investigations wait for external data, approvals arrive after workers restart and many tenants share limited model capacity. The platform must preserve obligations while components scale or fail. The design is not automatically a large cluster because the word production appears; it becomes distributed where duration, load, isolation and recovery requirements justify separate components.

This chapter assembles the platform around those requirements. Stateless entry points accept work, queues or workflow engines coordinate execution, interchangeable workers run the harness and durable stores preserve state. Shared identity, policy, model access and tools enforce common boundaries. You will also examine the concurrency and disaster-recovery conditions that make “any worker can resume a run” truthful rather than a hopeful sentence beneath an architecture diagram.

:::analogy A hospital across staff shifts
A hospital reception desk registers requests, staff prioritise care and patient records let another shift continue an obligation. Shared services such as the laboratory remain independently responsible for their work. The chart, not one doctor's memory, preserves the case. Where it stops: a digital lease can expire while the previous worker continues, and copied records can lag behind real effects. A handover tag alone does not guarantee exclusive execution or safe regional recovery; fencing, versioning and effect reconciliation must provide those properties.
:::

## Reference architecture and separation of responsibility

The agent gateway authenticates callers, applies admission policy and selects the agent release and execution mode. An API records the request and returns a result or durable run identity. A queue or workflow engine schedules eligible work. Workers load state and execute bounded harness steps. The tool gateway and LLM gateway mediate capabilities and model access, while policy and approval services determine authority. Durable data services store current state, events, artifacts, audit and retrieval indexes with different contracts.

These are logical responsibilities before they are deployment units. A small service can combine several safely while keeping interfaces clear. Separate components when they scale, fail or require permissions differently. Sandboxes should remain a distinct untrusted execution tier even if the control plane is small. A shared policy service can reduce duplicated rules, but it also needs availability and fail-closed behaviour at protected boundaries. Centralisation is useful when its failure mode is designed, not assumed away.

The platform should make an agent definition thin: instructions, authorised capabilities, state schema and behaviour configuration, rather than a new copy of every identity, logging and budget service. Shared infrastructure still needs tenant-aware policy. One gateway for many teams must not collapse all authority into an unrestricted service account. Record which agent/workload and user requested each operation, and let downstream systems enforce their own constraints.

## The gateway: synchronous and asynchronous execution

Synchronous execution keeps a connection open while a short run completes, possibly streaming progress. It can suit interactive tasks with bounded duration. Asynchronous execution returns a run ID and status interface immediately, allowing work to outlive the connection. A hybrid can stream within an interactive window and continue through the durable status path if the task becomes long. The switch should be visible to the client rather than appearing as a disconnected failed request.

Submission must have an idempotent contract. An atomic mapping from client operation or triggering event identity to run ID prevents a repeated webhook or lost response from creating duplicate runs. Retain the request's trusted tenant and principal context and check that repeated use of the key matches the original request. A caller-chosen key is a mechanism, not authorisation. Scope it appropriately and avoid letting one tenant's key retrieve another tenant's run.

Cancellation is a state transition with obligations. Stop new work and requests under the applicable contract, but preserve unknown or already completed effects for reconciliation. A status API should distinguish waiting, running, partial, canceled and verified-complete where the product needs those distinctions. Authenticate status reads and callbacks. Returning a run ID without a durable record and reachable recovery path is not a complete asynchronous service contract.

## Workers, queues and backpressure

Queues decouple admission from available workers and absorb bounded bursts. They do not make unlimited backlog harmless. Monitor depth and oldest-item age, set retention and dead-letter policy, and defer or reject work when capacity is saturated. Priorities can favour interactive or incident work over batch tasks, while per-tenant permits prevent one customer from consuming every worker. Fairness and ordering depend on the selected queue; do not promise global first-in-first-out behaviour when retries or priorities intentionally change it.

Acquire a tenant concurrency permit atomically rather than checking a boolean that can become stale before work starts. Release permits under their owner and lifecycle rules. Queue visibility and acknowledgment also have contracts: a task longer than the visibility timeout may be redelivered while the first worker still runs. Renew visibility where supported, retain receipt ownership and rely on run/effect deduplication for duplicate deliveries. Acknowledging the wrong receipt or deleting another worker's lease can corrupt recovery.

Apply backpressure to the actual bottleneck. Increasing worker replicas cannot create more model quota or speed a saturated database. Bound per-worker concurrency and shared dependency requests, and make admission account for in-flight capacity. AegisOps may reserve priority capacity for incident handling and safe recovery. That policy must still be finite and observable; labelling work urgent should not let a model bypass every limit.

## Durable workflows for long-running tasks

Use a durable execution mechanism for waits, timers, external callbacks and long obligations that must survive worker changes. A workflow encodes the skeleton and decisions; activities perform model, tool and harness I/O under recorded results and retry policy. Keep workflow code within the selected engine's determinism rules. A sleeping process is not a durable timer, and a checkpoint callback is durable only if its storage and transactional contract actually provide that property.

Activities can be attempted again, so external effects still need stable operation identity and downstream deduplication or authoritative reconciliation. A workflow engine's recorded result prevents reissuing completed recorded work during replay; it cannot erase the gap after an external commit whose activity completion was not recorded. Preserve that uncertainty and make the activity contract clear. Durable orchestration and one external effect are distinct claims.

Choose one clear source of orchestration truth. If both a workflow engine and an application database store state, define which facts each owns and how references connect them. Duplicated unsynchronised status can make one system say waiting while another schedules execution. Use transactional outbox/inbox or the engine's supported durable scheduling boundary where coordination requires it. The platform must not lose a continuation because state was saved but the next queue message was never published.

## State, checkpoints and object stores

Current run state fits a durable database with versioned updates. An append-only event log supports history, while audit may need separate integrity/retention protection. Large transcripts and artifacts belong in object storage referenced by ID rather than bloating every checkpoint. Cache and lease stores can improve coordination but should not become the sole record of critical obligations. Workflow history has its engine's own persistence and retention contract.

State writes need optimistic concurrency or an equivalent owned transaction. The simplified SQL below shows a version and fencing epoch checked together. Taking over ownership must advance the epoch through an atomic trusted service; workers cannot invent an epoch. Zero updated rows means the writer is stale and must stop/reload, not overwrite the latest state. This statement demonstrates a state boundary; the external executor also needs an ownership/effect contract.

```sql
UPDATE agent_runs
SET state = :new_state,
    version = version + 1,
    updated_at = now()
WHERE run_id = :run_id
  AND tenant_id = :trusted_tenant
  AND version = :expected_version
  AND lease_epoch = :fencing_epoch;
```

Store events with stable sequence or event identities so duplicate delivery does not create inconsistent history. Save related intent, checkpoint and scheduling information atomically when the design requires them to agree. Large artifact references should point to authorised immutable/versioned objects or include a clear update contract. A database backup is useful only when the referenced object versions and event history needed for recovery remain available too.

## Vector/search architecture and multi-tenancy

A shared retrieval index can serve many small tenants efficiently if tenant and entitlement filters are enforced inside every query. An index or collection per tenant provides stronger logical separation and easier independent tuning/deletion, with more operational overhead. A cluster per tenant can provide a physical boundary for selected high-scale or regulated deployments. Choose from isolation, capacity, residency and operating requirements rather than declaring one layout mandatory for all customers.

The query layer must derive tenant and entitlements from trusted context, not a model's arguments. Retrieval of another tenant's passage followed by a final-answer refusal is already an exposure if the passage entered context or telemetry. Keep source freshness, policy versioning and deletion coverage observable. Indexes may be restored from backups or rebuilt from authoritative sources, but document the recovery time and version consistency. A rebuilt index can differ if source content changed after the backed-up run.

## Kubernetes/OpenShift, autoscaling and isolation

Container orchestration can separate gateway, API, workers, sandbox pools and model-serving resources. Scale workers using queue depth/age and observed progress when they mostly wait on I/O, rather than relying only on CPU. KEDA is one possible event-driven autoscaling integration. Concurrency and provider quota remain independent limits: forty pods each launching twenty requests can overwhelm a service even when the autoscaler correctly followed its queue target.

Define resource requests/limits, readiness, liveness and graceful shutdown. On termination, complete or checkpoint the current bounded step under its ownership contract and avoid accepting new work. Pod disruption budgets can reduce planned simultaneous disruption but do not prevent every node or region failure. Put untrusted sandbox workloads on appropriately separated execution resources with the reviewed runtime class and network policy. GPU inference has different capacity and cold-start behaviour, developed in Chapter 30.

OpenShift or another Kubernetes distribution adds platform-specific security and operational policies. Use supported identity, admission and runtime configuration rather than assuming a portable YAML fragment supplies the whole deployment. The same applies to event scalers: connection authentication, queue mode and provider-specific metadata are required alongside the scaling target. Keep examples compact and refer to the pinned platform documentation for deployable configuration instead of presenting omitted authentication as working infrastructure.

## CI/CD, infrastructure as code and GitOps

Version infrastructure, deployment configuration, agent definitions, prompts, policy, tool schemas and evaluation gates. Promote a reviewed release bundle through development, staging and production with the tests and rollout evidence from Chapters 24-27. GitOps reconciliation can provide an auditable desired-state history, but reconciliation does not prove the behaviour is correct. Keep observed running versions and outcome monitoring connected to the desired-state manifest.

State and dependency compatibility matter during promotion. A new schema must support planned resume and rollback, or the release needs an explicit migration strategy. Pin supported tool/model interfaces and keep approved rollback dependencies available. Secrets should be referenced through the platform's secret/identity mechanism, not committed into infrastructure code. Record current emergency execution controls separately from a run's reproducible behaviour bundle so rollback does not accidentally remove a containment restriction.

## Secrets, network policy and service identity

Give each component a verified workload identity and minimal service access. The worker needs model/tool gateways and relevant state stores, not unrestricted internet and cluster administration. The tool executor holds narrow downstream credentials; generated code does not. Use secrets management for unavoidable static secrets and supported rotation. Service-to-service encryption and identity, such as mTLS where appropriate, protect transport but do not replace per-action policy.

Network policy should make permitted paths explicit. Sandboxes start with denied egress; workers use approved gateways; data services restrict clients. Verify the network implementation actually enforces the selected rules. Egress proxies need destination and payload policy, not just logging. Apply tenant and purpose checks at the application boundary too, because an allowed connection to the payments API can still carry an unauthorised refund request.

## HA, disaster recovery and regional design

High availability handles component failure through replication and controlled takeover. Disaster recovery restores service after larger loss, with a stated recovery point objective for tolerable data loss and recovery time objective for restoration. Define them separately for run state, audit, operation/dedupe records, artifacts and retrieval. Replicated current state is not a backup against every erroneous change, while an occasional backup may not meet the recovery point needed for financial operations.

Regional failover must preserve the identity and outcome of in-flight effects. Reusing a key is safe only when its downstream deduplication record still exists and remains reachable for the retry horizon. Restoring run state but losing effect records can make a previously executed operation appear new. Reconcile uncertain operations before resuming mutations. Keep approved provider/region and tenant residency requirements during failover; availability does not authorise moving restricted data to an unapproved region.

Test recovery as a procedure. Restore stores and referenced objects, verify sequence/version consistency, inspect pending approvals and reconcile external effects. A healthy database endpoint does not prove all runs recovered correctly. Preserve audit integrity across the restore and document legal/retention implications of reintroducing old data. A warm standby reduces setup time but still requires tested routing, ownership and capacity at the recovery location.

## Scaling a stateful agent horizontally

Workers can be interchangeable when durable state owns the continuation and the ownership protocol prevents stale advancement. A lease has a limited validity window. A paused worker can outlive it and resume after another worker takes over. Renewal alone is not a proof of exclusive authority. Use an owner token for release/renewal, a monotonically increasing fencing token at relevant consumers and a defined stop condition when ownership is lost.

The state store can reject an old epoch, while the protected effect gateway must also prevent a stale worker from creating a new external operation. Once an external request is accepted, ownership loss may leave an uncertain result that needs the operation ledger. Downstream idempotency protects repeating the same logical operation; it does not authorise two conflicting new proposals. These mechanisms cooperate. Do not reduce the contract to “a Redis TTL ensures one worker.”
