# 16. Workflow & Graph Orchestration

An incident investigation needs room to explore. The commander may inspect metrics, compare logs and reject several hypotheses before finding a useful explanation. A production rollback needs a different kind of freedom: the system must not omit authorisation, execute an expired proposal or declare success without verification. A single unrestricted loop makes these two kinds of work look alike. Graph orchestration separates the exploratory work from the required route around it.

A graph represents execution as named steps connected by allowed transitions. Each step reads state and returns an update. A transition determines which step follows. The model can still decide within a step or select among permitted branches, but the runtime owns the graph and its constraints. You will build that structure, decide how parallel results merge, pause for external decisions and understand what persistence must provide before a graph becomes durable.

:::analogy The railway and its stations
A railway map defines stations, connecting tracks and signals that choose a route. A train cannot invent a new track simply because a passenger asks. A platform can hold it while other trains continue. Nodes, edges, routers and durable waits serve similar purposes in a workflow. Where it stops: a permitted station can still perform the wrong work. Safe routing does not constrain the tools a node holds, prove an approval is valid or make a checkpoint durable by itself.
:::

## Graph shapes and the work they fit

A linear graph has a fixed sequence, such as extract an order identifier, validate it and store a result. A conditional graph selects one of several routes, such as refund investigation or shipping investigation. A cyclic graph revisits a step, such as revising a hypothesis after a failed test. These are control-flow shapes, not promises about quality. A well-formed sequence can still extract the wrong identifier; a declared loop can still waste resources without a stopping rule.

Most agent workflows combine these shapes. AegisOps uses a fixed incident skeleton with an exploratory investigation node inside it. The investigation can make several read-only observations, but a proposed mutation must leave that node and pass through policy and approval. After execution, verification determines whether the incident is resolved or needs further investigation. This structure gives the model useful choice while preserving the transitions the service owner requires.

Think first about invariants, then about boxes. An invariant might say that no production mutation occurs without a valid approval for its exact proposal, or that no terminal success is reported before an outcome check. Draw the graph so its routes respect the invariant, then restrict capabilities so nodes cannot bypass it internally. An investigation node that already holds an unrestricted rollback tool can violate the invariant without crossing an illegal graph edge.

## Nodes, edges, routers and loop guards

A node should have one clear responsibility and an explicit input/output contract. “Investigate” is too vague unless its tool set, evidence output and budget are specified. A useful investigation node reads a goal and known evidence, uses read-only tools, and returns findings with provenance plus a proposal or escalation reason. It does not edit the whole global state arbitrarily. The runtime applies its partial update through the state rules.

An unconditional edge always selects the same next node. A conditional edge evaluates a router against the updated state. A deterministic router can inspect risk or task status. A model-driven router must return a value from a declared set, and the runtime must validate that value before dispatch. An unknown destination should produce a controlled error or escalation, not a dynamic node that a model invents through text.

Every cycle needs a guard that applies to every entrance. In an investigation graph, both a request for more evidence and a failed post-action verification can return to investigation. Limiting only the evaluator's retry branch leaves the verification branch unbounded. Count total investigation attempts or allocate a separate budget to each loop, and test the worst route. Also enforce a whole-run visit, time and cost limit so combinations of individually bounded loops remain bounded.

The guard's exit is part of the design. Throwing a generic exception at the visit limit may stop computation, but it does not automatically produce a useful or safe outcome. Record why the budget ended, checkpoint the known effects and choose a terminal status such as incomplete, escalation-required or compensation-pending. Reserve enough headroom to perform that transition. Stopping a train in the middle of an unsafe section is not the same as routing it to a safe platform.

## A minimal graph engine and its exact limits

The following teaching dispatcher owns a declared transition table and validates each result. Its state type represents the narrow information needed for this example. Nodes may return an update, but this snippet does not supply database persistence, parallel scheduling or side-effect deduplication. Those are separate contracts. Naming the limits avoids teaching that a compact dictionary loop has already solved the distributed problems addressed in later chapters.

```python
from typing import Literal, TypedDict

class RunState(TypedDict):
    next_node: str
    visits: int
    attempts: int
    outcome: str | None

ALLOWED = {
    "plan": {"investigate"},
    "investigate": {"evaluate"},
    "evaluate": {"investigate", "approve", "end"},
    "approve": {"act", "end"},
    "act": {"verify"},
    "verify": {"investigate", "end"},
}

def checked_next(node: str, proposed: str) -> str:
    if proposed not in ALLOWED[node]:
        raise ValueError("undeclared transition")
    return proposed
```

```python
def investigate_route(state, verdict, limit=3):
    if verdict == "answer":
        return "end"
    if verdict == "propose_action":
        return "approve"
    if verdict == "need_evidence" and state["attempts"] < limit:
        return "investigate"
    state["outcome"] = "escalation_required"
    return "end"

def verification_route(state, verified, limit=3):
    if verified:
        state["outcome"] = "verified_complete"
        return "end"
    if state["attempts"] < limit:
        return "investigate"
    state["outcome"] = "not_recovered"
    return "end"
```

In this sketch, every entry into investigation increments attempts before the work starts. The same counter therefore covers both return paths. A real scheduler should persist that increment and the next transition with optimistic concurrency or workflow-engine ownership. The functions also need a typed proposal and evidence contract when they become an application. The small example makes one mechanism visible: legal routes and bounded re-entry, rather than claiming an entire production harness.

## Build it: plan, investigate, evaluate, act and verify

Start with an incident goal that can be tested, such as restoring checkout latency below an agreed threshold. Planning records the relevant service, investigation scope and initial questions. Investigation gathers evidence, and evaluation chooses among answering, requesting more evidence, proposing an action or escalating. A proposed action includes exact arguments, anticipated impact and preconditions. It is a record to review, not a command that executes when the evaluator writes it.

Approval is an interrupt before the protected action. A rejected or expired decision ends that proposal safely; a modification creates a new proposal that needs its own binding. An approved decision resumes only after the application verifies identity, entitlement, proposal digest and current resource version. Execution uses the stable logical operation identifier described in Chapter 6. Verification then reads the resulting system state and checks success against the original goal.

If verification fails, the graph records the actual effect before returning to investigation. It must not pretend that no action happened. The next proposal may need compensation, an alternate action or escalation, and it receives a new identity and approval when its arguments differ. A retry of the same uncertain action reuses the original operation identity. Keeping these two cases separate prevents a retry loop from becoming a sequence of newly authorised-looking duplicate mutations.

## State passing, reducers and joins

State is the shared contract between nodes. Keep it smaller than the entire conversation: the goal, selected plan, evidence references, attempts, pending proposal, effect ledger and current status are often enough. A reducer defines how an update combines with the existing value. Scalars may replace a previous value; evidence may merge by a stable evidence identifier. The merge rule must be explicit because parallel updates otherwise lose or inconsistently overwrite information.

Suppose the metrics branch returns evidence E1 and E2 while the logs branch returns E2 and E3. A union by evidence ID avoids duplicating E2, but that raises another question: what if two records with ID E2 contain different payloads? Silently retaining whichever arrived last is unsafe. Reject the conflict, require immutable evidence identifiers or keep separate versions with provenance. Deduplication should not hide disagreement that the evaluator needs to inspect.

A join decides when the combined state is ready. It may wait for all required branches, a defined quorum or a deadline. A deadline join must record which branch results are absent and why. A result assembled from metrics and changes but missing logs is partial, even if it looks persuasive. Reducers combine values; they do not decide whether missing evidence is acceptable. That decision belongs to the join contract and the downstream policy.

For a scheduler with nondeterministic completion order, prefer reducers whose result does not change with ordering, or define a deterministic merge order explicitly. Associativity helps when partial updates are grouped differently; commutativity helps when branch order changes; idempotence helps when the same update is delivered twice. Not every state field needs all three properties. What matters is matching the reducer to the delivery and replay semantics the scheduler actually provides.

## Fan-out, fan-in and parallel branches

AegisOps can inspect metrics, logs and recent changes concurrently because these investigations have independent read inputs. Give each branch only its required state slice and its own timeout and tool budget. Sharing a mutable dictionary between branches invites accidental coordination through undocumented writes. It also defeats the least-privilege intention of scoped inputs. Each worker should return an update or a labelled failure, while the owner performs the merge.

Cancel work that is no longer needed, but await cancellation and account for external calls already started. In Python, cancelling an asyncio task requests cancellation; it does not make remote computation or effects disappear. A branch may complete while cancellation is being requested. The collector needs a clear treatment for completed, failed and cancelled tasks, and it must drain pending tasks so exceptions and resource cleanup are not left behind.

Parallelism shortens wall-clock time only when there is capacity. Three branches can contend for the same provider quota or database connection pool and become slower than serial work. Apply a semaphore or scheduler limit, include branch cost in the parent's budget and reserve capacity for safe termination. Choose independent investigations rather than parallelising steps where the second requires the first one's evidence. The dependency graph should determine concurrency, not the desire for a more impressive diagram.

## Interrupts, checkpoints and resume

An interrupt records that the next step needs input from outside the current worker. Persist the continuation, proposal and pending request, then release the worker. When the input arrives, an authorised resume operation loads the checkpoint, validates the decision and advances the run. A boolean stored in a process variable is not a durable approval. The checkpoint and decision service must survive a restart and prevent conflicting resumes from advancing the same proposal twice.

Checkpoints also support crash recovery. Saving after a node limits repeated computation, but a node that performs an external effect can crash after the effect and before the save. Its re-execution therefore needs downstream idempotency or an uncertain-outcome reconciliation path. Persisting the intention before the effect and its observed result afterward helps recovery understand the gap. A graph checkpoint alone does not give an external API exactly-once behaviour.

Use versioned state updates or workflow-engine ownership to protect a resume from a competing worker. Expiring leases need fencing and owner-checked renewal, as Chapter 29 explains. Resume may occur hours later, so re-read facts that authorise the action rather than trusting the old checkpoint blindly. A deployment version, order status or policy can change while approval is waiting. Retaining the old state supports audit; it does not make those old facts current.

## Long-running timers and durable execution

An in-process sleep disappears when the process dies. A durable workflow engine records timers, activity results and external signals so it can reconstruct progress after a restart. Temporal is one example. Its deterministic replay reruns workflow code against recorded history to reconstruct the same orchestration decisions. Model calls and ordinary network I/O belong in activities, whose recorded outcomes can be reused during replay rather than being generated again in workflow code. Workflow code must follow the selected SDK's determinism rules.

An activity can still execute more than once when an attempt fails or its completion is not recorded. The activity's external effects therefore need the same operation identity and downstream contract as any other retryable mutation. Durable execution improves orchestration recovery; it does not remove distributed uncertainty. Configure activity timeouts, retry classifications and cancellation behaviour explicitly, and keep an approval signal tied to the exact proposal rather than treating any late signal as permission for the current action.

For AegisOps, the workflow can request diagnosis, wait up to a policy-defined approval deadline, execute one approved operation and schedule verification checks. During the wait no dedicated worker needs to remain blocked. The engine still consumes durable storage and scheduling resources; “no worker waiting” is a useful architectural statement, not a claim of zero resource use. Long histories may also require supported history-management patterns rather than keeping one workflow alive indefinitely without limits.

## Choosing a graph or a free-form loop

A graph is valuable when required phases, long waits, permission changes or parallel joins must be visible and testable. A free-form loop can fit short research or debugging where the next useful read is genuinely unknown. Often the right answer combines them: the graph owns required transitions while a bounded agent chooses investigative reads inside a node. Avoid expressing every small action as a graph node if doing so obscures rather than clarifies the invariant.

Review failure modes through the route and the effect boundary together. An undeclared transition is a routing defect. Lost evidence is a merge defect. A restarted wait without a decision record is a persistence defect. Duplicate mutation is an effect-contract defect. A loop that ends without a useful escalation is a termination-design defect. Naming the failure layer makes the correction clearer than simply increasing prompts, adding nodes or selecting a stronger model.
